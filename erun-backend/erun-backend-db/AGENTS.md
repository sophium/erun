# AGENTS.md

Module-specific guidance for `erun-backend-db`. Follow the repository root and `erun-backend/AGENTS.md` first.

## Module Role

- `erun-backend-db` is the Atlas-managed database project for hosted ERun backend state.
- The default OLTP database is PostgreSQL 18 or newer.
- Do not add SQLite migrations, schema files, repository branches, or local fallback behavior.
- Store audit events in PostgreSQL with the rest of the hosted backend schema. Do not reintroduce SQLite audit storage as a simple-deployment fallback.

## Atlas Workflow

- Store Atlas configuration in `atlas.hcl`.
- Store default OLTP migrations in `migrations/default/`.
- Store declarative target schema files in `schema/` when generating migrations.
- Generate schema changes through Atlas rather than hand-maintaining API startup DDL.
- Validate OLTP migrations against the default Atlas environment.
- Keep audit-event schema in PostgreSQL schema files when audit persistence changes.

## Schema Layout

- Organize declarative schema by database object type under `schema/`.
- Put one table definition per file in `schema/tables/<table>.sql`.
- Put indexes in `schema/indexes/<table>.sql` when they are owned by one table.
- Put cross-table or specialized objects in their own object-type folders, such as `schema/views/`, `schema/triggers/`, or `schema/policies/`, when those objects are introduced.
- Keep table files focused on the table contract: columns, primary key, foreign keys, and table-level constraints.
- Keep secondary indexes separate from table files unless the index is part of a table-level uniqueness contract that is clearer beside the table definition.
- Put trigger files under `schema/triggers/`.
- Put row-level security policy files under `schema/rls/<table>.sql`.
- Put default-database foreign-key files that are clearer outside table definitions under `schema/fks/`.
- Keep primary-key defaults in table definitions, not in trigger files.
- Keep `atlas.hcl` as the ordered list of schema source files. Add new schema files there intentionally so review shows the source ordering Atlas uses.
- Do not organize migrations per table. Keep versioned migrations in one chronological stream per dialect so database upgrades preserve the real cross-table change order.
- Prefer splitting by stable ownership. Do not create vague catch-all schema files such as `common.sql` or `misc.sql`.

## PostgreSQL Types

- Use `UUID` for externally visible IDs.
- Generate UUIDv7 surrogate primary keys with column defaults that call native `uuidv7()`.
- Use `TIMESTAMPTZ` for timestamps. Timestamp columns are populated by PostgreSQL triggers.
- Native database features such as RLS, `TIMESTAMPTZ`, and `uuidv7()` are allowed in the default OLTP schema when they are the clearest way to enforce the backend contract.
- Audit tables use PostgreSQL types and constraints.

## Row-Level Security

- PostgreSQL row-level security is mandatory for tenant-owned tables in hosted deployments.
- Keep RLS definitions in schema files under `schema/rls/` and include them in the default Atlas env.
- Keep RLS statements in `migrations/default/`.
- Enable and force RLS on every tenant-owned PostgreSQL table with `ALTER TABLE <table> ENABLE ROW LEVEL SECURITY` and `ALTER TABLE <table> FORCE ROW LEVEL SECURITY`.
- RLS policies must scope rows by `tenant_id` using a database session setting named `erun.tenant_id`.
- Use `erun_current_tenant_id()` in tenant-scoped policies so a missing tenant setting denies access instead of matching rows.
- Tenant-owned tables should default `tenant_id` from `erun_current_tenant_id()` so normal application inserts omit caller-provided tenant IDs and let the transaction security context populate ownership.
- `erun_current_user_id()` is the sibling of `erun_current_tenant_id()`, reading the `erun.user_id` session setting the same way. Default a user-ownership column (such as `reviews.author_user_id`) to it rather than accepting the owner from the caller — a caller-supplied owner column is an impersonation surface the same way a caller-supplied `tenant_id` would be.
- Define policies with both `USING` and `WITH CHECK` so reads, updates, deletes, and writes all enforce the tenant boundary.
- Keep normal tenant and operations access in separate PostgreSQL roles and separate RLS policies. Do not put an `OR` branch for operations access inside tenant-scoped policies.
- PostgreSQL role `erun_tenant` is for normal tenant-scoped access. PostgreSQL role `erun_operations` is for operations-tenant access across tenant-owned rows.
- The API database login role must be allowed to `SET ROLE erun_tenant` and `SET ROLE erun_operations`, for example by granting those roles to the application login during deployment.
- Operations tenants are allowed through `erun_operations` RLS policies for tenant-owned rows across tenants. Application authorization still controls which operations tenant users have broad permissions.
- API and worker code must set `SET LOCAL ROLE`, then `erun.tenant_id`, on the PostgreSQL transaction before running tenant-owned SQL. This is database enforcement setup, not application-side filtering.
- API and worker code must set `erun.user_id` on PostgreSQL transactions that update user-owned row state, such as closing comments.
- Root tenant resolution tables such as `tenants` and `tenant_issuers` are not tenant-owned in the same way as operational tables. Access to issuer lookup must be handled through tightly scoped database roles, grants, or future security-definer functions before tenant context exists.
- Do not add new tenant-owned tables without adding the matching RLS policy file and including it in the default Atlas env source list.

## Naming And Keys

- Use plural snake_case table names, such as `tenants`, `tenant_issuers`, `users`, `user_external_ids`, `environments`, and `deployments`.
- Use explicit entity-prefixed primary key column names instead of a generic `id` on root/domain tables.
- Name root table primary keys as `<entity>_id`, for example `tenants.tenant_id`, `environments.environment_id`, and `deployments.deployment_id`.
- Use the same column name for foreign keys where practical. Tenant-owned tables should use `tenant_id UUID NOT NULL DEFAULT erun_current_tenant_id() REFERENCES tenants(tenant_id)`.
- Use generic `id` only for small private join tables or append-only internal records when the ID is never part of an API contract and no clearer entity name exists.
- Use UUIDv7 for externally visible primary keys and foreign keys that point to externally visible primary keys.
- Use `DEFAULT uuidv7()` on UUID primary-key columns that own externally visible identities.
- Give tenant-owned tables a `tenant_id` column even when another foreign key could imply the tenant. Tenant scoping should be directly visible in table definitions, query predicates, and indexes.
- Name indexes as `<table>_<column_list>_idx`, such as `user_external_ids_tenant_user_idx`.
- Scope tenant-owned natural-key uniqueness by `tenant_id`, for example `UNIQUE (tenant_id, name)` instead of `UNIQUE (name)`.
- Use `created_at TIMESTAMPTZ` and `updated_at TIMESTAMPTZ` on mutable domain tables.
- Keep column names stable and domain-specific. Avoid vague columns such as `value`, `data`, `ref`, or `type` unless the table owns a deliberately generic key-value contract.

## Primary Key Defaults

- Use column defaults to populate UUIDv7 surrogate primary keys for domain tables that own externally visible identities.
- UUIDv7 defaults currently apply to `tenants.tenant_id`, `users.user_id`, `roles.role_id`, `role_permissions.role_permission_id`, `reviews.review_id`, `builds.build_id`, `comments.comment_id`, and `audit_events.audit_event_id`.
- Define those columns inline as `<entity>_id UUID PRIMARY KEY DEFAULT uuidv7()`.
- Do not add UUID defaults for natural keys such as `tenant_issuers.issuer` or composite association keys such as `user_external_ids (tenant_id, issuer, external_id)`.
- UUID primary-key defaults must call native `uuidv7()`. Do not add a custom UUIDv7 implementation.
- Private integer queue/order keys should use native identity columns, such as `GENERATED BY DEFAULT AS IDENTITY`.
- Caller-provided UUIDv7 primary keys are allowed only for direct database imports, deterministic fixtures, and data repair. Normal application inserts should omit default-owned primary keys.
- When adding a new default-owned primary key, validate by inserting without the key.

## Timestamp Triggers

- Use database triggers to populate `created_at` and `updated_at`.
- Timestamp triggers belong in `schema/triggers/` and `migrations/default/`.
- Include trigger files in the default Atlas env source list immediately after table and index files, before RLS files.
- Keep trigger names deterministic: `<table>_set_timestamps`.
- Keep PostgreSQL timestamp behavior in one shared trigger function named `erun_set_timestamps()` unless a table has a real exception.
- Inserts may omit `created_at` and `updated_at`; triggers must populate both.
- Updates must preserve `created_at` and refresh `updated_at`.
- PostgreSQL triggers should be `BEFORE INSERT OR UPDATE` so rows are stored with timestamps in one write.
- Preserve caller-provided `created_at` on updates. `created_at` is creation identity, not mutable metadata.
- Caller-provided timestamps are allowed for imports and deterministic tests, but normal application inserts should omit both timestamp columns.
- Do not add application-side timestamp fallback as the primary behavior. Application code may pass explicit timestamps for tests or imports, but database triggers own the default lifecycle.
- When adding a mutable table with timestamp columns, add PostgreSQL trigger coverage.
- Validate timestamp trigger changes by inserting without timestamps and updating at least one row in PostgreSQL.

## Natural Keys And Mappings

- Prefer natural keys when the source value is globally stable, already externally defined, and is the exact lookup key used by the workflow.
- Do not add surrogate IDs to mapping tables when a natural key already exists and is stable.
- `tenant_issuers` does not use `issuer` as a global primary key: a shared (org-scoped) issuer maps to many tenants. Its identity is `UNIQUE (tenant_id, issuer)` (a tenant maps an issuer once), and resolution uses `UNIQUE NULLS NOT DISTINCT (issuer, org_field_value)`. The per-issuer org-scoping mode lives once on `issuers.org_field_key`, and `issuers.issuer` is the globally unique issuer registry key.
- Mapping tables may still include `tenant_id` or other foreign keys for traversal and integrity, but those foreign keys should not replace the natural lookup key.
- Add composite uniqueness when another table needs to prove that two columns belong together. `tenant_issuers` keeps `UNIQUE (tenant_id, issuer)` so `user_external_ids` can foreign-key `(tenant_id, issuer)`.
- Use UUIDv7 surrogate primary keys only for domain records that need their own externally visible identity, such as `tenants.tenant_id` or `users.user_id`.
- Do not use UUID primary keys for purely internal association rows unless there is a current API, audit, or lifecycle requirement to address that row directly.
- Register each OIDC issuer once in `issuers` (the globally unique issuer key). It may resolve to one tenant (single-tenant, NULL `org_field_value`) or many (org-scoped, one `tenant_issuers` row per org value). Multiple distinct issuers may still map to the same tenant.

## Multi-Tenant Database Plan

- Use a shared database with tenant-scoped rows by default, not one database per tenant.
- The `tenants` table is the root tenant registry. It stores tenant identity and tenant type without assuming a single identity provider issuer.
- `tenants.type` must be one of `OPERATIONS` or `COMPANY` and defaults to `COMPANY`.
- The `issuers` table holds each OIDC issuer once with its org-scoping mode: `org_field_key` NULL means a single-tenant issuer (the common case — BYO/external IdPs like cloud workload identity or a tenant's own OIDC); a set `org_field_key` names the token claim carrying the org for a shared multi-tenant issuer (e.g. a hosted Zitadel).
- The `tenant_issuers` table maps `(issuer, org_field_value) → tenant`. An issuer is **not** globally unique to one tenant: a single-tenant issuer maps to exactly one tenant (NULL `org_field_value`), and an org-scoped issuer maps to many tenants (one row per org value). `UNIQUE NULLS NOT DISTINCT (issuer, org_field_value)` keeps the resolution key unambiguous; `tenant_issuers.issuer` foreign-keys `issuers(issuer)`. Multiple distinct issuers may still map to the same tenant.
- The `users` table stores tenant-owned users with `user_id` as the UUIDv7 externally visible user identity.
- The `user_external_ids` table maps multiple external identity-provider subjects to one user.
- User external IDs must be unique per tenant with `PRIMARY KEY (tenant_id, issuer, external_id)`.
- `user_external_ids` must foreign-key `(tenant_id, user_id)` to `users` and `(tenant_id, issuer)` to `tenant_issuers` so external IDs cannot cross tenant or issuer boundaries.
- The `roles` table stores tenant-owned authorization roles with tenant-scoped role names.
- The `user_roles` table assigns multiple roles to users with `PRIMARY KEY (tenant_id, user_id, role_id)`.
- The `role_permissions` table stores role-owned permissions. A permission is either an exact API method/path pair or a regex API method/path pattern pair.
- Exact `role_permissions.api_method` values must be one of `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`, or `HEAD`.
- Regex permissions must use `api_method_pattern` and `api_path_pattern`, and should be anchored with `^` and `$` unless partial matching is explicitly intended.
- Keep `ReadAll` and `WriteAll` as predefined tenant roles. `ReadAll` grants all read-style methods across all API paths, and `WriteAll` grants all write-style methods across all API paths.
- Role permissions must be unique per tenant and role for exact values with `UNIQUE (tenant_id, role_id, api_method, api_path)` and for pattern values with `UNIQUE (tenant_id, role_id, api_method_pattern, api_path_pattern)`.
- A user's effective permissions are calculated as the distinct union of permissions for all roles assigned to that user within the same tenant.
- Authorization queries must join through `user_roles` and `role_permissions` scoped by `tenant_id`; do not calculate permissions from role names alone.
- If the database has no tenants, the first authenticated identity may bootstrap the system by creating an `OPERATIONS` tenant, mapping the token issuer to that tenant, creating the first user, and assigning both `ReadAll` and `WriteAll`.
- Do not bootstrap another operations tenant once any tenant row exists. After the first tenant exists, unknown issuers and subjects must remain unauthorized until explicitly configured.
- The `reviews` table stores tenant-owned review records with tenant-scoped names, non-empty `target_branch`, and non-empty `source_branch`.
- Review `name` is the squash merge message.
- `reviews.author_user_id` records who opened the review, defaulted from `erun_current_user_id()` and foreign-keyed to `users (tenant_id, user_id)`. It is set once, at creation, and never reassigned.
- The `review_reviewers` table assigns reviewers to a review with `PRIMARY KEY (tenant_id, review_id, user_id)`, tenant-scoped FKs to `reviews` and `users`. Many reviewers per review is the default shape; assigning a reviewer does not gate any status transition on its own.
- `reviews.status` must be one of `OPEN`, `CLOSED`, `FAILED`, `READY`, `MERGE`, or `MERGED`.
- Reviews track `last_failed_build_id`, `last_ready_build_id`, and `last_merged_build_id`. When a review status is `FAILED`, `READY`, `MERGE`, or `MERGED`, the matching last-build column must be populated.
- At most one review with status not in `MERGED`/`CLOSED` may exist per `(tenant_id, source_branch, target_branch)`, enforced by a partial unique index (`reviews_tenant_live_source_target_idx`) rather than application logic, so a second live proposal of the same change is refused at insert time. Branch history stays unbounded: a recycled branch name may have many `MERGED`/`CLOSED` reviews.
- The `review_merge_queue` table stores per-target-branch queue membership. Queue order is the ascending internal integer `review_merge_queue_id` surrogate key, not a mutable position column.
- Move reviews through the queue by deleting and inserting `review_merge_queue` rows. Requeue a review by deleting any old queue row, setting the review back to `READY`, and inserting a new row so it sorts at the end.
- `READY` reviews may appear in `review_merge_queue`. The active `MERGE` review must be removed from `review_merge_queue` when it is promoted, so the queue table contains only waiting reviews.
- `CLOSED` reviews must not appear in the merge queue.
- The `builds` table stores tenant-owned build records. `review_id` is nullable: a `GATE` build always belongs to the review it gates (enforced by `builds_gate_requires_review_check`), but a `RECORDED` build may instead belong only to an `environment_id` (nullable, `ON DELETE SET NULL`) — an ordinary `erun build` self-reporting with no review attached (erun#1954). A build naming neither a review nor an environment has no identity and is refused at the application layer. Every build stores whether it was successful, the commit ID it ran on, and its `kind`: `RECORDED` (a client-reported build or a release's own build, either of which mints a version and requires it non-empty) or `GATE` (the merge queue's own prospective-merge build, which publishes nothing and so has a NULL version). A failed `GATE` build must carry `failure_detail` in the gate's own words; a `RECORDED` failure's reason lives wherever the reporting caller's own CI recorded it, not here.
- A successful build moves an `OPEN` or `FAILED` review into the target branch merge queue as `READY`; if there is no active `MERGE` review for that target branch, the next queued review may be promoted to `MERGE`.
- A failed build for a queued or merging review moves it to `FAILED` and removes it from the merge queue.
- If a `MERGE` review misses its merge window without failing, move it back to `READY` at the end of the same target branch queue.
- The `gate_runs` table stores the first-class record of one attempt to gate a prospective merge — independent of whether an erun review exists for the change. Reviews are one producer (a review-driven merge reports a gate run alongside its GATE build); a repository whose changes arrive as GitHub pull requests, with no erun review at all, is the other. `status` is one of `RUNNING`, `PASSED`, `FAILED`, or `INCONCLUSIVE` — a wrapper timing out or a run interrupted by an environment fault must report `INCONCLUSIVE`, never `FAILED`, since `FAILED` asserts a real verdict was reached. A `FAILED` row must carry `failing_step` (which gate step produced the red verdict); `log_ref` is an optional pointer to where to read it. `merge_commit` is NULL only when the run failed before that commit existed at all (a squash conflict). `review_id` is nullable and, when set, foreign-keys `(tenant_id, review_id)` to `reviews`.
- Audit events are stored in PostgreSQL.
- Every tenant-owned PostgreSQL OLTP table must include `tenant_id`, enforce tenant-scoped uniqueness with composite unique indexes, and have PostgreSQL RLS.
- API request handling must resolve tenant from the bearer token issuer before running tenant-owned queries.
- Persistence code must require authenticated tenant identity in transaction context, then omit `tenant_id` from normal application inserts so the database default uses `erun_current_tenant_id()`.
- Use UUIDv7 values for externally visible IDs. Keep database primary keys and API IDs aligned unless a later migration introduces private surrogate keys for a measured reason.
- Store timestamps in UTC. Database triggers own default timestamp population.
- Add foreign keys from tenant-owned tables to `tenants(tenant_id)`.

## Initial Schema Direction

- `tenants` stores tenant ID, name, type, and timestamps.
- `issuers` stores each OIDC issuer once with its org-scoping mode (`org_field_key`). `tenant_issuers` maps `(issuer, org_field_value)` to tenants — single-tenant (NULL org) or org-scoped (one row per org value).
- `users` stores tenant-owned user records with a tenant-scoped `username`.
- `user_external_ids` stores one or more external identity-provider subject IDs for each user, unique per tenant, issuer, and external ID.
- `roles` stores tenant-owned role records with tenant-scoped names.
- `user_roles` stores user-to-role assignments.
- `role_permissions` stores permissions owned by roles as exact API method/path pairs or regex method/path pattern pairs.
- `reviews` stores tenant-owned review records with `name`, `target_branch`, `source_branch`, status, and last build links for failed, ready, and merged states.
- `review_merge_queue` stores waiting review queue entries. Each queued review appears at most once per tenant, and queue order is by the internal integer `review_merge_queue.review_merge_queue_id`.
- `review_reviewers` stores reviewer assignments for reviews.
- `builds` stores tenant-owned build records, linked to a review (a `GATE` build always) or, for an unattached `RECORDED` build, an environment instead, including `successful`, `commit_id`, `kind` (`RECORDED` or `GATE`), `version` (required for `RECORDED`, NULL for `GATE`), and `failure_detail` (required for a failed `GATE` build).
- `comments` stores tenant-owned review comments. Root comments own one review/commit/line discussion, and child comments must reference that root.
- `gate_runs` stores the first-class record of one gate attempt: `source_branch`, `target_branch`, `source_commit`, `merge_commit` (nullable), an optional `review_id`, `status` (`RUNNING`/`PASSED`/`FAILED`/`INCONCLUSIVE`), and `failing_step`/`log_ref` for a red verdict.
- `audit_events` stores append-only API, MCP, and CLI activity with tenant, ERun user, external identity, source-specific action fields, and event time.
- Future environment, deployment, activity, and runtime state tables should hang from `tenants(tenant_id)` and use tenant-scoped indexes.

## Audit Events

- Audit events track authenticated API, MCP, and CLI activity.
- Store audit events in PostgreSQL for normal deployments.
- Required common audit fields are `tenant_id`, `erun_user_id`, `external_user_id`, `external_issuer_id`, `type`, and `created_at`.
- `type` must be one of `API`, `MCP`, or `CLI`.
- `external_issuer_id` stores the OIDC `iss` value that mapped to the tenant.
- `external_org_id` stores the org/resource-owner claim value (for org-scoped issuers) that, together with `iss`, resolved the tenant; NULL for single-tenant issuers.
- `external_user_id` stores the external subject/user ID presented by the identity provider.
- `erun_user_id` stores the internal ERun user ID resolved from the external identity.
- API audit events must set `api_method` and `api_path`. `api_method` must be one of `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`, or `HEAD`.
- `api_path` must use the same canonical route template stored in `role_permissions.api_path`, such as `/v1/reviews/{review_id}` rather than a concrete request URL with IDs or query strings.
- CLI audit events must set `cli_command` and may set `cli_parameters`.
- MCP audit events must set `mcp_tool` and may set `mcp_tool_parameters`.
- API audit events may set `api_parameters` when the action itself requires recording a caller-supplied justification, such as a merge-queue gate override's reason; ordinary API audit events leave it null.
- Store CLI and MCP parameters as serialized text, preferably compact JSON when the caller has structured input.
- Audit events are append-only. Do not update or delete audit rows as part of normal application behavior.
- PostgreSQL audit events should be indexed for tenant/time/user/API access patterns.
- `audit_events` records authenticated, single-tenant activity only — a system-initiated action with no caller identity behind it (e.g. the scheduled retention sweep) does not fit here and belongs in its own table instead. See § "Retention Mechanism"'s `retention_runs` bullets for the reasoning and the self-referential boundary this avoids.

## Review Comments

- Comments belong to reviews through `(tenant_id, review_id)`.
- Comments must include `commit_id`, non-empty `file_path`, and positive `line`. A comment's address is the full `(commit_id, file_path, line)` tuple, not `(commit_id, line)` alone — two files can share a line number in the same commit.
- Comments must include non-empty, non-whitespace-only `body`, bounded to 8 KiB (`octet_length(body) <= 8192`).
- `comments.status` must be one of `OPEN` or `CLOSED`.
- Every comment, root or child, must have `creator_user_id`. Every reply records its own author; the root's creator does not stand in for a reply's author.
- Root comments have `parent_comment_id IS NULL`.
- Comments must not reference themselves as parents.
- Comment thread identity fields are immutable after insert: `comment_id`, `tenant_id`, `review_id`, `creator_user_id`, `parent_comment_id`, `commit_id`, `file_path`, `line`, and `body` (there is no edit endpoint in this increment).
- There can be only one root comment per tenant, review, commit, file_path, and line.
- Child comments must reference the root comment for the same tenant, review, commit, file_path, and line; a reply whose file disagrees with its parent's is refused.
- Only a thread's root comment may have its `status` updated; a reply's own status is not separately settable.
- PostgreSQL must enforce that only the root comment's own creator can update that root's status by comparing `creator_user_id` to transaction setting `erun.user_id`. There is no per-review "any write-access actor" exception at the database layer — the database cannot see role-based write permissions, so that documented allowance was narrowed to "the root author" to match what the trigger can actually enforce.
- Do not calculate comment-thread validity in API code as the primary guard. Keep the review/commit/file_path/line and parent-child invariants in database triggers.

## Retention For High-Frequency Tables (#1956, design recorded — not yet implemented)

- **The rate is measured, not guessed, from this repository's own dogfooding activity** (the closest real signal available; production per-tenant telemetry doesn't exist yet). `sophium/erun` merged 243 PRs over 7 days (`gh pr list --state merged`, 2026-08-27 through 2026-09-02: 36/27/56/42/32/50, ~35/day average, 56/day peak) and cut 43 releases over the same window (~6/day). Every merged PR's gate promotion is at least one `GATE`-kind `builds` row, and every release is at least one `RECORDED`-kind row, so **today's `builds` table already accrues roughly 40-60 rows/day on this one tenant** even before #1954 records anything. #1954's own motivating example — an agent running `erun build` twenty times in an afternoon while iterating, none of it recorded today — describes a per-environment multiplier this repository's activity corroborates: reaching 35-56 merges/day implies several concurrently active agent lanes, each iterating well past its single final gate attempt before it goes green. A conservative extrapolation (5-10 concurrent lanes × 10-30 ordinary builds each while iterating) puts the *added* volume #1954 introduces at roughly 50-300 rows/day on this one already-very-active tenant — a 2-6x multiplier over today's baseline — and that multiplier applies per tenant, so the platform-wide total is unbounded by construction (it compounds forever with zero pruning, not because any one tenant is unreasonable). The exact constants below are conservative starting points, not a fitted answer: the ordinary-build rate literally cannot be measured until #1954 ships the write path, so tune them from real counts (a simple per-day count read off `builds` is enough) once it has run for a week or two.
- **A build record's value decays fast, and what's left after it decays is small enough to keep forever instead of rolling up.** A `GATE` build answers "why did this gate attempt fail" for as long as the review it gates is still being worked — days, not months — and once a review reaches `MERGED`/`CLOSED` its superseded gate attempts (everything except whichever one is pinned by `last_failed_build_id`/`last_ready_build_id`/`last_merged_build_id`, see below) have no further use. A `RECORDED` build (ordinary or release) answers "why did my build fail an hour ago," "is a build running right now," "did this environment start failing after a version bump" — useful for a sprint-length window, essentially worthless past a month for the same reason `RuntimeUsageHistory`'s raw sample window is bounded to ~2 hours while its aggregates are kept forever (`erun-common/runtime_usage_history.go`): unlike that precedent, no product surface today asks for a rolled-up build trend (success-rate-over-90-days, duration percentiles), and `Build` doesn't even carry a duration field, so **there is nothing to roll up yet** — recommend fully disposable rows past the retention window, and add a rollup only if a future feature actually needs one (don't build it speculatively now).
- **The referential graph is the hard constraint, and it's narrower than "anything might reference a build."** Two back-references exist, both `RESTRICT` (no `ON DELETE` clause) today: `reviews.last_failed_build_id`/`last_ready_build_id`/`last_merged_build_id` (`schema/fks/review_builds.sql`) and `releases.build_id` (`schema/tables/releases.sql`). Nothing references `gate_runs` at all — it has no inbound FK, so it is fully disposable on its own age/count bound with no guard needed. Naively deleting by age alone will hit a live FK violation the moment it reaches a review's pinned build (worse, `reviews_status_build_link_check` requires a `MERGED` review to keep `last_merged_build_id` populated forever, so that pinned row can never be nulled out either) or a release's `build_id`. The fix is a `NOT EXISTS` guard against both back-references in the delete predicate, not a schema change: the pinned set is tiny (at most 3 rows per review, 1 per release) and reviews/releases are themselves queue-paced, so exempting it from both bounds costs nothing and is what keeps this from ever taking an FK violation. This guard works unchanged whether `review_id` is required (today) or nullable (#1954): an unattached build simply can't match either back-reference, so it ages out purely on time/count.
- **Recommended policy: age + count, either bound prunes, exemption is the `NOT EXISTS` guard above** — the same two-bound shape as `EnvironmentJobRetention`/`EnvironmentJobHistoryCap` (`erun-common/job.go`, 24h + 50), scaled up because a build's useful window is weeks not hours. Starting constants (revisit once #1954 supplies real counts): **30-day age bound** on `builds` and `gate_runs` alike (comfortably covers a sprint-length "did this start failing after a version bump" investigation, since releases alone recur ~6/day on an active tenant); **a per-tenant count cap** (proposed 2,000 most-recent rows) as the runaway-loop backstop, sized so a stuck agent retry-looping `erun build` for hours gets capped well before the age bound would otherwise catch it. Once #1954 lands `builds.environment_id`, move the count cap to per-`(tenant, environment)` — matching `EnvironmentJobHistoryCap`'s per-environment scope — so one loud environment can't crowd out another's history inside the same tenant's cap; until then, per-tenant is the only key the schema supports.
- **Scope this pass to `builds` and `gate_runs` only; `usage_events`/`audit_events` are a separate, harder decision, split out as #1959.** Both are append-only at the role level (`schema/roles.sql` grants only `SELECT, INSERT, REFERENCES`, no `DELETE`, no RLS `FOR DELETE` policy) — pruning either needs a new grant/policy carved as an explicit exception to this file's "audit events are append-only" rule, plus a retention-window decision that may be compliance-driven rather than debugging-usefulness-driven. `builds` and `gate_runs` need no such carve-out: `schema/roles.sql` already grants `erun_tenant`/`erun_operations` `DELETE` on both, and their RLS policies (`builds_tenant_isolation`/`builds_operations_access` and the `gate_runs` equivalents) are already `FOR ALL`, so a retention sweep is an ordinary tenant-scoped `DELETE`, not a schema change.
- **Mechanism: a scheduled CronJob, not a lazy read-path prune.** `EnvironmentJobRetention`'s lazy-on-read model only bounds the environments/tenants someone actually reads from — a tenant whose agents write to `builds` continuously without anyone opening the Builds tab would keep growing unboundedly, which is exactly the failure mode #1954 introduces (growth decoupled from human attention). A scheduled sweep bounds every tenant regardless of read pattern. Shape it like the existing `migrate-repair-cronjob.yaml` precedent (`erun-devops/k8s/erun-backend-db/templates/`) but on a much slower cadence — daily is enough, since pruning has no urgency the way schema-drift repair does. No new grant is needed for the connection: `erun_operations` already holds `DELETE` on `builds`/`releases`/`gate_runs` with `USING (true)` policies, so one connection with `SET ROLE erun_operations` can sweep every tenant in one pass — but its `DELETE` predicate must still filter by `tenant_id`/`created_at`/the count-cap window explicitly, the same "explicit filters, don't lean on implicit RLS scoping" discipline `erun-operations` reads already follow, since `erun_operations`'s own RLS doesn't filter by tenant at all.
- **Not implemented by this pass.** This is the design record; the actual migration (delete predicate, count-cap column keying once #1954 lands `environment_id`) is follow-up work, and needs #1954's schema (nullable `review_id`, `environment_id`) to land first for the per-environment cap to have a column to key on. The CronJob mechanism this design called for now exists (§ "Retention Mechanism" under "Retention For The #1968 Six-Table Sweep", built and proven against #1970) — porting this policy in is adding `erun-backend-db/retention/builds_gate_runs.sql`, not building a new mechanism.

## Retention For Append-Only Audit/Usage Tables (#1959, design recorded — a compliance decision blocks implementation)

- **The retention obligation is not established in this repository, and that gap — not performance — is what blocks implementation.** A repo-wide search turns up no SOC 2/GDPR/HIPAA/PCI commitment, no signed customer retention clause, nothing beyond marketing copy in `erun-docs/docs/intro.md` ("audit-ready, compliance is how the platform works, not a bolt-on"). `erun-docs/docs/agent-reference/audit-log.md` already promises "the event format, retention windows, and the catalogue of captured security events are the Agent's spec" without ever stating a window — an existing unfilled promise, not one this design invents. Unlike `builds` (#1956), where the floor was purely operational usefulness and an engineering judgment call was enough, `audit_events`' floor — if one exists — is set by a business/legal decision this codebase cannot answer on its own. **Decision the operator must make:** does erun have, or intend to sell into, a compliance/contractual commitment on audit-log retention, and if so what is the minimum window, and is it per-tenant (a customer's own contract could set a longer floor than the platform default)? Until that's answered, treat the floor as indefinite — no deletion — rather than guess low and be wrong in a way nobody can undo.
- **`audit_events`/`usage_events` are append-only by design, not append-only-so-far — pruning either is a deliberate, narrow exception to a documented invariant, not "run the delete the grant already permits."** `schema/roles.sql` grants only `SELECT, INSERT, REFERENCES` on both to every role; no role holds `DELETE`, and neither table has a `FOR DELETE` RLS policy. This file's own "Audit Events" section already states the rule in prose: "Audit events are append-only. Do not update or delete audit rows as part of normal application behavior." #1956's tables (`builds`, `gate_runs`) already had `DELETE` granted with `FOR ALL` policies — pruning those needed no schema change. Pruning these needs the opposite: a new, narrowly-scoped grant that does not flow through any code path `erun_tenant`/`erun_operations` already exercise.
- **Referentially these tables are the easiest in the schema to prune — nothing points at them.** Neither `audit_events` nor `usage_events` has any inbound foreign key (confirmed against every file in `schema/fks/`); `usage_events`' own outbound FK to `environments` is `ON DELETE SET NULL`, so a deleted environment doesn't even touch its usage rows. The constraint here isn't referential, it's evidentiary. `audit_events` is the platform's only record that a given authenticated API call happened at all — `erun-docs/docs/collaboration/operator-in-the-loop.md`'s "The audit trail" section promises "nothing an Agent does via the API is anonymous; nothing is unrecoverable," a promise a retention window quietly breaks past its edge. `usage_events` is the only record that a given environment lifecycle transition generated a metered charge — exactly what a billing dispute would need to re-derive. Neither has an operational "past this point nobody looks at it" horizon the way a build's does: a security investigation or a billing dispute can legitimately reach back further than any debugging session would, and neither can know in advance how far back it will need to reach.
- **Growth rate is asymmetric between the two tables, and unlike #1956's `builds` estimate, neither can be measured precisely today — say what's known and what isn't.**
  - `audit_events` writes on **every successfully authorized hosted-API request**, not just build/gate/merge events: `erun-backend-api/auth.go`'s `logAuditEvent` runs from request middleware after token verification, tenant resolution, user resolution, and endpoint authorization all succeed, regardless of HTTP method (`erun-backend-api/AGENTS.md`'s "Audit Logging" section documents this as the contract). That makes it strictly higher-frequency than `builds`/`gate_runs`: every `POST /v1/builds` or `POST /v1/gate-runs` #1956 counted is *also* one `audit_events` row, plus every list/get/whoami/review/comment/environment call around it that never touches `builds` at all. Neither `erun-console` nor `erun-ui/frontend` polls the hosted API on an interval today (no `refetchInterval`/`setInterval` hits a hosted-API route), so current volume is bounded by human/agent-initiated calls, not background polling. CLI audit logging is still unimplemented. **MCP `type` classification landed (erun#763), and it does not move this estimate: it reclassifies rows this API already wrote as type `API`, it does not add new ones.** The feared multiplier below is about MCP tool calls starting to write rows *at all* — the vast majority never do, by architecture, because most MCP tools (`exec_raw`, `list`, `idle`, `exec_job_status`/`exec_job_output` polling, and the rest of the purely in-pod surface) never call this API and so were never counted here in the first place. Only the narrow subset that already called through to this API — `review_*`, `platform_*`, `gate_*`/`exec_gate-run_*`/`exec_reconcile-bypass`, `expose`/`unexpose`'s platform DNS path, and `build`'s self-report (`erun-common/build_report.go`) — now says `type: MCP` instead of `type: API` for the identical call it already made and already wrote a row for (see `erun-backend-api/AGENTS.md`'s "Audit Logging" section). If CLI classification lands the same way later, the same reasoning applies: it is a relabeling of the `erun-cli`-driven share of this same already-counted volume, not a new source of rows. The multiplier this bullet actually still warns about — an *unaudited* surface starting to write rows, dwarfing today's volume by orders of magnitude — remains open and unaffected by this fix: it would require literally auditing per-MCP-tool-call activity (`erun build`, `erun list`, `erun idle`, job-status polling) the way this bullet originally worried about, which nothing does today and which is a distinct, much larger design decision (a new write path, not a classification fix) that should be weighed against this section's own retention questions before anyone builds it. Reusing #1956's own measured window (243 merged PRs / 43 releases, 2026-08-27 through 2026-09-02 on `sophium/erun`) as a floor, not a fit: every one of those PRs' gate `builds`/`gate_runs` rows is also an `audit_events` row, plus the review/comment/list/whoami traffic around each, so `audit_events` is accruing at least the ~40-60 rows/day #1956 measured for `builds` alone, plausibly several times that once non-build API traffic is counted. A real number needs `SELECT count(*) FROM audit_events GROUP BY date_trunc('day', created_at)` run for a couple of weeks in production — the same "tune from real counts" caveat #1956 gave for `builds`.
  - `usage_events` is the opposite case: it writes only on environment lifecycle transitions — `environment_provisioned` once per environment (`internal/service/environments.go`), `environment_stopped`/`environment_deleted` from `internal/provision/lifecycle.go`'s `Stop`/`Delete` — and no "resumed" event exists at all (the `event_type` check constraint allows only those three values), so an idle-stop/resume cycle adds at most one row per stop, none per resume. Its volume is bounded by environment churn and idle-stop cadence, not request volume — almost certainly the lowest-volume of the four tables #1956's originating issue named (`builds`, `gate_runs`, `usage_events`, `audit_events`), which weakens any storage-pressure argument for pruning it quickly even though its append-only shape matches `audit_events` exactly.
- **Recommended privilege model: a dedicated, non-application role with its own login — not a grant layered onto the roles application code already uses.** Do not add `DELETE` on these two tables to `erun_tenant`/`erun_operations`: `erun-backend-api` already holds `SET ROLE erun_operations` on every request, so any bug or compromised code path in that process could delete audit rows the moment the grant exists. Instead: add a new `NOLOGIN` role (e.g. `erun_retention`, following the `erun_tenant`/`erun_operations` pattern in `schema/roles.sql`) granted `DELETE` — and whatever read access it needs — on `audit_events`/`usage_events` only, with its own `FOR DELETE` RLS policy scoped by `created_at` age (cross-tenant `USING (true)`, mirroring `erun_operations`'s reach on other tables, since a retention sweep runs once for the whole platform). Give the retention job **its own PostgreSQL login**, distinct from the API's login role, and never grant that login `erun_retention` — the exception this issue asks for lives in *which connection* can delete, not in a permission any request handler could reach by accident. Once implemented, reword this file's "Audit Events" append-only bullet to name the exception explicitly: "...as part of normal application behavior. The only permitted deletion path is a scheduled, separately-privileged retention job running under a dedicated role with its own database login — see this section. No other caller, including operations-tenant callers, may delete or update an audit row." The same wording applies to `usage_events` if it later gets its own prose section.
- **Recommended shape: archival before deletion, not #1956's fully-disposable answer.** #1956 recommended fully disposable rows for `builds`/`gate_runs` because nothing reads a superseded build past a sprint and there is no rollup worth preserving. That reasoning doesn't transfer here: an audit trail's entire value is "prove this happened," which argues for *moving* an aged-out row somewhere colder and still retrievable, not discarding it. Once a window is set, prefer an export-then-delete shape — write aging-out rows to object storage (destination and format unspecified here; that is new infrastructure this repo does not have today and needs its own design pass) before the retention job deletes them from the hot OLTP table. Until that archival path exists, prefer **not pruning `audit_events` at all** over pruning without an archive: a wrong guess at a compliance-relevant retention window is not reversible once the row and its only copy are both gone.
- **Mechanism, once a window and an archival answer both exist: the retention CronJob that now exists** (§ "Retention Mechanism" under "Retention For The #1968 Six-Table Sweep", daily cadence — pruning an audit trail has even less urgency than pruning `builds`), authenticating as the dedicated `erun_retention` login above, never as the API's login or `erun_operations`. That mechanism's runner iterates every `.sql` file under `erun-backend-db/retention/` against one connection; a policy needing this table's own dedicated login opens its own connection inside its own file rather than reusing the shared one, so this exception stays exactly that — an exception — instead of widening what the shared connection can reach.
- **Not implemented by this pass. Two decisions block it, both the operator's to make, not engineering's:**
  - **`audit_events`:** is there a compliance/contractual retention floor, what is it, does it need to be per-tenant-configurable, and is archival-before-delete a hard requirement or negotiable.
  - **`usage_events`:** what billing/reporting window applies (how far back a usage dispute must be provable), and whether that is a platform-wide constant or per-tenant.
  Until both are answered, the correct engineering default is that `audit_events` and `usage_events` keep growing unbounded, exactly as they do today: a low-volume table with no urgency (`usage_events`) and a higher-volume table whose entire value is its permanence (`audit_events`) are both better left growing than pruned on a guessed window.

## Retention For The #1968 Six-Table Sweep

- **#1968 split six append-only/high-growth tables (`builds`, `gate_runs`, `usage_events`, `audit_events`, `comments`, `releases`, `reviews`, `ai_sessions`, `invites`/`invite_requests` — the sweep grew beyond its original six as related tables surfaced) into independently designable groups so no single pass had to resolve every table's obligation-vs-performance question at once.** `builds`/`gate_runs` (#1956) and `audit_events`/`usage_events` (#1959) remain design-only, blocked as their own sections above describe. The remaining four groups are all **implemented**: `comments`/`releases` (#1970), `reviews` (#1971, scope narrowed — see below), `ai_sessions` (#1972), and `invites`/`invite_requests` (#1973). Each subsection below follows the same shape: growth-rate evidence, the referential graph that constrains a delete predicate, any table-specific guard beyond a plain age/count bound, the recommended policy, the mechanism, and (where relevant) what was narrowed or found while porting the design onto the shared mechanism.
- **A shared mechanism now exists (see § "Retention Mechanism" below), built once and proven against #1970 rather than hand-rolled per table.** Before this, `erun-backend-db` had zero retention machinery of any kind: #1956 and #1959 (both older than this sweep) were themselves still design-only with no CronJob, no grant, no code — the `EnvironmentJobRetention`/`EnvironmentJobHistoryCap` precedent both designs cite for their two-bound shape is an in-memory bound on a different resource (`erun-common/job.go`'s job-history map), not a database mechanism either design could plug into. Each of the four groups below is additive to the one mechanism: a new `.sql` file under `erun-backend-db/retention/`, picked up by the existing runner and the existing CronJob with no code change, once its own blocker (a product decision, a prerequisite fix, or simply landing its design on `main`) clears.

### Retention Mechanism

- **One runner, one CronJob, one file per policy.** `erun-backend-db/retention/*.sql` holds one file per retention policy: `comments_releases.sql` (#1970), `reviews.sql` (#1971), `ai_sessions.sql` (#1972), and `invites_invite_requests.sql` (#1973) as of this pass. `erun-devops/docker/erun-backend-db/retention.sh` (baked into the `erun-backend-db` image as `erun-backend-db-retention`, the same image `erun-backend-db-migrate` already ships from) runs every file in the directory, in name order, inside a single `psql` session against `$ERUN_DATABASE_URL` (psql runs every `-c`/`-f` it is given, in order, on one connection). Adding a policy — porting `builds`/`gate_runs` (#1956) is the one group left — is adding a new `.sql` file; neither the runner nor the CronJob changes. `make test-retention` (root Makefile) runs every `erun-devops/docker/erun-backend-db/retention*_test.sh` script in turn, one real-postgres container per policy group, so a new policy's own test is picked up with no Makefile edit.
- **`erun-devops/k8s/erun-backend-db/templates/retention-cronjob.yaml` runs the sweep once a day (`0 3 * * *`), independent of any Helm operation, but is off by default.** `retention.enabled` (default `false`) gates the whole CronJob document — a fresh install or upgrade of this chart never starts deleting rows on its own, and turning the sweep on is an explicit, no-code-change Helm value flip, not a behavior a deploy silently inherits. Once enabled it runs the same "on its own schedule, not tied to a deploy" shape as `migrate-repair-cronjob.yaml`, but on a slow cadence: pruning has none of schema-drift-repair's urgency. `concurrencyPolicy: Forbid` keeps the CronJob's own scheduled runs from overlapping each other; the advisory lock below is what makes that true regardless of how a run started, not only via the schedule. It overrides the image's default `command` (which is the migrate entrypoint) to run the retention entrypoint instead, and honors the same `imageOverrides.erun-backend-db` every other mechanism in this chart does. Locked by `erun-devops/k8s/erun-backend-db-chart_test.sh`.
- **Every policy file reports before it deletes, and defaults to reporting only.** Each `.sql` file runs an unconditional `SELECT count(*)` per table naming how many rows are currently eligible under that table's bound, then — guarded by a `dry_run` variable the caller must supply (`psql -v dry_run=true|false`) — runs the matching `DELETE` inside its own `BEGIN`/`COMMIT`, using the identical predicate the count just reported. `retention.dryRun` (chart value, default `true`) sets `ERUN_RETENTION_DRY_RUN` on the CronJob container; `retention.sh` itself also defaults to `dry_run=true` when that variable is unset, so an operator turning retention on sees a report before anything is deleted, and must take a second, explicit step (`retention.dryRun=false`) to let it delete. `retention.enabled`/`retention.dryRun` both use the `hasKey`-guarded resolution `mcpEnabled` uses (`erun-devops/k8s/erun-devops/templates/service.yaml`) rather than a plain sprig `default`, because `default` cannot tell "unset" from "explicitly `false`" — a plain `default true $retention.dryRun` would silently coerce `retention.dryRun=false` back to `true`.
- **A session-scoped advisory lock guards the whole sweep against a second run racing this one's deletes.** `retention.sh` acquires `pg_try_advisory_lock(hashtext('erun_retention'))` before the first policy file and releases it with `pg_advisory_unlock` after the last, all inside the one psql session described above — so the lock covers every policy file in one run, not just one file. A run that finds the lock already held raises immediately (`retention sweep already running (advisory lock held)`) rather than proceeding. This is deliberately independent of `concurrencyPolicy: Forbid`: the lock is what stops two overlapping deletes regardless of whether both runs came from the CronJob's own schedule, a manual invocation, or any other trigger, and a session-scoped lock releases automatically if the connection drops, so a crashed run never strands the lock for the next attempt.
- **Every run — dry or real — records its outcome in `retention_runs`, so a scheduled deletion is never silent.** `retention_runs` (no tenant scoping — it is a platform-wide operational log, not tenant data, the same shape as `platform_rate_limits`) holds one row per `(policy_name, table_name)` per run: `dry_run`, `eligible_count`, and `deleted_count` (always `0` for a dry run, enforced by a `CHECK`). Each policy file inserts these rows itself, using the identical predicate its own report and delete use, so the count in the table is never a second, independently-computed estimate. Only `erun_operations` can read or write it (`schema/roles.sql`) — an operator queries it directly today; a future API/console surface is not part of this pass. This is the durable alternative to relying on the CronJob's own transient pod logs, which are capped (`successfulJobsHistoryLimit`/`failedJobsHistoryLimit`) and only reachable with cluster access.
- **`retention_runs`, not `audit_events`, because a scheduled sweep has no identity to attribute the record to.** `audit_events` was the obvious first candidate — it already exists to record what the system did — but every row requires `erun_user_id NOT NULL` (foreign-keyed to `users (tenant_id, user_id)`), `external_user_id NOT NULL`, and `external_issuer_id NOT NULL`: the table's whole shape assumes an authenticated caller who came in through an OIDC-issued token, one tenant at a time. `logAuditEvent` (`erun-backend-api/auth.go`) writes from request middleware *after* token verification and tenant resolution both succeed — there is no request, no token, and no single tenant behind a CronJob pod running `psql` with `SET ROLE erun_operations` across every tenant in one pass. Recording a sweep there would mean inventing a sentinel user/issuer/tenant with no real identity behind it, which corrupts the one thing `audit_events` promises: every row traces to a real authenticated actor. `retention_runs` sidesteps the mismatch instead of forcing it — no `erun_user_id`, no `tenant_id`, platform-wide by design, matching what a system-initiated, cross-tenant action actually is.
- **The boundary this avoids: a retention record must not be able to delete itself before anyone reads it.** `audit_events` is itself slated for its own retention policy (#1959, design recorded, not yet implemented) — had the sweep written its own record into `audit_events`, that future policy would eventually prune the very rows proving earlier sweeps ran, and a deletion's only evidence could go missing before an operator ever queried it. Writing to `retention_runs` instead removes the cycle by construction: `retention_runs` is not one of the tables any policy file under `erun-backend-db/retention/` sweeps today, so nothing deletes a sweep's own record. This is a property of what the mechanism does today, not a permanent exemption — if `retention_runs` ever needs its own bound (its own volume is tiny: one row per `(policy_name, table_name)` per run, so this is not urgent), that policy must guarantee a run's own record outlives the run that would prune it, e.g. by recording before deleting within the same statement ordering `comments_releases.sql` already uses for every other table, and by never letting one run's bound reach back far enough to remove the record of the immediately preceding run.
- **No new grant for `comments`/`releases`.** The connection runs `SET ROLE erun_operations;` and deletes cross-tenant in one pass, the same privilege shape #1956/#1959 already described for this connection — see each policy's own grant note. A future policy needing the `audit_events`/`usage_events`-style dedicated-login carve-out (#1959) adds that connection alongside this one rather than replacing it; the runner iterates files, not connections, so a policy that genuinely needs a different login is free to open one itself.
- **Blast radius if a bound is misconfigured:** a bound written too loose (a short age, a low count) deletes rows a real investigation would have wanted — for `comments`/`releases` specifically, an unrecoverable loss of review discussion or release provenance, not a crash or an outage, since neither table's rows are needed for correctness once written (nothing reads them to make a live decision). A bound written backwards (e.g. `rn < N` instead of `rn > N`) would delete the *newest* rows and keep the oldest — the test suite's exact-count assertions on which specific rows survive (not just how many) are what catch that class of mistake, not just an off-by-one in the count. `retention.enabled=false` (default) and `retention.dryRun=true` (default once enabled) both exist so a misconfigured bound is caught by reading a report, not by discovering the loss after the fact.

### Review Comments And Releases (#1970, implemented)

- **Grouped together because they share an answer that `reviews` (#1971) — the table both hang off — does not.** `reviews` has six inbound `RESTRICT` foreign keys and a documented "Branch history stays unbounded" property that may be a deliberate product promise, the same obligation-vs-performance question #1959 had to resolve for audit trails. `comments` and `releases` carry neither complication: each is a leaf with nothing referencing it back, and neither has any stated permanence guarantee anywhere in this repo. That is what makes them answerable now, in the same pass, while `reviews` needs its own harder design.
- **Growth rate is driven by review-lifecycle activity, already measured for one of the two by #1956.** `releases` reuses #1956's own count directly: 43 releases over the 7-day window `sophium/erun` was measured (2026-08-27 through 2026-09-02), ~6/day/tenant on this one dogfooding tenant, `UNIQUE (tenant_id, commit_id)` capping it at one row per merged commit. `comments` has no equivalent direct measurement — erun's own review-comment system is separate from GitHub's PR review comments, so GitHub's counts don't transfer — but its order of magnitude is bounded by review count × comments-per-review, and review count is itself at least the ~35-56 merges/day #1956 measured (reviews that never merge add more). Both grow continuously in every active tenant today, not conditionally on a future feature the way #1956's `builds` estimate depended on #1954.
- **Referentially both are leaves, and pruning either is independent of whatever `reviews` (#1971) ends up doing.** `comments.review_id` and `releases.review_id` both foreign-key `reviews` with the default `RESTRICT`/no-`ON DELETE` behavior, but that constraint only stops a `reviews` row from being deleted while dependents remain — it does not stop a `comments` or `releases` row from being deleted while its parent review still exists. Nothing references `comments` except itself (`parent_comment_id`, self-referencing) and nothing references `releases` at all. This means a comment or release can age out on its own schedule even if `reviews` itself is left unbounded indefinitely (#1971's outcome, whatever it turns out to be), same way #1956 exempted only the tiny pinned-build set rather than waiting on a `reviews`-side decision.
- **`comments` needs one guard beyond a plain age/count bound: don't delete a live thread, and don't orphan a still-live reply.** A root comment (`parent_comment_id IS NULL`) with `status = 'OPEN'` represents an unresolved discussion someone may still act on — pruning it by age alone would silently delete an open conversation nobody closed, not a superseded record the way an old `GATE` build is. The bound should therefore be age/count **on `CLOSED` root threads only**, exempting `OPEN` roots the same way #1956 exempted a review's pinned build rather than deleting through it. Within a `CLOSED` thread, the delete predicate must also guard against orphaning: a root can be older than the age bound while a reply posted just before the thread closed is not, so the sweep should delete a root only together with its full reply set, keyed off the root's own age/count position (mirroring `comments_tenant_review_comment_key`'s `(tenant_id, review_id, comment_id)` grouping) rather than filtering each row independently.
- **`releases` needs one thing #1956's tables didn't: a check that deleting the idempotency row doesn't reopen it.** `releases_tenant_commit_key` (`UNIQUE (tenant_id, commit_id)`) is what stops the same merge commit from being released twice; deleting an aged-out `released` row removes that guard for that commit inside this database, even though the real-world artifact (the pushed git tag, the published image) still exists and would still conflict at the point a duplicate release actually tried to publish. This is a weaker safety net after pruning, not a correctness bug — recommend keeping the age bound long enough that this is very unlikely to matter in practice (see below), and note it explicitly rather than silently accept a narrower guard.
- **Recommended policy: age + count, same two-bound shape as #1956, tuned to each table's own decay curve.** For `releases`: a `RECORDED` release answers "what did this commit release" for as long as anyone might ask that question about a specific version — longer than a build's sprint-length window, since a release is a durable identity (a version string, a git tag) people reference indefinitely, but the *row* is redundant with the git tag itself once it's old enough that nobody is actively debugging around it. Recommend a longer age bound than `builds`' 30 days — **180 days** as a starting point — plus a per-tenant count cap (proposed **1,000** most-recent rows, since 6/day × 180 days ≈ 1,080 already approaches that, so the count cap is a real backstop here, not just a runaway-loop guard the way it was for `builds`). For `comments`: once a thread is `CLOSED`, its debugging/discussion value decays on the same sprint-length timescale #1956 gave `RECORDED` builds — recommend the same **30-day age bound**, applied to the root's `updated_at` (when it was closed) not `created_at`, plus a per-tenant count cap (proposed **5,000** most-recent closed root threads, sized above #1956's build cap since comment volume per review can exceed 1:1).
- **Mechanism: the shared retention CronJob, no new grant.** No new grant or role was needed — `schema/roles.sql` already granted `erun_tenant`/`erun_operations` `DELETE` on both `comments` and `releases` with `FOR ALL` RLS policies, so this is an ordinary tenant-scoped `DELETE`, not a carve-out. See § "Retention Mechanism" below.
- **Implemented.** `erun-backend-db/retention/comments_releases.sql` carries both tables' delete predicates exactly as designed above (`CLOSED`-only + age/count for `comments`, including the reply-together-with-its-root delete; age/count for `releases`), and records both tables' outcome into `retention_runs` per § "Retention Mechanism". `erun-devops/docker/erun-backend-db/retention_test.sh` proves both bounds — age, count, and the `OPEN`-thread exemption — plus the `retention_runs` recording (dry run and real run), the `retention.sh` entrypoint's default-to-dry-run behavior, and the advisory lock refusing a concurrent run, all against a real PostgreSQL, run via `make test-retention`. The starting constants above (180d/1,000 for `releases`, 30d/5,000 for `comments`) are what shipped; retune them once real per-tenant counts exist, the same revisit #1956 already calls for on its own constants.

### Reviews (#1971, implemented — scope narrowed to the unblocked case)

- **Split out as its own issue, not folded into `comments`/`releases` (#1970), because `reviews` is both the highest-volume table of the four groups and the structurally hardest.** Six inbound `RESTRICT`/`NO ACTION` foreign keys point at it (`builds`, `comments`, `releases`, `review_reviewers`, `review_merge_queue`, `gate_runs`) — 3x the fan-out #1956's own builds guard handled — and this file's Multi-Tenant Database Plan already states, in prose, "Branch history stays unbounded: a recycled branch name may have many `MERGED`/`CLOSED` reviews" (added in #1235 alongside the live-review uniqueness index). Whether that sentence is a deliberate promise or incidental phrasing has to be answered before any bound can be proposed — the same obligation-vs-performance question #1959 had to ask for `audit_events`.
- **The permanence signal is real but weaker than #1959's — flag it, don't resolve it.** No compliance/contractual language anywhere in the repo names review history specifically, unlike the marketing/spec language #1959 found for audit logs. But `erun-docs/docs/collaboration/operator-in-the-loop.md`'s "The path to eventual autonomy" section lists "the erun API's review history, comment threads, and build records" as one of the four surfaces backing "past and future behavior are both visible" — the trust mechanism the platform's autonomy model is built on ("the operator never has to take an Agent's word for" what it did). That is a product statement about visibility, not explicitly about retention duration — and #1970 already recommends pruning two of that same list's members (`comments`, `releases`) without treating the passage as a blocker. So this is ambiguous evidence, not a settled answer: it is enough to say the "unbounded" line might be intentional, not enough to say it definitely is. Resolving it is the operator's call, the same way #1959 left `audit_events`' floor to the operator instead of guessing.
- **Growth rate is the highest of the four groups, by construction, not just by volume of merges.** A review is created once per proposed change, and not every review reaches `MERGED` — every `OPEN`/`FAILED`/`CLOSED` review that never merges adds to this table without ever touching `releases`, so review creation outpaces #1956's own measured merge rate (~35-56/day on `sophium/erun`'s dogfooding tenant). That merge rate is a floor on `reviews`' growth, not the true creation rate.
- **Referential graph: six inbound edges with three different fates today, not one shape to guard against.**
  - `review_merge_queue.review_id` — genuinely self-clearing. This file already documents that "the active `MERGE` review must be removed from `review_merge_queue` when it is promoted" and "`CLOSED` reviews must not appear in the merge queue," so a `MERGED`/`CLOSED` review's queue row is gone well before retention would ever look at it. No prerequisite gap here.
  - `review_reviewers.review_id` — **not** self-clearing, despite #1968 filing it under "Bounded." `internal/repository/review_reviewers.go` exposes only `Create`/`List`/`Delete`, and `Delete` fires solely from the explicit `DELETE /v1/reviews/{review_id}/reviewers/{user_id}` route; `ReviewRepository` (`internal/repository/reviews.go`) has no method that touches `review_reviewers`, so nothing removes a reviewer when its review merges or closes. #1968's "bounded per review" meant reviewer *count* stays small per review, not that the rows drain on their own — a `MERGED` review keeps every reviewer ever assigned to it forever, and `ON DELETE NO ACTION` (`migrations/default/20260824130000_review_author_reviewers_branch_uniqueness.sql`) blocks deleting the review while they exist. Any `reviews` retention design has to prune `review_reviewers` itself in the same sweep — this table has no policy of its own anywhere yet.
  - `comments.review_id`, `releases.review_id` — pending #1970's own age/count bounds; a `reviews` sweep either runs after those clear for the review in question or re-checks both directly rather than assuming the timing lines up.
  - `builds.review_id`, `gate_runs.review_id` — pending #1956, and not just "wait for it to clear" — see the next bullet.
- **The pinned build is the foreign-key-from-something-longer-lived case: #1956's own design makes one `builds` row per merged review permanent, which makes `reviews` un-deletable by construction, not by neglect.** `reviews_status_build_link_check` requires `last_merged_build_id IS NOT NULL` for as long as `status = 'MERGED'`, and no route un-merges a review, so that column can never be nulled while the row exists in that state. #1956's design already exempts exactly this pinned build from its own 30-day/count bounds ("the pinned set is tiny... exempting it from both bounds costs nothing") — which means the pinned build isn't a row that merely ages out slower, it is a row `builds`' own design keeps alive for as long as the review that pins it stays `MERGED`. That closes a real cycle: the review can't be deleted while its pinned build exists (`builds.review_id → reviews`), the pinned build can't be deleted while the review still points at it (`reviews_last_merged_build_fk`, `schema/fks/review_builds.sql`), and the pointer itself can't be nulled while `status = 'MERGED'` (the check constraint). Null-then-delete is not available for a `MERGED` review — the only way through is deleting the review row and its pinned build row together, in one statement/transaction, so neither constraint ever observes the other side as a dangling reference mid-way. A `CLOSED` review that never merged has no such trap: `reviews_status_build_link_check` only requires a pin while status is `FAILED`/`READY`/`MERGE`/`MERGED`, so a `CLOSED` review's stale `last_failed_build_id`/`last_ready_build_id` can be nulled first (an ordinary `UPDATE`), and the now-unpinned build ages out through #1956's normal path.
- **Recommended shape, once the product question is answered in favor of pruning at all: split the policy by how a review reached its terminal state, not one age/count bound for the whole table.** `OPEN`/`FAILED`/`READY`/`MERGE` reviews are live work and are never candidates, the same way #1970 exempts an `OPEN` comment thread. `CLOSED` reviews that never had a build pinned are the easy case — age/count bound plus a `NOT EXISTS` guard against `comments`/`review_reviewers`/`releases`/`gate_runs`. `CLOSED` reviews with a stale `last_failed_build_id`/`last_ready_build_id` pin need that column nulled first, then the same guard. `MERGED` reviews need the coupled review-plus-pinned-build delete described above, plus a check that no `releases` row still points at that same build via `releases.build_id` (per #1970, `releases`' own 180-day bound should usually have cleared this already, but the sweep must check, not assume the timing lines up). Given this complexity and the unresolved permanence question, the conservative default mirrors #1959's: no pruning of `MERGED` reviews unless and until the operator says branch history is not a permanence promise; `CLOSED`-without-a-merge reviews are the comparatively low-risk case to prune once `review_reviewers` gets its own cleanup path.
- **Mechanism: no new grant needed.** `reviews`, `review_reviewers`, and `review_merge_queue` are already granted `DELETE` with `FOR ALL` RLS policies to `erun_tenant`/`erun_operations` (`schema/roles.sql`; `schema/rls/reviews.sql`), the same `builds`/`gate_runs` shape #1956 used, not the `audit_events` carve-out shape #1959 needed. Plugs into the retention CronJob (§ "Retention Mechanism" above) as `erun-backend-db/retention/reviews.sql`, no runner or CronJob change needed.
- **Implemented, with the scope narrowed to resolve blocker 1 conservatively rather than wait on an operator decision: `MERGED` reviews are exempt entirely, exactly as this design's own "conservative default" recommended.** `erun-backend-db/retention/reviews.sql` prunes only `status = 'CLOSED'` reviews — a review's status is one exclusive value (`reviews_status_check`), so `CLOSED` alone already excludes everything that ever reached `MERGED`, with no separate `last_merged_build_id` check needed. This sidesteps the "branch history stays unbounded" product question entirely rather than resolving it: a `MERGED` review's history is untouched by this pass, so the promise-or-incidental-phrasing question named above is still open and still the operator's to answer if `MERGED` pruning is ever wanted. Blocker 2 (`review_reviewers` has no self-cleanup path) is resolved in the same file: it prunes `review_reviewers` for exactly the reviews it is about to delete, in the same transaction, before deleting the review row — never for a review that survives the round, so "who reviewed this" is never lost for a review still standing. Starting constants not given by the original design (it left `reviews`' own age/count numbers unspecified pending the product decision): a 90-day age bound on `updated_at` and a 2,000-per-tenant count cap, reasoned from comments'/releases'/builds' own constants — see the SQL file's header comment for the full reasoning, and retune once real per-tenant counts exist.
- **Mechanism gap found while porting: the design's own guard list omits `builds`, and that omission is not cosmetic.** The design's "easy case" bullet says a `CLOSED` review with no build *pinned* needs only a `NOT EXISTS` guard against `comments`/`review_reviewers`/`releases`/`gate_runs`. But `builds.review_id` is `RESTRICT` exactly like the other four inbound edges, and any review that ever had so much as one `GATE` build attempt — the common case for a review that actually went through a gate — has a `builds` row pointing at it whether or not that row is one of the pinned `last_*_build_id` columns. Deleting a review while an *unpinned* `builds`/`gate_runs` row still references it hits a live FK violation the design's own guard list would not have caught. `reviews.sql` closes this by guarding against `builds` directly (see its header comment and `retention_reviews_test.sh` scenario 2, which locks exactly this case) rather than trusting the design's list as written. Flagging this explicitly per the task's own instruction: a mechanism/design that needed correcting on its second serious use is worth knowing about, not silently patched over.
- **Effectiveness caveat, not a correctness gap: until #1956 (`builds`/`gate_runs` retention) ships, this policy will find few or no eligible rows on a tenant whose closed reviews all went through at least one gate attempt.** A `CLOSED` review with any `GATE` build ever attached keeps that `builds` row forever under today's mechanism (no sweep ages it out yet), which fails this file's own `builds` guard forever. The policy is still correct and safe to run now — it simply prunes fewer rows than it eventually will once #1956 lands and starts aging `builds`/`gate_runs` rows out. The stale-pin-nulling step (nulling `last_failed_build_id`/`last_ready_build_id` on an otherwise-eligible `CLOSED` review) is what lets a *future* #1956 sweep eventually free up that pinned build, which in turn lets a *future* run of this reviews sweep finally delete the review — forward progress banked now, paid off later.
- **Tested end-to-end against a real postgres** (`erun-devops/docker/erun-backend-db/retention_reviews_test.sh`, run via `make test-retention`): locks the age bound, the count cap, the `OPEN`/`MERGED` exemptions, all five guard tables (`comments`, `releases`, `builds`, `gate_runs`, `review_merge_queue`) independently including the previously-missing `builds` guard, the `review_reviewers` cleanup happening only alongside its review's own deletion, and the stale-pin nulling on a review that is guard-blocked but otherwise age/count-eligible.
- **Blast radius if the 90-day/2,000 bound above is misconfigured:** an unrecoverable loss of review history and its reviewer assignments — not a crash, since nothing reads a deleted review to make a live decision. The five-table guard bounds that loss to reviews with no surviving artifact of their own, but a bound written too loose still discards real review provenance sooner than a real audit would want.

### AI Sessions (#1972, implemented)

- **The growth key is per-environment session count over the environment's lifetime, not tenant-wide calendar time — the property that made #1968's sweep split this table out on its own rather than folding it into `reviews`/`comments`/`releases`.** `ai_sessions` is a true upsert keyed on `(tenant_id, environment_id, session_id)` (`schema/tables/ai_sessions.sql`'s own comment: "a later report replaces the row outright") — a given session never grows past one row no matter how many turn-boundary events its hooks report. But a fresh `session_id` is minted continuously for as long as an environment stays alive: `AISessionLaunchCommand` (`erun-common/ai_launch.go`) deliberately never passes `--fork-session` on reattach so a *resumed* dtach tab keeps its conversation id, but Claude Code's own session id still changes mid-run at `SessionStart`'s `clear`/`compact` boundaries (`erun-docs/docs/agent-reference/skills-spec.md` § the `SessionStart` hook bullet: "the id can change mid-run"), and every detached `exec_agent` job run (`erun-common/job_agent.go`) is its own tool invocation with its own fresh session id, not a resume of the interactive tab's. So row count for a long-lived, continuously-agent-driven environment climbs for as long as that environment exists, capped only by `ON DELETE CASCADE` from `environments` (`schema/tables/ai_sessions.sql`) — i.e., only when the whole environment is deleted, which is exactly the failure mode #1956 flagged for `builds`: growth decoupled from any bound shorter than the parent resource's own lifetime, and this platform's environments are designed to be long-lived, not created-and-destroyed per task.
- **Unlike the other three groups in this sweep, there is no real traffic to measure yet — the write path has zero producers today, and that gap is the honest headline finding, not a caveat.** `POST /v1/environments/{environment_id}/ai-sessions` (`internal/routes/ai_sessions.go`) is registered and reachable, but nothing in this repository calls it: `erun activity ai-session report` — the CLI verb hooks actually invoke at each turn boundary — writes only to the environment's own local activity-dir file (`eruncommon.RecordAISessionEvent`, `erun-common/ai_session_status.go`), and the MCP `ai_sessions` tool (`erun-mcp/server.go`) only reads that same local file back (`LoadAISessionStatuses`); neither calls the HTTP route. The DB table is provisioned ahead of its own consumer — "the authenticated-edge twin," per the route's own doc comment, for a caller with no local kubeconfig/port-forward — and today has never been written to in production, the same "cannot be measured until the write path ships" position #1956 was in before #1954, except here the write path is already merged and still unused. **Estimating from the driver rather than the (currently nonexistent) data:** once wired, one row accrues per distinct session id, and #1956's own dogfooding measurement (~35-56 merges/day, "5-10 concurrent lanes" inferred to sustain it) is the closest proxy for how many environments are active at once on this one tenant; each active environment's own session count is driven by its `exec_agent` job cadence (agents in this repository run many jobs per feature branch) plus its interactive tab's own `clear`/`compact` boundaries, plausibly single digits to a couple dozen new session rows per environment per day of heavy use. Over a long-lived environment's real lifetime (weeks to months, this platform's normal case) that is hundreds to low thousands of rows — an order of magnitude below `builds`'/`reviews`' tenant-wide daily rate, but still unbounded because nothing ages a session row out on its own.
- **Referentially this is a leaf exactly like `comments`/`releases` (#1970) — nothing points at `ai_sessions` — so a retention sweep here needs no coupled-delete choreography the way `reviews` (#1971) does.** The only inbound relationship is the outbound `FOREIGN KEY (tenant_id, environment_id) REFERENCES environments (...) ON DELETE CASCADE` this table itself declares, and that cascade is deliberate (the table comment contrasts it with `usage_events.environment_id`'s `SET NULL`: "a session-status row for a deleted environment describes nothing real"). That already fully solves the *short-lived* environment case; it does nothing for the *long-lived* one the issue is actually about, since the environment never gets deleted.
- **A session row's value decays to zero the moment a newer session exists for the same environment, with one live exception.** The table holds only the *last* reported event per session — never a history of turns — so an old session's row answers exactly one question: "what state did this session end in." That question has real, current value for a session whose last event is not `exit` (`turn-start`/`tool-use`/`turn-end`/`notify` — still busy or genuinely awaiting a human, the state `ResolveAISessionStatus` and the desktop's session list both read live), and essentially none for a session whose last event is `exit`: nobody polls the terminal state of a conversation that ended, the same way nobody reads a superseded `GATE` build past its review's merge (#1956). Unlike `comments`' `OPEN`-thread exemption, this isn't a status column toggled by a separate action — it falls straight out of the `event` value already on the row, so the guard is a plain predicate (`event = 'exit'`), no new column.
- **Recommended policy: age + count on exited sessions only, keyed per `(tenant_id, environment_id)` from day one — no schema wait required, unlike `builds`' cap (#1956 had to defer per-environment keying until #1954 landed `builds.environment_id`).** `environment_id` is already `NOT NULL` and part of `ai_sessions`' own primary key, so "one environment's noisy agent lane crowding out another's session history inside the same tenant" is avoidable immediately, not a follow-up. Starting constants, offered as a starting point given the estimate above rather than a fitted answer: a **14-day age bound** on `occurred_at` for `exit`-event rows (materially shorter than `builds`' 30 days, since a session's terminal-state row loses its "why did this end" debugging value faster than a build's does — nobody investigates why a two-week-old AI session exited once the work it did is long since merged or abandoned) plus a **500-row-per-`(tenant, environment)` count cap** as the runaway-loop backstop (sized well above the "single digits to a couple dozen per day" estimate above, so it only bites a genuinely pathological environment, e.g. a hook mis-wired to mint a fresh session id every turn). Revisit both once the write path has a real producer and a week or two of actual counts, the same "tune from real counts" caveat every prior design in this sweep has had to give.
- **Mechanism needs a new grant, but not for the compliance reason #1959 needed one — this is a plain gap, not a deliberate append-only policy carved as an exception.** `ai_sessions`' grant (`SELECT, INSERT, UPDATE, REFERENCES`, no `DELETE`) lives only in the hand-written migration (`migrations/default/20260831120000_ai_sessions.sql`) — unlike every other table's grant, it was **never added to the declarative `schema/roles.sql`** that `atlas.hcl` treats as the source of truth for `atlas schema apply`/dev-diff. This file has no "sessions are append-only" prose rule anywhere (unlike `audit_events`), and no visibility/trust surface in `erun-docs` claims permanence for this table either (checked: `erun-docs/docs/agent-reference/api-protocol.md`'s two `ai-sessions` route entries describe the current-status read/write contract only, nothing about history) — so there is no policy reason to withhold `DELETE` the way #1959 withheld it from `audit_events`/`usage_events`. Granting `DELETE` on `ai_sessions` to `erun_tenant`/`erun_operations` with the existing `FOR ALL` RLS policies (`ai_sessions_tenant_isolation`/`ai_sessions_operations_access`, both already `FOR ALL`) is the `builds`/`gate_runs` shape, not the dedicated-role shape — but implementing it means also adding the missing grant line to `schema/roles.sql` itself, closing the pre-existing schema/migration drift rather than compounding it with a second hand-only grant. Same daily-CronJob precedent as the other three groups (`erun-devops/k8s/erun-backend-db/templates/migrate-repair-cronjob.yaml` shape), extended to cover this predicate once it exists.
- **Implemented.** The `schema/roles.sql` drift is fixed: `ai_sessions` now appears in the shared `DELETE`-granted table list alongside every other `FOR ALL`-policy table, and `migrations/default/20260903130000_ai_sessions_delete_grant.sql` (hand-written, matching `20260831120000_ai_sessions.sql`'s own reason — `atlas migrate diff` is login-gated on the RLS functions in the source schema) grants it to the already-migrated table. `erun-backend-db/retention/ai_sessions.sql` carries the age/count bounds exactly as designed above (14-day age bound on `occurred_at` for `event = 'exit'` rows only, 500-row-per-`(tenant, environment)` count cap, both bounds prune), plugged into the shared CronJob with no runner or CronJob change.
- **Still true as written: nothing calls `POST /v1/environments/{environment_id}/ai-sessions` yet**, so the starting constants above remain an estimate, not a measurement, independent of this pass having implemented the sweep itself. Retune once a real write path ships and real counts exist, the same "tune from real counts" caveat every policy in this sweep carries.
- **Tested end-to-end against a real postgres** (`erun-devops/docker/erun-backend-db/retention_ai_sessions_test.sh`, run via `make test-retention`): locks the age bound, the non-`exit`-event exemption, and that the count cap is per-`(tenant, environment)` — a second, quiet environment in the same tenant as a noisy one is untouched by the noisy one's count.
- **A separate cross-table audit closes the gap that made this grant miss `schema/roles.sql` in the first place: proving a table-level grant alone is not enough, since RLS or a missing grant can still block the real statement even when a catalog privilege check passes.** `make test-retention-grants` (`erun-devops/docker/erun-backend-db/retention_grants_test.sh`) runs a real `INSERT` then `DELETE` under `erun_operations` against every table carrying an implemented or designed retention policy (`builds`, `gate_runs`, `comments`, `releases`, `reviews`, `invites`, `invite_requests`, `ai_sessions`), and asserts a real permission-denied `DELETE` against `audit_events`/`usage_events`, confirming their #1959 append-only carve-out is still enforced. This is what surfaced that `ai_sessions` was the only table in that set missing `DELETE` — the rest already had it.
- **Blast radius if the 14-day/500 bound above is misconfigured:** loss of a session's last-known terminal state — "how did this AI session end" becomes unanswerable past the bound. Not a crash and not data any live decision depends on (a resolved-status read only ever wants the *current* session, never a historical one), but a real loss of debugging context for whoever investigates a stale environment's history after the fact.

### Invites And Invite Requests (#1973, implemented)

- **The lowest-urgency pair of #1968's six, split out on its own because its growth is human-paced, not event-paced.** `invites` grows one row per invite an existing member issues; `invite_requests` grows one row per unauthenticated onboarding submission. Neither fires per commit, per build, or per API call the way `builds`/`comments`/`releases`/`audit_events` do — state the order of magnitude rather than measure it precisely, the same latitude the originating issue gave this pair: onboarding activity (new members added to a tenant) runs at a small fraction of #1956's ~35-56 merges/day, plausibly single digits per day even on an active tenant, and #1968 already found zero cleanup on either table's two most common terminal states, not merely an unbounded window.
- **Both tables are audit trails of platform admission, and that is what a deleted row actually costs — not disk.** Every other table in this sweep decays toward "redundant with something durable" (`releases` with the git tag), "operationally superseded" (`builds`, `gate_runs`), or "conversation nobody reopens" (`comments`). A consumed `invites` row and a decided `invite_requests` row decay toward neither: they are the record of who was let into a tenant, on whose invitation or whose approval, and when. Losing one doesn't just lose debugging context — it loses the answer to "how did this account get in here," the exact question a security review or an incident investigation into a tenant's membership asks. That framing, not a storage argument, is what should set the bound below, and it argues for something closer to #1959's evidentiary caution than to #1956's disposable-build reasoning — with one real difference from #1959: no compliance/contractual promise blocks a decision here, so an engineering judgment call is enough, it just needs to weigh the loss honestly rather than default to a builds-sized window.
- **Neither row is reproducible from anything else in this schema — worse than `releases`, closer to `audit_events`.** `invites.accept` (`POST /v1/invites/accept`) is registered unauthenticated, directly on the mux (`RegisterInviteAcceptRoute`), not through the protected registrar — so consuming an invite writes no `audit_events` row at all; the only record that a given token was actually used, by whom it was created, and when, is the `invites` row itself with `consumed_at` set. Revoking one already deletes it immediately today (`InviteRepository.Revoke`), and even that authenticated `DELETE /v1/invites/{invite_id}` call is audited only against the canonical route template (`api_path` stores `/v1/invites/{invite_id}`, never the concrete ID — `erun-backend-db/AGENTS.md`'s own "Audit Events" section requires this), so `audit_events` never carried per-invite detail to fall back on even for that path. `invite_requests` fares slightly better — `approve`/`decline` are authenticated calls that do write an `audit_events` row for "who decided" — but the request's own content (`tenant_name`, `email`, `display_name`, and critically `decline_reason`, the only record of *why* someone was refused entry) has no second copy anywhere; ordinary audit rows leave `api_parameters` null.
- **The one referential guard runs in the direction that matters, and it's the child, not the parent, that's unconstrained.** `invite_requests.minted_invite_id → invites` is `RESTRICT` (no `ON DELETE` clause), set by both approval paths. That only threatens deleting `invites` while a `minted_invite_id` still points at it — deleting an `invite_requests` row is always safe on its own schedule, since nothing references `invite_requests` at all. So: prune `invite_requests` on its own predicate with no guard, and add the same `NOT EXISTS` guard shape #1956/#1970 already use before deleting a consumed `invites` row — `NOT EXISTS (SELECT 1 FROM invite_requests WHERE minted_invite_id = invites.invite_id)`. In practice this rarely fires long: `invite_requests`' own age bound (below) is shorter than `invites`' own, so the referencing row is normally already gone by the time the invite would otherwise qualify.
- **`invite_requests` has no `tenant_id` and no RLS at all — the count-cap side of the policy can't be "per tenant" the way every other table in this sweep is.** The submitter isn't authenticated into any tenant yet, so the table is deliberately global (`schema/rls/` has no file for it); `tenant_name` is free text, not an enforced key. A count cap here has to be platform-wide, not per-tenant, and the sweep connection needs no `SET ROLE erun_operations` to reach every row the way it does for RLS-protected tables — every role already sees every `invite_requests` row.
- **Recommended policy: age bound is the loss-driven part, count cap is the usual runaway-loop backstop.** Split by terminal state, matching the guard the sibling designs already give a live/non-live split:
  - `invites` with `consumed_at IS NOT NULL` (the row that proves someone was actually let in): recommend a **365-day age bound** — long enough to survive one full access-review cycle (the standard cadence a SOC2/security review re-certifies tenant membership on), which is the realistic horizon for "how did this account get access" to actually get asked, not a debugging-session horizon. Per-tenant count cap: **10,000** rows, sized well above plausible onboarding volume so it backstops a scripted invite-spam abuse case rather than ever being the normal trigger.
  - `invites` with `consumed_at IS NULL AND expires_at < now()` (issued, never used, nobody was let in): recommend the shorter **30-day age bound** #1956 gave `builds` — its only remaining value is "did we actually send invite X," a debugging-session question, not an access-provenance one. Same **10,000** per-tenant count cap (shared with the consumed case; both are `invites`, one table).
  - `invite_requests` with `status IN ('APPROVED', 'DECLINED')`, exempting `PENDING` the same way #1970 exempts `OPEN` comment roots: recommend a **180-day age bound**, applied to `updated_at` (when decided) not `created_at` — shorter than the consumed-invite window because the decision itself (who approved/declined, when) is already durably audited via `audit_events`; only the request's own content and, for a decline, the reason, are at risk, and those matter for a shorter "was this abuse" review rather than a year-long access-provenance one. Recommend a **platform-wide count cap of 10,000** rows (not per-tenant — see above).
- **Mechanism: the same scheduled CronJob, same connection, no new grant.** `schema/roles.sql` already grants `erun_tenant`/`erun_operations` `DELETE` on both `invites` and `invite_requests`; `invites` has `FOR ALL` RLS policies for both roles, so pruning it is an ordinary tenant-scoped `DELETE` under `erun_operations` the same way `builds`/`comments`/`releases` are swept. `invite_requests` has no RLS to bypass, so its own delete predicate needs no role switch at all beyond whatever connection the job already uses.
- **Implemented.** `erun-backend-db/retention/invites_invite_requests.sql` prunes `invite_requests` first (no guard needed, `APPROVED`/`DECLINED` only, 180-day age bound on `updated_at`, 10,000-row platform-wide count cap since the table has no `tenant_id`), then `invites` (365-day age bound on `consumed_at` for consumed invites, 30-day age bound on `expires_at` for unconsumed-expired invites, both sharing a 10,000-per-tenant count cap ranked separately per population), both inside the same transaction so the `NOT EXISTS (SELECT 1 FROM invite_requests WHERE minted_invite_id = invites.invite_id)` guard sees `invite_requests` already pruned before it runs. Plugs into the shared CronJob with no runner or CronJob change.
- **Tested end-to-end against a real postgres** (`erun-devops/docker/erun-backend-db/retention_invites_test.sh`, run via `make test-retention`): locks the `PENDING`/live-invite exemptions, both `invites` age bounds independently, the count cap, and — the one property unique to this policy — that a consumed invite still referenced by a `PENDING` request's `minted_invite_id` survives past its own age bound even though the request pruning already ran in the same sweep.
- **Blast radius if a bound above is misconfigured:** for `invites`, an unrecoverable loss of "how did this account get access" provenance — the design's own framing that this pair is closer to `audit_events`' evidentiary caution than to `builds`' disposable-record reasoning, since neither row is reproducible from anything else in the schema. For `invite_requests`, loss of the request's own content and, for a decline, `decline_reason` — the only record of *why* someone was refused entry. Both bounds were left as this pass's own judgment call, same as the original design; retune once real onboarding-volume counts exist.
