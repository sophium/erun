# AGENTS.md

Module-specific guidance for `erun-backend-api`. Follow the repository root and `erun-backend/AGENTS.md` first.

## Module Role

- `erun-backend-api` is the Go HTTP API module for hosted ERun backend functionality.
- API endpoints must require an OIDC bearer token unless the endpoint is explicitly infrastructure-only, such as the `/healthz` health check.
- The token `iss` claim determines the tenant. Resolve the tenant before invoking endpoint behavior, then pass tenant identity explicitly through request-scoped context.
- Keep endpoint handlers thin: authenticate, adapt HTTP inputs, call focused workflow or persistence code, and return JSON-safe responses.
- Do not let CLI or MCP import this module directly. Shared clients, request contracts, and result contracts used by CLI and MCP belong in `erun-common`.

## Layer Layout

- Keep each API layer in its own directory under `internal/`.
- Put DB-mapped entities in `internal/model/`.
- Put SQL persistence code in `internal/repository/`.
- Put workflow orchestration in `internal/service/` only when a workflow has real logic beyond calling one repository method.
- Put HTTP route registration, request parsing, and response writing in `internal/routes/`.
- Keep `server.go` as the composition boundary. It should construct repositories, optional services, routes, and middleware, then wire them together.
- Do not create layer directories as empty abstractions. Add a service file only when a service owns behavior.
- Keep imports directional: routes may import repositories or services and model; services may import repositories and model; repositories may import model; model must not import API layers.

## Model Entities

- `internal/model` is the shared entity language for all API layers.
- Model structs should map to database tables, for example `model.Review` for `reviews` and `model.Comment` for `comments`.
- Do not create separate repository entities, service entities, domain entities, DTOs, or response entities that mirror the same table fields.
- Repositories must use Bun for database row mapping into `model` structs. Do not add new hand-written `Scan` helpers for table-backed entities.
- Services should accept and return `model` structs when they are working with table-backed entities.
- Routes may return `model` structs directly when the API shape matches the entity.
- Routes may decode create/update JSON into `model` structs when the writable API shape mostly matches the entity. It is acceptable for clients to send read-only fields in that JSON; persistence must ignore them.
- Model structs may include read-only, derived, or UX-facing fields when repositories return those fields for display, such as counts, labels, status details, or related entity names.
- Treat read-only model fields as persistence-output fields, not as strict JSON-unmarshal fields. Go's standard JSON decoder may populate them when decoding into a model, but repository writes must not persist caller-provided values.
- Distinguish read-only model fields by write ownership: Bun tags and repository write column lists must prevent inserting or updating them, database defaults/triggers must own generated values, and repository read queries should be the only code that intentionally populates UX-derived fields.
- Externally visible IDs, tenant IDs, and timestamps are read-only model fields. Create methods may receive a model value, but must not persist caller-provided values for those fields; IDs, tenant IDs, and timestamps should be generated by the database and returned from the insert.
- Do not defensively copy a create input model into another same-type model just to drop read-only fields. Keep the model value intact and rely on explicit Bun `Column(...)` lists plus database defaults/triggers to define the write set.
- Add a short field comment for read-only, derived, or UX-facing model fields unless the field name makes that status obvious. Use `omitempty` when the field is not populated by every read path.
- Route-local request structs are allowed for partial inputs such as create requests, status updates, filters, or path/body combinations that are not full table entities.
- Do not add entity-to-entity mapping just to cross a layer boundary.

## Repository Layer

- Repositories own SQL and persistence behavior.
- Repository methods should use `context.Context` and return `model` values directly.
- Prefer a small standard method vocabulary for entity persistence: `Create`, `Get`, `List`, and `Update` when those operations exist. Add `Delete` only when the product actually hard-deletes rows.
- Use `Get(ctx, id)` for lookup by a globally unique public ID. Do not require parent IDs in `Get` methods only to duplicate route nesting or tenant filtering.
- Use `List(ctx, filter)` with a small repository-local filter params struct when listing needs filters. Prefer this over adding many `ListBy...` methods as new filters appear.
- Repository methods should be basic CRUD or find/list methods. Do not put business workflow names such as `UpdateStatus`, `AdvanceMergeQueue`, or build-result promotion on repositories.
- Put business workflows in `internal/service/`. Services should load models through repositories, mutate the model according to the workflow, and persist through repository `Update` or queue CRUD/find methods.
- Repository methods should not parse HTTP, write JSON, inspect headers, or know route names.
- Repository methods should not receive security filter arguments such as tenant ID or user ID just to satisfy RLS. Security context setup belongs to shared transaction wiring.
- Keep authentication identity resolution separate from normal user management. `IdentityRepository` should own only issuer/subject resolution and first-identity bootstrap; list/get/update user behavior belongs in a separate `UserRepository`.
- Do not add general user CRUD or profile-management methods to `IdentityRepository`. Add `UserRepository` when implementing user-management behavior such as listing users, looking up users by ERun user ID, editing user profile fields, linking external identities outside bootstrap, activating/deactivating users, or managing user-visible user state.
- Bun model tags belong on the existing `internal/model` structs. Do not introduce separate Bun entities that mirror the same table fields.
- Bun usage must preserve repository ownership, explicit transaction/RLS wiring, explicit filters, and output-only model fields. Do not let Bun associations or implicit tenant scopes replace PostgreSQL RLS or repository method contracts.
- Persisted fields should map directly to table columns, while read-only UX fields such as `Build.ReviewName` must use Bun scan-only or write-ignored mapping semantics and must not be inserted or updated.
- Repository queries should remain SQL-visible through Bun query builders or explicit SQL. Do not hide tenant-sensitive behavior behind broad implicit ORM behavior.
- Bun raw SQL should use Bun `?` placeholders, including PostgreSQL security-context SQL such as `set_config(...)`. Do not write driver-specific `$1` placeholders in Bun-managed queries.
- Tenant-owned SQL should run inside repository transaction wiring that reads the authenticated security context from `context.Context`.
- For PostgreSQL, transaction wiring must set `erun.tenant_id` with transaction-local scope before tenant-owned SQL runs.
- For PostgreSQL operations that depend on user ownership, such as closing comments, transaction wiring must also set `erun.user_id`.
- Use transaction-local settings such as `set_config(..., true)` so values do not leak through pooled connections.
- Missing security context inside repository transaction setup is an internal wiring error for protected routes, not a user authentication failure.
- Backend API persistence uses the default PostgreSQL-backed database. Do not add SQLite repository branches, compatibility SQL, or local fallback behavior.

## Service Layer

- Do not add service pass-through methods that only call one repository method with the same inputs and outputs.
- Do not make a route depend on a service for all entity endpoints just because one endpoint on that entity has workflow behavior.
- Route groups may accept both repository and service dependencies. Choose the dependency per handler: repositories for persistence-only handlers, services for workflow handlers.
- Routes should call repositories directly for simple CRUD or simple lookups.
- Routes should call services only for business actions such as status transitions, merge queue advancement, build-result promotion, comment ownership behavior, or any workflow that coordinates more than one repository call.
- Add a service when it owns real workflow behavior, such as coordinating multiple repositories, applying state-transition rules, deriving child comment fields from a root comment, writing audit events with another action, or running multiple writes in one transaction.
- A service may expose a small preparation method only when it owns server-derived input for a create/update flow, such as default status or creator ownership. The route should still call the repository for the final simple persistence operation.
- Services should remain transport-neutral. They should not read HTTP headers, path values, or request bodies.
- Services should use `model` structs as their entity language and avoid layer-specific entity copies.

## Routes Layer

- Routes own HTTP adaptation: path values, query values, request body decoding, status codes, and JSON responses.
- Protected routes should be registered behind authentication middleware and may assume authenticated security context exists.
- Do not repeat `security.RequiredFromContext` checks in every protected route just to reject invalid users. Authentication middleware must reject invalid, missing, or unknown users before route code runs.
- If a route needs authenticated identity as user-visible input, prefer a small helper that treats missing context as an internal wiring error.
- Keep route request structs local to `internal/routes` unless the request contract is intentionally shared with CLI or MCP through `erun-common`.
- Avoid route-to-model response mapping when the model already has the correct JSON shape.
- `erun-integration`'s desktop-surface gate (`erun-integration/AGENTS.md` § "Desktop-surface gate") audits every route registered here for an operator entry point in `erun-ui/frontend` or `erun-console`, the same standard it already holds CLI commands and MCP tools to. A route with no operator surface and no real one planned for this change needs an explicit exemption in `route_audit.go`'s `InternalAPIRoutes`, with a comment explaining why — silence is never how a route opts out.

## Reviews And Builds

- Review `name` is the squash merge message.
- Reviews must have both `targetBranch` and `sourceBranch`.
- Review status values include `OPEN`, `CLOSED`, `FAILED`, `READY`, `MERGE`, and `MERGED`; do not remove existing statuses when adding workflow states.
- Successful builds should move `OPEN` or `FAILED` reviews into the per-target-branch merge queue as `READY`.
- A `READY` review becomes `MERGE` only when it is advanced as the next item for that target branch. The promoted environment is expected to build the prospective merge onto the *current* target itself — the property that catches two reviews that are each green alone but broken together before the target branch moves.
- If a `MERGE` review misses its merge window without failing, move it back to `READY` at the end of the same target branch queue.
- Failed builds for queued or merging reviews should move the review to `FAILED` and remove it from the queue.
- `MERGE` is never a caller-reported status — `PATCH /v1/reviews/{review_id}/status` refuses it; only `AdvanceMergeQueue`/`OverrideAdvanceMergeQueue` promoting the queue head reach it. `MERGED` *is* reachable from `PATCH .../status`, from any caller, because acceptance is verified rather than privileged (see "Merge Queue" below): the platform checks the reported `buildId` names an already-recorded, successful `GATE` build for this review, and fetches `remoteUrl` to confirm that build's commit is really on the target branch with the parent this review was gated against. `builds.kind = 'GATE'` marks that build; it carries no version because the gate publishes nothing.
- `CLOSED` reviews must not appear in the merge queue.
- Review list endpoints should support filtering by target branch, source branch, status, author, and reviewer, composable with each other.
- `Review.AuthorUserID` is a read-only, database-defaulted field (`erun_current_user_id()`). Never add it to a repository `Create`/`Update` column list — a client-supplied value in the request body must be ignored, the same as tenant ID and timestamps.
- Reviewer assignment is a separate resource (`ReviewReviewerRepository`, table `review_reviewers`), not a field on `Review`. Adding a reviewer does not gate any review status transition.

### Builds Without A Review (erun#1954)

- **`Build.ReviewID` is optional, not a second table.** An ordinary `erun build` run (agents run this continuously, in every environment) previously had nowhere to be recorded at all, because `review_id` was a required column. The same table, model, and route family now cover both cases: a review-linked build (`RECORDED`/`GATE`, reported through `POST /v1/reviews/{review_id}/builds`) and an unattached build (always `RECORDED`, reported through `POST /v1/builds`). This is the opposite conclusion from `gate_runs` (see "Gate Runs" below), and for reasons specific to each: `gate_runs` needed a genuinely new verdict vocabulary (`INCONCLUSIVE`) that `builds.successful`'s boolean cannot express, and forcing a GitHub-PR-only repository to open an erun review just to get a build recorded would conflate code review with CI verification. Neither reason applies here — an ordinary build always does reach a real success/failure outcome, and giving it no `reviewId` skips the review-status transition entirely rather than forcing one.
- **What identifies an unattached build:** tenant + environment + commit + version, not a review. `EnvironmentID` (nullable, `ON DELETE SET NULL` like `usage_events.environment_id` — an append-only build history should outlive the row it described) is the identity a build with no review reports instead. A build naming neither a review nor an environment is refused (`UnattachedBuildRequiresEnvironmentError`) — it would have no identity at all.
- **A `GATE` build always carries a `ReviewID`.** It gates a specific review's merge by definition, so `POST /v1/builds` refuses `kind: GATE` outright (`kind must be RECORDED for an unattached build`) and the service layer refuses one reported with no review even directly (`GateBuildRequiresReviewError`) — enforced again at the database layer by `builds_gate_requires_review_check`, the same defense-in-depth `builds_version_check`/`builds_failure_detail_check` already practice.
- **`GET /v1/builds` paginates; the review-nested list does not.** A review's own builds are naturally bounded (one review, a handful of attempts); the tenant-wide history an ordinary `erun build` feeds is the platform's highest-frequency write, so it uses the same keyset-cursor shape `audit_events` already established (`BuildListFilter`/`BuildCursor`/`BuildPage`, mirroring `AuditEventFilter`/`AuditEventCursor`/`AuditEventPage`) rather than gate_runs' unbounded, unpaginated list — gate_runs and per-review builds are both human-paced; ordinary builds are agent-paced and unbounded. Retention/pruning for this table is intentionally not part of this change (erun#1956): every other high-volume table in this schema (`usage_events`, `gate_runs`, `audit_events` itself) also has no TTL or reaper today, and picking a per-tenant retention window is a distinct design decision, not a schema afterthought.
- **`POST /v1/builds` always clears any caller-supplied `reviewId`.** There is exactly one route for a review-linked build and exactly one for an unattached build; a body field cannot smuggle a review link through the unattached route, the same discipline that already ignores a caller-supplied `authorUserId`/tenant ID/timestamp.

## Authentication

- Validate bearer tokens before resolving tenant state.
- Treat missing, malformed, or unverifiable bearer tokens as unauthorized.
- Treat an unknown issuer as unauthorized because it cannot be mapped to an ERun tenant.
- Resolve the ERun user from the token issuer and subject before protected route code runs.
- Store tenant ID, ERun user ID, external issuer, and external user ID in request-scoped security context.
- Avoid package-level mutable auth configuration. Pass verifiers and tenant resolvers through explicit API construction.
- Prefer a single identity resolver when database-backed auth is used, because empty-database bootstrap must resolve or create tenant, issuer, user, roles, and permissions atomically.
- If there are no tenants, the first valid authenticated identity may create the initial `OPERATIONS` tenant and first ERun user. That user must receive both predefined roles: `ReadAll` and `WriteAll` — the platform's own genesis bootstrap, which has no other user yet to administer even the platform's own tenant registration.
- Once any tenant exists, unknown or unregistered issuers are unauthorized, and an unknown external subject is unauthorized for a tenant that already has a user. The one implicit-creation case beyond empty-database bootstrap is per-tenant first-user bootstrap: when a token resolves to a tenant that has zero users, enrol that subject as the tenant's first user. What that user receives depends on the tenant's type (`IdentityRepository.insertTenantFirstUserAccess`): an `OPERATIONS` tenant's first user gets `ReadAll`/`WriteAll` too, the same reach the genesis bootstrap grants, because this tenant's own root-resolution capabilities (registering another tenant, administering the platform's IdP, the one-time bootstrap-name repair) live only behind that wildcard and no other user exists yet in the tenant to grant it later; a `COMPANY` tenant's first user gets `TenantAdmin` instead — full administration of that tenant, without platform-operator reach. This is how a newly-provisioned tenant gets its first admin; for an org-scoped issuer it means the first valid caller in a new org becomes that tenant's admin. Do not create users implicitly in any other case.
- `ReadAll`/`WriteAll` at enrolment is otherwise **not** the default. `UserRepository.Create` (the shared enrolment path behind `POST /v1/users`, `POST /v1/identity/users`, and invite acceptance) grants only the roles named in a caller-supplied `roleIds` when given. Otherwise, the tenant's first user gets `TenantAdmin` (mirroring the sign-in bootstrap bullet above for that path) — granting a role is itself permission-gated, so a first user enrolled with nothing could never be granted anything — and every later enrollment defaults to `TenantUser` rather than the zero-role default this repository shipped briefly: an invited colleague can read the tenant and drive reviews/comments/builds/the merge queue and existing environments immediately, not sit fully capability-less (unable even to read `GET /v1/whoami`) until someone remembers to grant a role by hand. See `internal/routeroles` and the "Predefined Roles" section below for what `TenantUser`/`TenantAdmin` actually grant.
- Operations tenants are system tenants. PostgreSQL RLS allows them to access tenant-owned rows across tenants by setting the transaction role to `erun_operations`, but API authorization must still require assigned roles and permissions.
- Normal tenant transactions must use PostgreSQL role `erun_tenant`; operations tenant transactions must use PostgreSQL role `erun_operations`.

## Authorization

- Permissions are stored in `role_permissions` as either exact API method/path pairs or regex method/path patterns.
- Permission matching must use the canonical API path template set by route registration, such as `/v1/reviews/{review_id}`, not the concrete request URL.
- Keep broad predefined roles pattern-based: `ReadAll` covers all read-style methods across all API paths, and `WriteAll` covers all write-style methods across all API paths.
- **`TenantUser`/`TenantAdmin` are the narrower predefined roles, built from exact routes, never a hand-authored pattern.** `internal/routeroles` (`Routes`, a `map["METHOD /path"]Class`) is the single source of truth for which registered route each grants: `TenantUserClass` (both `TenantUser` and `TenantAdmin` grant it — reading the tenant, driving reviews/comments/builds/the merge queue, operating environments that already exist), `TenantAdminOnly` (only `TenantAdmin` — creating/deleting environments, registering contexts, managing users/invites/roles/org-adjacent settings), or `OperationsOnly` (neither — reachable only through `ReadAll`/`WriteAll`, even from inside an `OPERATIONS` tenant, so `TenantAdmin` stays a genuinely lesser position than the platform operator there). `routeroles.TenantUserPermissions()`/`TenantAdminPermissions()` derive each role's exact `role_permissions` grants directly from that map. `internal/repository/predefined_roles.go`'s `ensureNarrowerRolesExist` creates/re-grants both roles for a tenant lazily and idempotently — at every first-user bootstrap and every `RoleRepository.List` read — so an already-bootstrapped tenant (or one that predates a later route reclassification) picks up the current grant set the next time anything calls it, with no migration backfill.
- **Every registered route must be classified.** `erun-integration`'s role-classification gate (`erun-integration/AGENTS.md` § "Role-classification gate") fails when a route registered in `internal/routes` has no entry in `routeroles.Routes` — the same "classify every route or fail" discipline as its desktop-surface gate, so a route added later cannot silently land inside or outside `TenantUser`/`TenantAdmin`.
- Route handlers should not check role names directly. Authorization middleware should compute access from the authenticated user's assigned roles and permissions before the route handler runs.
- **The caller's effective permission set is reported, not left to be guessed.** `GET /v1/whoami` carries `capabilities`: every registered route this caller would be let through to. It is resolved by the same authorizer that enforces access (`PermissionAuthorizer.PermittedRoutes`, one query and one matcher shared with `Authorize`), over the handler's own route catalog. A second implementation of the decision is a second place for it to be wrong — a client rendering from a capability set that disagrees with enforcement is worse than one with no set at all, because it teaches an operator to expect the wrong thing.
- The candidate set is the routes the handler actually registered (`routeCatalog`), recorded as they register and read per request, so a route added anywhere reaches the answer without a second list to maintain.
- `capabilities` is deliberately not `omitempty`. An empty set means "this caller may do nothing" and a missing field means "this platform cannot say" — a client treats the second as licence to attempt the call, so collapsing them would hide surfaces a caller can use. For the same reason a capability set that cannot be resolved fails the whoami read rather than answering without one.
- **The operations gate stays keyed on tenant type, not roles (recorded decision).** Every user of an `OPERATIONS` tenant inherits that tenant's cross-tenant `erun_operations` reach regardless of which roles they hold, because the gate checks `tenants.type`, not a permission. Moving it to a role-based check is a deliberate, separate security change (narrower blast radius per OPERATIONS user) rather than something to fold into ordinary role-assignment work — it needs its own design pass on what an "operations-scoped" permission means and how it interacts with `erun_operations`'s RLS bypass.

## Identity Resolution Cache

- Authentication middleware may cache issuer, external subject, tenant, and ERun user resolution results with a bounded TTL.
- Cache both successful and failed external identity lookups.
- Failed external identity lookup caching is required so repeated requests with invalid external IDs do not repeatedly hit the database.
- Keep negative-cache TTL short enough that newly created users become usable without a long delay.
- Keep positive-cache TTL bounded so tenant issuer and user mapping changes converge without restarting the API.
- Key identity caches by issuer and external subject. Do not cache only by subject because subjects are issuer-scoped.
- Also key on the resolved org claim value for org-scoped (shared) issuers. Under a shared issuer the same `(issuer, subject)` resolves to different tenants per org, so an `(issuer, subject)`-only key would serve one tenant's resolved RLS context to another. Derive the org before the cache lookup (its claim name lives on `issuers.org_field_key`) and include it in the key; single-tenant issuers resolve org to empty and keep `(issuer, subject)` behavior.
- Do not cache raw bearer tokens as identity keys.
- Do not let identity cache decisions bypass token verification. Verify the bearer token first, then use claims to look up cached tenant/user resolution.
- Cache entries must be safe for concurrent requests and must not use package-level mutable globals. Pass cache instances through API construction.
- Expose cache TTLs as explicit configuration when they become runtime-tunable.

## Audit Logging

- Authentication or request middleware should write audit events for successfully authorized API requests.
- Do not make individual route handlers responsible for routine audit logging.
- Write audit events only after token verification, tenant resolution, user resolution, and endpoint authorization have succeeded.
- API audit events must include tenant ID, ERun user ID, external issuer, external user ID, type `API`, API method, canonical API path, and event time.
- The audit API path must be the same canonical route template used by `role_permissions.api_path`, such as `/v1/reviews/{review_id}`, not a concrete URL containing IDs or query strings.
- Use the canonical route path and method observed by middleware as the audit source. Do not let routes hand-write those values for normal request auditing.
- Register protected routes through the shared route registration helper so the canonical API path is available to authentication, authorization, and audit middleware.
- Audit logging should use the same request-scoped security context that repository transaction wiring uses.
- Audit writes should target PostgreSQL, matching `erun-backend-db` schema guidance.
- Future CLI and MCP audit callers must set type `CLI` or `MCP` and populate `cli_command` or `mcp_tool` respectively. Store parameter payloads as serialized text, preferably compact JSON for structured input.
- **MCP classification is implemented (erun#763), CLI is not.** `AuthMiddleware.logAuditEvent` (`auth.go`) authenticates an MCP tool call exactly like any other bearer-token caller — there is no separate token scheme, so nothing distinguishes the two on the wire except a caller-set header. `eruncommon.PlatformClient.WithMCPTool` sets `eruncommon.MCPToolAuditHeader` on the request; `logAuditEvent` reads it and, when present, records type `MCP` with `mcp_tool` set instead of the default type `API`. `erun-mcp`'s tool handlers set `eruncommon.Context.MCPTool` to their own tool name before calling into shared `erun-common` execution that reaches this API (`review_*`, `platform_*`, `gate_*`/`exec_gate-run_*`/`exec_reconcile-bypass`, `expose`/`unexpose`'s platform DNS path, and `build`'s self-report to the platform, `erun-common/build_report.go`) — `newPlatformClientForAlias` forwards the field onto the client automatically, so a new platform-backed MCP tool gets correct classification for free once it sets `ctx.MCPTool`. This reclassifies existing audit rows; it adds none. Every one of those call paths was already authenticated and already wrote an `audit_events` row as type `API` before this change — the fix only makes the row say who really made the call. The much larger set of MCP tools that never call this API at all (`exec_raw`, `list`, `idle`, job-status polling, and the rest of the purely in-pod surface) still write no audit row, by architecture: `audit_events` is this API's own request log, not a general erun-mcp activity log, and auditing every in-pod tool call would require a new write path and a very different volume/retention analysis (see `erun-backend-db/AGENTS.md`'s "Retention For Append-Only Audit/Usage Tables") — out of scope for this fix. `erun-cli` does not set an equivalent header yet, so a CLI call to the same routes still reads as type `API`; wiring the CLI half is separate follow-up work.
- Treat audit logging failure policy as an explicit API configuration decision. Default request auditing should prefer failing closed only when the endpoint requires audit durability; otherwise log/report the audit failure without hiding authorization failures as unrelated route errors.
- Do not log audit events for requests rejected before authorization, such as missing tokens, invalid tokens, unknown issuers, unknown external users, or denied permissions.

## IDs

- Use UUIDv7 for all externally visible API IDs.
- Keep externally visible ID generation in database defaults. Create routes and repository create methods must not accept or generate those IDs in application code.

## Server-Side Executors

- Work that needs the erun toolchain and does not already have a warm daemon and checkout to run against — env-deploy, stop, and delete — runs as a Kubernetes Job in the tenant's runtime image, never embedded in the API. `internal/jobexec` owns the shared half — creating the Job, watching it to a terminal outcome, and reading the run's own account of a failure off the pod before the TTL reaps it. A new executor supplies only its Job shape and its command; do not write a second launcher.
- Key a Job and its durable workflow by the **attempt**, never by the resource. A name derived from something already terminal makes a retry re-read the previous outcome instead of running — the replay bug behind #1020.
- Derive the attempt suffix from a hash of the whole id, not a slice of it. A UUIDv7's leading characters are its timestamp, so two ids minted milliseconds apart share them and collapse onto one Job name.
- A Job that sets `command` replaces the image's entrypoint, so nothing the entrypoint would have exported is set. Pass what the run needs explicitly (`ERUN_REPO_PATH` is the one that has bitten).
- Record a failure in the run's own words. A reason that says only that a Job exited names nothing an operator can act on.
- **The merge gate and the release run are deliberately not this pattern (recorded decision, obsoletes #1463).** Both used to be a dedicated Job (`internal/mergeexec`, `internal/releaseexec`) mounting only the agent environment's `HomeClaim`/`WorkspaceClaim` — no docker socket, no dind sidecar, no `DOCKER_HOST` — so `erun build`/`erun release` had no daemon to connect to and failed immediately, verified against a real disposable `batch/v1.Job`. The fix is not a bigger Job: the environment that gets promoted to `MERGE`, or that earns a release, already holds a real workspace, a running daemon, and a warm fingerprint cache, so it does the work itself and reports the outcome. There is no Job, no cluster dependency, and no per-instance placement config (`provision.MergeConfig`/`ReleaseConfig` are gone) for either anymore.

## Release Queue

- The queue releases what has already been accepted. It does not approve, and it must not grow merge-decision logic.
- `ReleaseService` (`internal/service/releases.go`) owns only `Enqueue`/`Get`: recording a trigger exactly once per `(tenant, commit)`, requeuing a failed one as a new attempt, and answering an already-released commit with the row that already exists. Minting a second version for one merge commit is the worst failure this feature can have.
- **Nothing claims or runs a queued release yet.** `internal/repository/releases.go`'s `ClaimNext`/`RecordOutcome`/`ExpireStale` still hold the serialisation contracts (one running row per tenant via a partial unique index, a cooldown, stale-release expiry) and are exercised directly against Postgres in `release_queue_sql_e2e_test.go`, but no service or route calls them — the Job that used to (`internal/releaseexec`) is gone, and its environment-driven replacement (whichever environment earns the release runs `erun release` itself and reports the build, the same shift `MERGED` made — see "Merge Queue" below) is not wired up. A trigger reliably records `queued`; draining the queue is future work.

## Merge Queue

- The merge queue is what makes `MERGED` mean something happened, not something a caller asserted — but the guarantee is now a fact checked about the repository, not a claim believed because of who reported it. Promoting a review to `MERGE` (`ReviewService.AdvanceMergeQueue`) is the cue for whichever environment gets promoted to fetch the review's target and source, build the prospective squash merge locally, gate it with a real `erun build`, and push only on green — using its own already-warm workspace and daemon, not a Job standing up a cold one.
- `MERGED` is reached by `PATCH /v1/reviews/{review_id}/status` — from any caller — via `ReviewService.acceptMerged`, never by a privileged internal path. Before accepting it, `acceptMerged` checks all three: `verifyGateBuild` confirms `buildId` names an already-recorded, successful `GATE` build against this exact review; `verifyRepositoryState` fetches the caller-supplied `remoteUrl` (`internal/gitverify.RemoteVerifier`, real `go-git`, no `git` binary needed in this container) to confirm the build's commit is really reachable from the target branch's tip, and that `gatedTargetTip` — the merge commit of whichever review most recently reached `MERGED` on the same target branch, or nothing to compare against for the first merge through the queue on a branch — is really its *ancestor*. Any of the three failing refuses with `*MergeNotVerifiedError` (409, `MERGE_NOT_VERIFIED`) and leaves the review at `MERGE`.
- **Ancestry, not strict parent equality (erun#2250 fix).** The check used to require the reported commit's immediate parent to equal `gatedTargetTip` exactly. The release flow (see root `AGENTS.md` § "Release Rules") pushes its own `[skip ci] release`/`sync package metadata`/`prepare <next>` commits straight to the target branch outside the review queue, and `acceptMerged` fires again for the very next review a release's own `TriggerRelease` call enqueues — so the first release after any merge moved the branch tip past `gatedTargetTip`, the next review's reported parent could never equal it again, and the queue refused every merge permanently from then on. `MergeVerifier.IsAncestor` (`internal/gitverify`) replaces the equality check with reachability: `gatedTargetTip` must be an ancestor of (or equal to) the reported commit, tolerating any number of unrelated commits landing in between while still refusing a commit whose history never really passed through the gated tip at all (a force-push replacing it, the property `TestMergeQueueRefusesAMergeReportedAgainstAStaleTarget` locks). `gatedTargetTip` itself stays the right anchor: no per-build record of "the tip this build was actually gated against" exists on `model.Build`, and the one-`MERGE`-review-per-target-branch invariant already makes reading it at verification time equivalent to reading it at promotion time (see below), so there is nothing more precise to compare against.
- The gate is `erun build`, never `erun release`. The gate publishes nothing — releasing stays exactly where #1030 put it, after the merge lands, triggered off the merge commit the gate produced. `ReviewService` calls `ReleaseTrigger.TriggerRelease` directly on a successful `acceptMerged` — no cycle, because `ReleaseService` does not depend back on `ReviewService` the way the old Job-dispatching `MergeQueueService` had to avoid one.
- A failed `GATE` build does not need this verification: reporting one through the ordinary `POST /builds` route reaches `ReviewService.MarkBuildResult`, which (being kind-agnostic) already moves a `MERGE` review straight to `FAILED` exactly as a failed `RECORDED` build would. Only a *successful* `GATE` build's `MERGED` claim needs the separate, verified `PATCH .../status` call.
- One merge in flight per `(tenant, target_branch)` falls out of the existing invariant `AdvanceMergeQueue` already enforced: it refuses to promote while a `MERGE` review is active on that branch. Because the head is always gated against the *current* target, re-testing after each landed merge is automatic rather than a separate invalidation pass — and it is what makes reading `gatedTargetTip` at verification time equivalent to reading it at promotion time: nothing else can move a target branch's recorded tip while this review is the one holding `MERGE` on it.
- A build reported for one review can promote a *different* review to `MERGE`. Every call site that can produce a promotion has to observe the promoted review, not assume it is the one it was already looking at.
- **An agent environment has no way to provision the platform cloud alias driving this queue requires (#1969, design recorded on `feature/1969-agent-platform-alias`, not yet implemented).** Every step of `erun-merge-queue-drive` resolves through `newPlatformClientForAlias`, which needs a pre-configured erun-type cloud provider alias — and the only way to create one today is an interactive OIDC login (device code or loopback PKCE), both of which need a human in a browser. A freshly provisioned or recreated agent pod has neither, so it cannot self-report a gate run even though the design assumes "whichever environment gets promoted to MERGE" can. Recommended fix: a Zitadel machine user (client-credentials grant) provisioned server-side per tenant, verified through erun-backend-api's existing OIDC-bearer path with no new authentication scheme — not a new trust anchor. Until this lands, the queue is driven by hand from an already-authenticated environment.

### What a hand-run merge-queue script should hand off to erun vs keep as operator policy (#1987)

- **Why a script existed at all.** `erun-merge-queue-drive` needs a pre-configured platform cloud alias for every command it runs, and an agent environment has no unattended way to provision one (#1969) until the design there (#1978, open) lands and is implemented. Until then, driving the queue from an agent pod means running the same primitives by hand — which is exactly what produced a ~30-line script doing ~20 merges in one session, plus three behaviors the skill itself does not have.
- **Batch-gating N branches into one prospective merge, with a per-branch conflict skip: a real capability gap, not just a scripting convenience (implemented, erun#2011).** `erun exec gate-merge` used to take exactly one `SOURCE_BRANCH` and always fetch and check out fresh from `origin/<target>` before squashing — there was no way to test whether two *unmerged* branches compile together without hand-rolling the chained squash outside erun's own tooling, no matter how careful the caller was. That gap is what let #1893 pass its own single-branch gate while failing to compile against #1898 — a failure structurally invisible to one-branch-at-a-time gating. `erun-common/exec_gate_merge.go`'s `GateMergeWorkingTree` now takes an ordered `Sources` list (CLI: repeatable `--source`, paired with one NUL-separated commit message per source on stdin; MCP: `sources: [{branch, message}]`) and squashes each in turn onto **one** working tree — fetching every branch in a single `git fetch`, then one `git checkout -B <target>`, then one `git merge --squash` + `git commit` pair per source — instead of resetting from the target's remote tip on every call, which is what silently discarded every branch but the last when a caller looped single-source `gate-merge` calls by hand. A source whose squash conflicts is skipped: the working tree is reset (`git reset --hard HEAD`, not `git merge --abort` — `--squash` never records a `MERGE_HEAD` to abort) and the conflict recorded in the result's `skipped` list with the conflicted files, and the batch keeps going against the clean tree the reset left behind. A batch where every source lands nothing refuses rather than reporting success against an unchanged target. Which branches to batch and in what order stays caller policy, unchanged. Explicitly **not** resolved by this: how `acceptMerged`'s one-review-per-build verification (`gatedTargetTip` parentage, see above) would report `MERGED` for N reviews off a shared batch build — that needs its own design pass, not a rider on this one.
- **What a batch records in `gate_runs`: one run per batch, not N runs sharing a prospective sha.** `gate_runs` already models "one attempt to gate a prospective merge" (see "Gate Runs" below); a batch is structurally one such attempt — one working tree, one final tip — so one row matches the existing model exactly. N rows sharing the same `mergeCommit` would misrepresent a single attempt as N independent ones, and since a shared build's outcome is identical across all N rows by construction, the duplication adds write volume without adding a diagnostic bit: every one of the N rows would flip `PASSED`/`FAILED` together, and `erun gate list` would show N entries that are the same event N times. This needs **no `gate_runs` schema change**: an operator's "which change made this batch red" is answered by the batch's own composition — `GateMergeWorkingTreeResult`'s `landed` (branch, source commit, and the squash commit that landed it, in order) and `skipped` (branch, reason, conflicted files) — which the driver passing that gate run's `--log-ref` (or `logRef`) at a saved copy of the batch result is what makes readable later, the same convention `erun-merge-queue-drive` rung 4 already uses for a build-failure capture (`--log-ref` pointing at a saved `erun build --output json`, never the failure text inline). Bisecting *within* that composition to find the specific commit that broke the build stays the punted, explicitly out-of-scope operator/agent judgment call the next bullet already carves out — this decision only makes sure the composition needed to start that judgment call is actually recorded somewhere reachable from the gate run, not that erun does the bisection.
- **Classifying a build failure as a non-verdict deserves a shared classifier, not a new command (implemented).** `GateRunStatus.INCONCLUSIVE` already existed for exactly this ("a verdict must be distinguishable from a non-verdict," see "Gate Runs" below), but nothing classified *which* failures qualify — the skill's own guidance left "genuinely unknown" to the driver's judgment, and a real merge-queue session reported the identical ghcr.io TLS-handshake-timeout failure as a red verdict three times before this landed. `erun-common/gate_run_failure_classifier.go`'s `gateRunInconclusiveSignatures` enumerates erun's own infrastructure signatures — a TLS handshake timeout, a failed oauth token fetch, a failed source-metadata resolution, the three clauses of BuildKit's own composite error when a base image pull can't resolve at all — and `reclassifyKnownInfrastructureGateFailure` matches them against `--failing-step`/`--log-ref` text, plus `--log-ref`'s own file content when it resolves to a real, reasonably small local file rather than the freeform text/URL/job-id the flag also allows — `erun-merge-queue-drive`'s own rung 4 points `--log-ref` at a saved `erun build --output json` capture, a path, never the failure text inline, so reading that file is what makes the classifier fire on the exact flow it exists to protect. Both `RunGateRunStart` and `RunGateRunReport` call it before sending a caller-reported `FAILED`: a match is reported `INCONCLUSIVE` instead, traced unconditionally (not only under `--dry-run`) so the override is visible even to a caller that only checks the reported status. Keeping the signature list current stays shared maintenance rather than a per-caller decision, and retry-count policy on top of a classified non-verdict still stays caller-configurable — neither of those changed.
- **Bisecting a red batch by dropping the suspect branch stays operator/agent judgment.** There is no mechanical rule for "which branch is suspect" that generalizes correctly — it requires reading the actual failure and forming a hypothesis, the same as a human-driven `git bisect`. Not proposed as product surface.
- **Verified end to end against a real migrated Postgres and a real `erun-backend-api` handler, and two gaps found beyond the classifier's own diff, both closed.** Driving `RunGateRunStart`/`RunGateRunReport`/`RunGateRunList`/`RunGateRunShow` against a live server confirmed the core claim: a genuinely failing change persists `FAILED`, a build failure carrying one of the three known signatures persists `INCONCLUSIVE`, a green run persists `PASSED`, and `erun gate list`/`gate show` and their MCP twins (`gate_list`/`gate_show`/`exec_gate-run_start`/`exec_gate-run_report`) all render the classified status verbatim — a caller reading either transport's output, or its `--output json`, can tell the three apart. Two things the classifier's own diff did not reach:
  - **`erun build --output json` writes nothing to stdout on failure — the JSON body is only ever written on success (`erun-cli/cmd/build.go`'s `ctx.WriteResult` call is unreachable once `RunBuildExecution` returns an error), and the actual one-line failure reason (`DockerBuildStepError`'s "last words") goes to stderr via `logger.Fatal`.** `erun-merge-queue-drive`'s rung 4 redirected only stdout (`erun build --output json > file.json`) before capturing that file as `--log-ref`, so on the exact ghcr.io-TLS-timeout shape the classifier exists to catch, the captured file was empty and the classifier had nothing to match — the golden test added alongside the classifier (`gate_run_report_dry_run_failed_log_ref_file_classified_inconclusive`) synthesized a JSON file with the signature text inline, which is not what a real failed build ever produces, so it passed without exercising the real flow. Fixed by redirecting `2>&1` in the skill so the log-ref file actually carries the diagnostic text a real failure writes.
  - **The classifier only ever reached `gate_runs.status`, never `builds.successful`/the review's own status** — and the review's status, not the gate run, is what actually determines whether a review stays in the merge queue. `erun review record-build --gate --failed` (the call the skill's own rung 4 makes right alongside `gate-run report`, and the one that actually flips the review to `FAILED`) had no equivalent check, so a caller could correctly see `gate_runs` say `INCONCLUSIVE` while the review itself still read `FAILED` for the identical network blip — "distinguishable in one record, indistinguishable in the one that matters." `builds.successful`'s own boolean has no `INCONCLUSIVE` to report instead (the same constraint that made `gate_runs` a separate table in the first place — see above), so the fix is a refusal, not a silent reclassification: `ensureNotKnownInfrastructureGateBuildFailure` (`erun-common/gate_run_failure_classifier.go`) refuses `RunReviewRecordBuild` outright when `--gate --failed --failure-detail` matches a known signature, naming `exec gate-run report --status inconclusive` as the remedy and leaving the review at `MERGE` for a re-drive — the same "report gate-run inconclusive and don't record a build" pattern the skill already used for an unattested desktop-coverage refusal, just reached by a different trigger.

## Gate Runs

- A gate run (`GateRunService`, `GET`/`POST /v1/gate-runs`, `GET`/`PATCH /v1/gate-runs/{gate_run_id}`) is the first-class record of one attempt to gate a prospective merge, independent of whether an erun review exists for the change (erun#1931). A review-driven merge's `GATE` build is one producer of a gate run (the environment driving `erun-merge-queue-drive` reports both); a repository whose changes arrive as GitHub pull requests, with no erun review at all, is the other — the reason this is a table of its own rather than an extension of `reviews`/`builds`: forcing every gated branch to open a review would conflate a code-review workflow (assignments, comment threads) with a CI-verification concern that has no need for either, and `builds.successful` is a plain boolean with no way to represent "never reached a verdict" without a review's own FAILED transition firing on it.
- `GateRunStatus` is `RUNNING`, `PASSED`, `FAILED`, or `INCONCLUSIVE`. **A verdict must be distinguishable from a non-verdict**: a wrapper that hits its own timeout cap, or a run interrupted by an environment-specific fault (a network blip, a pod eviction), reports `INCONCLUSIVE`, never `FAILED` — `FAILED` asserts a real verdict was reached and a real gate step produced it. `Start` may be called already carrying a terminal status (`MergeCommit` empty, `FailingStep` set) for a run that never had a trackable "running" phase at all, such as a squash conflict before any build starts. This distinction used to depend entirely on driver judgment call by call — `INCONCLUSIVE` existed in the enum with nothing that ever set it automatically. `erun-common/gate_run_failure_classifier.go` now closes that: `RunGateRunStart`/`RunGateRunReport` reclassify a caller-reported `FAILED` as `INCONCLUSIVE` automatically when `FailingStep`/`LogRef` names one of erun's own known infrastructure signatures (see "What a hand-run merge-queue script should hand off to erun" above).
- A `FAILED` report must always carry `FailingStep` (which gate step produced the red verdict); `LogRef` is an optional pointer to where to read it. Neither is required for `INCONCLUSIVE`, since the whole point is that the gate itself never reached a real verdict to name a step for.
- `ReportOutcome` refuses reporting against a gate run that is not `RUNNING` (`*GateRunAlreadyDecidedError`, 409): a verdict is immutable once reached, so a caller cannot silently overwrite one gate run's outcome with another.
- `ReviewID` is nullable and, when set, links a gate run to the review it gates — but nothing here writes to `reviews`/`builds`, and nothing there writes to `gate_runs`; the two are independent records a caller may report to either or both of, not one driving the other.
- `GET /v1/gate-runs`/`GET /v1/gate-runs/{gate_run_id}` are classified normally now (erun#1932): a real operator surface reads them in both `erun-console` (`src/gateRuns/`) and `erun-ui/frontend` (the tenant dashboard's Gates tab). They are no longer in `route_audit.go`'s `InternalAPIRoutes` — that entry was a deliberate, temporary scope decision for #1931's CLI-first delivery, not a claim they needed no operator surface forever. `POST /v1/gate-runs` and `PATCH /v1/gate-runs/{gate_run_id}` are internal permanently: the environment driving the gate reports its own attempt, the same self-report shape as `POST /v1/reviews/{review_id}/builds`.

### GitHub branch protection cannot tell the queue's push from a bypass (#1912, reconciliation and the narrowing plan implemented; applying the ruleset edit is still ops work)

- **The queue's push is itself a direct push, so "no direct pushes" is the wrong rule.** `erun-merge-queue-drive`'s rung 6 (`erun exec push <target>`) pushes the squash commit `gate-merge` built straight to the target branch — no GitHub PR-merge API call, no `pull_request` rule satisfied. That is what makes the gate test the prospective merge onto the target's *current* tip rather than the source branch as the author left it (the property called out earlier in this section). The rule branch protection actually needs is "no direct push except one a green gate produced," and today the only thing separating those two cases is which credential pushed — verified live against `sophium/erun`'s ruleset (`rulesets/11081432`): every environment that can drive this queue, this repo's release automation, and any human collaborator with sufficient repository role all authenticate through the same shared credential, so a bypass by the queue and a bypass by a person look identical in the audit log.
- **A required-status-checks rule does not add real enforcement on top of a broad "always" bypass grant.** GitHub's ruleset bypass is per-actor and per-ruleset, not per-rule: an actor with `bypass_mode: "always"` skips every rule in the ruleset, `required_status_checks` included, regardless of whether anything ever reported a status. So layering a required check on top of the *current* bypass list (three broad `RepositoryRole` grants, all `bypass_mode: "always"` — confirm the exact role each numeric `actor_id` resolves to in the GitHub UI before changing anything; GitHub does not document the `RepositoryRole` id mapping and community reports of it disagree) changes nothing for holders of that bypass. The enforcement value of a dedicated, narrowly-granted identity is not "it can prove a status" — it is that only one nameable, non-human actor holds the bypass grant at all. That is the fix for what #1912 actually asks: **provision a dedicated, non-human queue identity (a machine account or GitHub App, not a human's credential) that is the only actor holding `bypass_mode: "always"` on the ruleset**, and move every environment that drives `erun-merge-queue-drive` to authenticate as it. `erun release`'s own tag/branch/`[skip ci]` pushes bypass the same ruleset tonight and are a *different* actor from the merge queue's gate-merge/push — the design must say explicitly whether release shares this identity or gets its own bypass grant; leaving it unstated re-breaks every release the moment the broad bypass is narrowed. Humans who need a genuine emergency lever can be moved to `bypass_mode: "pull_request"` instead of removing bypass outright — they still must open a PR first, so the escape hatch stays auditable rather than disappearing; `erun review queue override-advance` already covers the ordinary "unblock the queue" case through the queue itself, not through GitHub bypass at all.
- **`erun exec report-commit-status` (#1887) does not, as built, close this gap, and has never run against a real merge.** Its own doc comment is explicit about what it targets: "the status always targets the review's source-branch tip commit, never the local prospective squash-merge commit gate-merge produces: GitHub only evaluates a required check against a commit reachable from the open pull request." That is the shape for a repository merging through a plain GitHub pull request without erun's own hosted `MERGE`/`MERGED` review flow at all (see `erun-docs/docs/collaboration/merge-queue.md`'s "separate mechanism" callout) — not for gating this repository's own queue, which never asks GitHub to merge a PR and pushes a commit no open PR's head ever equals. `erun-merge-queue-drive` never calls it, and nothing else does either, so it has zero producers against a real `sophium/erun` merge. Requiring a status nothing produces would block every merge in this repository, including whichever PR lands the fix — do not add a `required_status_checks` rule before proving a producer end-to-end against a real gated merge. Separately, this repository's `pull_request` rule requires zero approving reviews and has no status-check requirement at all today, so a human collaborator can currently land an ungated change through the ordinary GitHub "Squash and merge" button with no bypass needed whatsoever — a real gap, but a different one from #1912's bypass-identity question, and closing it (if wanted) is exactly what reusing `report-commit-status` against real PR head commits would be for.
- **A bypass is structurally unavoidable for the `pull_request` rule as long as the queue pushes raw commits instead of merging through the GitHub API**, so "make every bypass reconcilable after the fact" (the issue's third option) is not a competing design — it is a complement worth keeping regardless of which identity holds the bypass grant, and it is now implemented: `erun exec reconcile-bypass` (`erun-common/reconcile_bypass.go`, mirrored as MCP tool `exec_reconcile-bypass`) reads GitHub's own rule-suites ledger (`GET .../rulesets/rule-suites?ref=...&rule_suite_result=bypass`, then each bypassed suite's own detail to confirm which ruleset's rule was actually bypassed — a suite's top-level `result` can be `bypass` because of a *different* ruleset on the same push, and the detail's `rule_evaluations[].rule_source.id` is the only place that distinction is visible) and cross-references each bypassed push's landed commit (`after_sha`) against `gate_runs` filtered to `PASSED` on the same target branch. A push with no matching `mergeCommit` is reported `UNRECONCILED` and the command exits non-zero — loud by construction, not by convention — so it is safe to run on a schedule and alert on a non-zero exit. It depends on nothing `report-commit-status` would fix (see the bullet above): it reads GitHub's ledger and erun's own `gate_runs`, never a required-status-check.
- **The exact edit is now resolved by a command, not written by hand, and two things previously recorded here were wrong.** `erun exec plan-ruleset-bypass` (`erun-common/ruleset_bypass_plan.go`, mirrored as MCP tool `exec_plan-ruleset-bypass`) reads the live ruleset and emits the payloads; the corrections it encodes:
  - **GitHub added `User` as a ruleset bypass actor type** (repository-level rulesets, via UI/REST/GraphQL, announced May 2026 and explicitly aimed at "a single person or service account"). So the identity does **not** have to be a GitHub App: a dedicated machine account added as a write collaborator can hold the sole `always` grant, which matters because erun's existing device-flow credential path authenticates such an account with **no new code at all**, whereas an App installation token expires hourly and nothing in erun mints one. `sophium/erun` is a *user-owned* repository (verified: `GET /users/sophium` is type `User`, three collaborators — one admin, two write), so there are no teams, no org admins and no custom roles to grant to in the first place; `User` or `Integration` are the only realistic options and `User` is the cheaper one.
  - **Demote the existing broad grants; do not remove them.** The previously-recorded edit ("remove the three `bypass_actors` entries") depends on knowing which role each undocumented `RepositoryRole` id names, and it removes the operator's emergency lever outright. Flipping those same three entries' `bypass_mode` from `always` to `pull_request` needs no id mapping whatsoever — whoever they are, they lose direct-push bypass and keep a lever that forces a pull request — which is why `plan-ruleset-bypass` demotes rather than deletes.
  - **Never plan `bypass_mode: "exempt"`** (a third mode GitHub has since added). An exempt actor's push skips enforcement *without being recorded as a bypass*, so it never appears in the rule-suites ledger `reconcile-bypass` reads: it would make the push invisible rather than accountable, defeating the reconciliation half. Stage 2 demotes an existing `exempt` actor for the same reason.
  - **The ordering is a two-stage edit for a reason.** Stage 1 adds the queue identity alongside today's actors (both paths open, so the queue is proven under the new identity while the old one still works); stage 2 demotes the rest. Applying stage 2 first is what leaves `main` with no working way in. Verification is per-identity and GitHub answers it directly: `GET /repos/{owner}/{repo}/rulesets/{id}`'s `current_user_can_bypass` field is scoped to the *asking token* (`always`/`pull_requests_only`/`never`), so running it as each identity is the read-back. `GET /repos/{owner}/{repo}/rules/branches/{branch}` is **not** actor-filtered and cannot substitute for it — verified live: it returned all three rules to a token whose `current_user_can_bypass` is `always`. `git push --dry-run` proves write access, not ruleset evaluation; do not present it as a bypass check.
  - The command refuses when GitHub omits `bypass_actors` from the ruleset response — it returns them only to a token with write access to the ruleset, and a `PUT` computed from a response without them would silently drop every actor the ruleset already has.
- **Still ops work, and still an explicit decision rather than something a code PR should make unilaterally:** provisioning the machine account, deciding whether `erun release` shares it (its own tag/branch/`[skip ci]` pushes bypass the same ruleset and break the moment the broad grant is demoted unless they authenticate as a granted identity), authenticating the environments that drive `erun-merge-queue-drive`/`erun release` as it, running one real gated merge under it between the two stages, and applying the two `PUT`s. `erun exec plan-ruleset-bypass --ruleset-id 11081432 --target-branch main --queue-actor <login>` emits them; `erun exec reconcile-bypass --ruleset-id 11081432 --target-branch main --expected-actor <login>` is the read-back afterwards. Whether to add a `required_status_checks` rule remains a separate decision that must wait for a proven producer (see the `report-commit-status` bullet above) — nothing in this plan depends on one.
- **`reconcile-bypass` was verified against the live configuration and had two real defects, both fixed.** The ledger filter is correct as built (confirmed independently against `sophium/erun`'s own ruleset: a bypassed suite's detail carries `rule_source.type: "ruleset"`, its `id`, and `result: "fail"` for the `pull_request` rule, exactly what `bypassedRuleForRuleset` matches). What was wrong:
  - **It reconciled only the push's tip commit, so every release this repository has ever cut read as `UNRECONCILED`.** A release push moves the branch by three commits — the tagged release commit, the packaging-checksum sync, and the next version's stamp — and its `after_sha` is the last of them, which no gate run ever built. Two such pushes sit in the live ledger (`41377065`, `ef5cdfe8`). So the claim that the command is "safe to run on a schedule and alert on a non-zero exit" was false: it was already guaranteed to be red. It now expands each unmatched push's range (`GET .../compare/{before}...{after}`) and reports a push carrying a tagged commit as `RELEASE` rather than unaccounted-for. A release is not a gated merge and is deliberately not reported as one.
  - **It ignored the actor entirely**, so it could not detect the one failure the narrowing above exists to prevent. `--expected-actor` (repeatable) reports any other identity's bypass as `UNEXPECTED_ACTOR` even when a gate run covers the content, which is what makes the narrowed grant observable rather than merely configured.

### An agent environment cannot provision a platform cloud alias (#1969, design recorded; not yet implemented)

- **The gap is one credential, not one command.** Every step of `erun-merge-queue-drive` that touches the platform (`erun review show`, `record-build --gate`, `exec gate-run start/report`, `report-merged`) resolves through `newPlatformClientForAlias` (`erun-common/platform_commands.go:55`), which needs a configured erun-type cloud alias with a usable token. `erunCloudProviderLogin` (`erun-common/cloud_erun.go`) has exactly two grants today — OIDC device authorization and Authorization Code + PKCE — and both need a human with a browser. An agent pod, however long-lived, never acquires one on its own, so any environment the queue promotes can fail to self-report at exactly the moment the design assumes it will.
- **The fix is not a new trust anchor — erun-backend-api's bearer model is already issuer-generic, and that was verified rather than assumed.** `CloudProviderBearerToken` (`erun-common/cloud.go:495`) already mints a *non-Zitadel* platform bearer for an AWS-provider alias (`awsCloudProviderBearerToken`, AWS STS's outbound web-identity-token federation) — `PlatformClient.WithUsernameHint`'s own doc comment says as much: "a caller whose token carries no username claim — an AWS STS bearer, for one — still gets a readable identity." So erun-backend-api already accepts more than one issuer type for the same tenant, minted per call rather than cached (mirroring the MCP bearer's own per-call-mint principle, `erun-common/mcp_identity.go`'s `DesktopMCPTokenTTL` comment: "callers mint per request rather than holding one"). That rules out the third direction as *new backend surface*: a brand-new self-signed Ed25519 trust anchor (mirroring `mcp_auth.go` exactly, but for outbound platform calls) would require erun-backend-api to accept a wholly new verification scheme; the AWS precedent proves the existing scheme already generalizes to a second issuer without one.
- **Recommendation: a Zitadel machine user (client-credentials grant), not a new issuer type, not a self-signed scheme.** A Zitadel *machine user* under the tenant's own already-registered org authenticates via `grant_type=client_credentials` — no browser, no device code, purely programmatic — and is verified by erun-backend-api through the exact same OIDC-bearer path a human's token takes today: same issuer, same `(issuer, subject)` identity resolution, same role/capability model. This is cheaper than the AWS path above (no second issuer to register, no dependency on the tenant's own cluster having internet-reachable OIDC discovery — a real blocker for a `local-agent` cluster with no public endpoint at all) and needs no change to `erun-backend-api`'s authentication code, only to its Zitadel management client (`internal/zitadel/client.go`, which already does `CreateOrg`/`CreateHumanUser`/`DeactivateUser` against the same org — a machine-user create + secret mint is the same shape of call, not a new integration).
- **Scope: a new narrow role, not `TenantUser`.** `erun-merge-queue-drive`'s platform calls resolve to exactly five routes, all `TenantUserClass` today: `GET /v1/reviews/{review_id}`, `POST /v1/reviews/{review_id}/builds`, `POST /v1/gate-runs`, `PATCH /v1/gate-runs/{gate_run_id}`, `PATCH /v1/reviews/{review_id}/status`. `TenantUser` also grants `POST /v1/environments/{environment_id}/deploy`/`stop`, minting an MCP admin token for *any* environment (`POST .../mcp-token`), and reads across users/invites/roles/contexts — none of which the queue needs, all of which a compromised pod holding this credential would otherwise get for free. The identity this design provisions should hold a purpose-built role scoped to only those five routes (`RoleRepository.Create` already accepts an exact method/path permission list — no schema change, no new predefined-role plumbing in `routeroles.go` required), granting exactly the surface the queue drives and nothing an admin action would need.
- **Provisioning has to happen server-side, at bootstrap, not through the public API — otherwise this is the same chicken-and-egg problem again.** Creating a role or granting one is itself a `TenantAdminOnly` call; asking a fresh pod to authenticate as a human just to provision its own non-human credential defeats the design. The precedent already in this codebase for exactly this shape is per-tenant first-user bootstrap (`IdentityRepository.insertTenantFirstUserAccess`) — server-side code inside the API process, not an external caller, granting access with no pre-existing privilege. An equivalent idempotent `ensureMergeQueueIdentityExists(tenantID)` — create the narrow role if missing, create the Zitadel machine user and mint its secret if missing, insert the corresponding `users` row and grant the role if missing — belongs beside that bootstrap, invoked the first time any agent-capable environment is provisioned for a tenant. One identity per tenant, shared across every environment it drives the queue from (the same "one shared identity, isolation by scope rather than one-per-instance" pattern the desktop/hosted-backend MCP signer identity already uses), not one Zitadel object minted and torn down per pod.
- **Delivery reuses the channel that already works, because it was proven to reach agent pods for other secrets.** `deploy.go`'s `applyMCPAuthSecret` already ships a signing key into every environment's pod as a Kubernetes Secret at deploy time; the client id + secret from the bootstrap above ships the same way. No new reachability assumption: this is push, over the exact connection `erun deploy` already uses to get any config into the pod, not a pull that depends on the tenant's own cluster being reachable from erun-backend-api (the AWS-federation and any Kubernetes-ServiceAccount-token-federation alternative both fail that reachability test for a private `local-agent` cluster, e.g. `erun-setup-k3s-cluster`'s WSL2 k3s with no public endpoint — a real blocker checked, not assumed away).
- **Closing the loop means the pod bootstraps itself, not that an operator or agent runs `cloud login`.** The runtime entrypoint (or `erun doctor --sync-config`, which already seeds `ERUN_CLOUD_PROVIDER*` env vars into the pod's local config the same way — `erun-common/doctor_sync_config.go`) needs to detect the injected client id/secret and run `cloud init erun --api-url <injected>` plus a new non-interactive login grant automatically on pod start, with zero commands issued by a human or an agent. `erunCloudProviderLogin`/`resolveERunAccessToken` (`erun-common/cloud_erun.go`) need a third flow alongside device and authcode+PKCE — `client_credentials`, selected automatically when the alias's stored config carries a client-secret reference instead of a refresh-token ref — minting a fresh short-lived access token per call rather than caching one, the same discipline `DesktopMCPTokenTTL` already applies. Until that flow exists and the pod's bootstrap runs it unattended, the gap is a design, not a fix.
- **Relationship to #1912: same conceptual actor, two separate credentials — do not conflate them.** #1912 wants a dedicated non-human identity so GitHub's ruleset bypass warning means something; this issue wants a dedicated non-human identity so the queue can report its own gate runs at all. They should read as the *same actor* in both audit trails — name the Zitadel machine user and the GitHub machine account the same way (e.g. `erun-merge-queue`) so `reconcile-bypass --expected-actor` and erun-backend-api's own audit/build records tell a coherent story — but they are credentials in two unrelated trust domains (a Zitadel-issued OIDC bearer for erun-backend-api; a GitHub account credential for `git push`) and must never share one literal secret. Whether `erun release`'s own tag/branch pushes share this identity is #1912's open question, not this one's; this design does not extend to release's platform-API calls without checking whether they need the same narrow role or a distinct one.

## Cloud-Provider-Alias Storage: A Nil-Cipher Route Must Refuse, Not Vanish (erun#2042 follow-up)

- **A route unregistered because an optional dependency is nil, and a route that reports a clear 501 for the same reason, look identical in the source but are opposite in operation.** `PUT /v1/cloud-provider-aliases/{alias}` — the route `erun-console`'s `ProvisionPanel` (`src/provision/`, see `erun-console/AGENTS.md`) uses to register BYO-cloud credentials — used to be registered only inside `if options.Cipher != nil` in `server.go`. `options.Cipher` comes from `ERUN_SECRETS_KEY`, which **no chart in `erun-devops/` sets today**, so every real deployment of this API runs with `Cipher == nil` and the route was never registered at all: a request 404'd with the mux's own generic "not found," and the console rendered that as an undiagnosable "Could not save credentials: alias request failed (404)". This was found by actually driving the console's `ProvisionPanel` against a real, unmodified `eapi` binary (`erun-console/playwright/tests/rest-surfaces.spec.ts`) rather than by reading the code — the mocked-`fetch` unit test (`ProvisionPanel.test.tsx`) supplies its own response and so could never have caught a route that the real server never registers.
- **The fix: always register the route; refuse inside the handler when unconfigured.** `RegisterCloudProviderAliasRoutes(register, aliases)` now runs unconditionally with a possibly-nil `routes.CloudProviderAliasWriter`; `setAlias` checks `r.aliases == nil` first and reports `501` with a named, actionable message ("cloud provider alias storage is not configured (ERUN_SECRETS_KEY is unset)") — the same pattern `mintMCPToken` already uses for a nil MCP signer. This makes the failure diagnosable; it does not make the feature usable.
- **What still has to happen for the feature to actually work in production: `ERUN_SECRETS_KEY` needs to be provisioned into a deployed `erun-backend-api`, and nothing in this pass does that.** That is a devops/chart-side change (generating and delivering a real 32-byte key as a Kubernetes Secret, the same shape `deploy.go`'s `applyMCPAuthSecret` already uses for the MCP signing key) — out of scope for this console-focused pass, and named here rather than left to be rediscovered as a second "silent 404" investigation. Until it lands, every real tenant's `ProvisionPanel` will render the new, clearer 501 instead of the old opaque 404 — a real improvement, but not the same as the credentials actually saving.
