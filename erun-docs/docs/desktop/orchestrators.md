# Orchestrators

Above your environments, the sidebar's **ERUN** section lists your host-side orchestrators — AI sessions that coordinate work across the environments you link to them. For a remote-agent or local-agent environment that means reviewing its code on your machine and delegating every change to the Agent inside it; for a **host** environment it means working in that environment's directory directly, since a host environment is a plain directory with no pod and therefore no Agent in there to delegate to and nothing that syncs over your edits; for a runtime environment, linked with the **Runtime** role below, it means operating that environment directly instead. Open an orchestrator's **…** menu to manage it: restart, delete, or reveal the guidance it operates under.

**Orchestrator details on hover.** Hover a running orchestrator's row to see what it's doing and, for each linked environment, its own state rather than just its name: busy (naming the holder when it's known), idle, in outage, or not open from this desktop, plus its usage figure and age when one has been read — the same activity and usage this environment's own hover card reports, so the two can never disagree. A **Nudges** line reports whether ERun has had to restate its pacing contract to a quiet session, how many times, and whether it has stopped nudging after repeated attempts — a capped session needs your reply or a restart, since ERun has stopped acting on its behalf. A session ERun did not start — one you launched in a terminal, or one an earlier ERun window left running — is shown here too, and its **Nudges** line says **Not paced from this desktop**: ERun can only restate the contract into a pane it owns, so that session is running without that safety net. The line names this desktop rather than the session on purpose, since the session itself may be perfectly healthy and paced from somewhere else.

**Whip: push everything by hand.** The titlebar carries a whip button (beside the theme toggle) that runs the same pacing pass immediately, across every live orchestrator *and* every environment's own AI session — not only the ones that have gone quiet long enough for the automatic pass to notice on its own. Clicking it opens a report naming every target: **Pushed**, **Capped** (already at the automatic pass's consecutive-nudge limit — reply in its pane or restart it), **Failed** (a push was attempted and refused — the report names the error), or **Skipped**, with the reason (not alive — no live session to push, for example). Whip never restarts or interrupts anything, so it needs no confirmation and is safe to click at any time. See [`erun whip`](/cli/whip) for the same pass from the CLI, and [pacing](/agent-reference/skills-spec#periodic-pacing-re-statement-and-crash-auto-resume) for the message text and cap semantics both share.

**Editing a running orchestrator's environments takes a restart to apply.** Its session already holds the AI tooling for the environments it started with, and that can't be swapped out from under it — so saving a different set in **Manage** doesn't touch a session that's already running. The row's status dot and the hover card both say so ("Restart to apply") until you do, and the manage dialog carries the same **Restart** action right there, next to the reason. Editing a stopped orchestrator needs no restart: its next start already picks up the new set.

**Role, per linked environment.** Beside each checked environment's directory field, a **Role** control says what this orchestrator uses that environment for: **Code** (writes code, iterates fast, not sized for a full regression run), **Build** (checks out pushed branches, runs the gates, cuts releases), **Runtime** (operates the environment directly — deploy, pin, observe), or **Not declared** — the default, and never silently coerced to any of the other three. The control shows only for a checked environment, and a line beside it states what the selected value means. Role is independent of the environment's own type: a remote-agent or local-agent environment accepts any of the four values, a **host** environment any but Runtime — that role means deploy, pin, and observe, and a host environment has no pod for any of them to act on, so the dialog does not offer it there — while a runtime environment accepts only the Runtime role, the dialog offering just that one choice since it has no worktree to review and no in-pod agent to delegate to, and so carries no directory field at all. Changing a role while the orchestrator is running carries the same restart-to-apply notice as changing the linked environment set, so the dialog never implies an edit took effect before you've confirmed it did. `erun orchestrator set-role` (see [CLI · `erun orchestrator`](/cli/orchestrator)) sets the same field from the terminal, so `config.yaml` is never the only writer.

**Platform alias.** Below the name, a **Platform alias** control says which erun platform alias this orchestrator declares as its own — the orchestrator-scoped counterpart of a tenant's own cloud alias. **This machine's own alias** is the default and means it declares none of its own. The list offers only the erun-type aliases this machine has configured, because the value is a *selection* among them and never a credential: nothing here creates an alias or signs you in to one, and a name this machine cannot resolve is refused rather than saved. When no erun alias is configured on the machine at all, the control says so instead of offering an empty choice. `erun orchestrator set-alias` (see [CLI · `erun orchestrator`](/cli/orchestrator)) sets the same field from the terminal, and [`erun list`](/cli/list) prints it back. A value written from the terminal survives an edit made here, including one that changes something else entirely. **The control records a declaration and nothing more today:** an orchestrator resolves this machine's own alias regardless of what is selected here, and per-environment aliases are not implemented — see [Configuration · `ERunConfig`](/reference/configuration#erunconfig) for the current behavior and [erun#2684](https://github.com/sophium/erun/issues/2684) for the work that will change it.

**Launch settings: Use gateway, Model, and Effort.** Three controls decide how the orchestrator's own Claude session starts. **Use gateway** is off by default, which keeps the session on this machine's own Claude Code configuration exactly as before; turned on, it routes the session through the same gateway catalog your environments use, maintained once in the desktop's **ERun settings**. It is a choice per orchestrator — having a catalog does not move an orchestrator onto it — and it needs both halves of that setup: a catalog, without which turning it on is refused when you save, and the gateway's key, without which the orchestrator refuses to start and tells you to save the key in ERun settings. **Model** defaults to `opus`, or through the gateway to the catalog's default model (still `opus` when the catalog lists none); a model the gateway cannot drive is refused while the gateway is on. **Effort** defaults to `ultracode` and otherwise takes `low`, `medium`, `high`, `xhigh`, or `max`. A transient Investigate session always starts on these defaults. Like the linked environments, these are read when the session starts, so changing any of them on a running orchestrator shows the same "Restart to apply" notice until you restart it. One thing the dialog does not control: Claude Code applies the `env` block of this machine's own Claude Code settings to every session itself, so a gateway configured there still reaches an orchestrator whose **Use gateway** is off. `erun orchestrator set-gateway`, `set-model`, and `set-effort` (see [CLI · `erun orchestrator`](/cli/orchestrator#launch-settings)) set the same fields from the terminal, [`erun list`](/cli/list) prints them back, and [Configuration · `ERunConfig`](/reference/configuration#erunconfig) lists the fields themselves.

Each orchestrator runs under two layers of guidance, and the dialog opens either one in your editor (VS Code or IntelliJ):

- **Role** — what this orchestrator does. Yours to edit; ERun creates it once and never overwrites it.
- **Shared contract** — the rules every orchestrator follows. ERun-managed and rewritten on every launch, so edits here don't stick.

For the exact files behind these two layers and how they're injected into a session, see [Agent reference · Skills spec](/agent-reference/skills-spec#host-orchestrator-desktop).

**Provisioning also mints the orchestrator's claim label.** The first launch of a new orchestrator creates its `wip:<id>` label on the ERun repository, carrying the same colour and description as every other orchestrator's, which is what lets the claim protocol in the `erun-orchestrate` skill — adding that label to an issue before working it — run as written rather than being rejected for a label that does not exist. A label that is already there is left exactly as it is, and a label ERun cannot read or create is reported in the app's log without holding up the launch.

**Your own directories.** An orchestrator can also be pointed at directories that belong to no environment at all — a scratch checkout, a folder of notes, a second copy of a repo you build natively. They carry no tenant, no runtime version or image, and no role, because none of those describe a path with no pod behind it: nothing is registered for one, no deploy applies, and nothing else owns it, so the orchestrator authors and builds in it directly, exactly as it does in a host environment's own directory. **Add directory…** opens a folder picker, and each row carries its own remove control. A directory is a complete definition on its own: an orchestrator that names only directories and links no environment at all is valid, which is what makes this the way to point an orchestrator at a path without registering an environment for it first. Unlike the linked environments, changing them raises no restart notice — nothing a session resolved at launch is keyed on a directory, so the change is picked up the next time the orchestrator reads its own definition.

## The conversation an orchestrator comes back to {#orchestrator-conversations}

Each orchestrator runs as a Claude Code **background agent** named after the orchestrator — an orchestrator with id `erun` is the agent `erun` in `claude agents`. The orchestrator's pane is a window onto that agent, not the agent itself, so the agent keeps its own conversation whatever happens to the pane: a `/clear` or a compaction moves the agent onto its next conversation, and the pane follows it, because opening the orchestrator always attaches to the agent rather than naming a conversation for it to resume.

What that means in practice:

- **Opening** an orchestrator attaches to its agent, and creates the agent the first time. A stopped agent starts again on its latest conversation — after a reboot too.
- **Quitting or restarting the desktop** leaves every agent running, mid-turn included. The next desktop reattaches each orchestrator that was open. A rebuild-and-restart therefore no longer interrupts the orchestrator that asked for it.
- **Closing an orchestrator's tab** stops its agent. Its conversation is kept, and the next open starts the agent again on it.
- **Restart** stops the agent and starts it again on the orchestrator's current settings, on the same conversation.
- **Deleting** an orchestrator removes its agent too. The conversation's transcript is Claude Code's and is not deleted.

**Settings a restart cannot apply are applied by recreating the agent.** Model, gateway and every effort except `max` reach the agent on its next restart. Moving effort to or from `max` — and an agent of the orchestrator's name that ERun did not create, such as one you started by hand with `claude --bg -n erun` — needs the agent recreated: ERun says so in a notification, removes the old agent, and starts a new one on the same conversation.

**When ERun cannot tell which agent is the orchestrator's, it asks you rather than guessing.** Claude Code allows two agents with the same name; when it finds more than one named after an orchestrator, opening it is refused with each agent's id, and `claude rm <id>` on the ones that are not yours settles it.

**The orchestrators folder has to be trusted once.** Claude Code will not start a background agent in a folder nobody has trusted. If opening an orchestrator reports that the orchestrators folder is not trusted, run `claude` once in that folder (`~/orchestrators`), accept the trust prompt, exit, and open the orchestrator again.

An orchestrator created before this release continues the conversation it was on: its first agent resumes the conversation you had attached to it, or else the one derived from its id.
