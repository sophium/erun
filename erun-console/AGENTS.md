# AGENTS.md

Module-specific guidance for `erun-console`. Follow the repository root `AGENTS.md` first, then apply this file for work in this subtree.

## Module role

- `erun-console` is the **hosted web console** for erunpaas (issue #606): a browser SPA served at `console.<base-domain>` where an Operator signs in and views their tenant's erun config. It is a **separate app from `erun-ui`** (the Wails desktop app): the desktop is the _local_ control plane and talks to a Go backend over Wails IPC; the console is the _hosted_ control plane and talks to a backend over HTTP.
- **Architecture (decided).** The console calls **erun-backend-api directly** — that service already carries the OIDC/JWKS auth middleware, the tenant boundary, and `GET /v1/config`. There is **no separate BFF service** in this increment. Keep the console a thin read/render layer over the API contract; shared tenant/environment resolution stays in `erun-common` and is exposed to the console only through the API.
- The console does **not** import `erun-ui/frontend` and must not modify it. Component reuse with the desktop happens through the shared `erun-kit` workspace package (issue #1211) — never by importing across the two app boundaries directly. See `erun-kit/AGENTS.md` for what lives there and how to consume it.
- **The console has an app shell (issue #1207).** `src/shell/` is a persistent sidebar (navigation) + header (identity, sign-out, theme) + a main pane that switches on one derived section id — not every panel stacked and scrolling. It is console-owned (not moved into `erun-kit`: it composes kit widgets and shadcn primitives with console-specific navigation, not a generic widget another app would import), built entirely from `erun-kit`'s tokens, shadcn primitives, and generic widgets. See Layout below.
- **Installable as an independent PaaS instance (#603/#606): hardcode no instance-specific names.** The API base, brand, and OIDC issuer are configuration (Vite env / runtime config), never literals in source. `erunpaas.com` / `console.erunpaas.com` are one instance's values, shown as examples.

## What is verifiable here vs. what is a flagged placeholder

This module's verifiable value-prop in its first increment is the **read view**: `GET /v1/config` → `{ tenant, environments[], contexts[] }` rendered for an Operator, proven by a component test against a **mocked** API (`src/config/ConfigView.test.tsx`).

**OIDC sign-in is no longer a placeholder.** `src/auth/auth.ts` implements the real Authorization Code + PKCE flow against `VITE_OIDC_ISSUER` / `VITE_OIDC_CLIENT_ID`, and it is verified two ways: `src/auth/auth.test.ts` locks the PKCE mechanics against mocked discovery/token endpoints, and `playwright/` drives the whole browser sign-in against a **real Zitadel v4** through to the rendered tenant config (see `playwright/AGENTS.md`). `VITE_DEV_BEARER_TOKEN` remains as the fallback when OIDC is unconfigured — a local-dev path only.

**Driving each env's per-env MCP is now real, with one disclosed gap.** Minting a per-env MCP bearer token (`src/mcp/`, the backend signs it so the browser holds no key) and _using_ that token to call a tool over the live edge (`src/mcp/liveClient.ts`) are both implemented: `liveClient.ts` speaks the edge's own JSON-RPC wire protocol directly from the browser (`initialize` → `notifications/initialized` → `tools/call`, per `erun-mcp/AGENTS.md`'s documented sequence), and `erun-mcp/server.go`'s `corsMiddleware` unblocks the cross-origin call a browser would otherwise refuse before it ever reaches the edge. Verified two ways: `MCPAccessPanel.test.tsx`/`liveClient.test.ts` exercise the full mint → drive → result flow against a mocked `fetch`, and the exact request sequence was additionally run from a Node script against a real, unmodified, currently-deployed `emcp` process (not a mock) to confirm the wire protocol interops byte-for-byte.

**Attaching to a live session from the browser is now real too (issue #1692).** `src/mcp/attachClient.ts` speaks `erun-mcp/attach.go`'s WebSocket wire protocol (binary PTY bytes both ways, `resize`/`outcome` JSON control frames) and authenticates via the `Sec-WebSocket-Protocol` offer (`erun.bearer.v1`, then the token) rather than an `Authorization` header — the one credential channel a browser's `WebSocket` constructor actually exposes; `erun-mcp/auth.go`'s `wsAttachAuthHTTPMiddleware` is the server-side half of that fallback. `controller.ts`'s `useAttachSessionController` owns the whole mint (`erun:attach` scope, never `erun:admin`) → connect → drive lifecycle, rendered by `MCPAccessPanel.tsx`'s `AttachSessionForm`. This is deliberately a minimal, line-based view (a scrollback `<pre>` plus a line-at-a-time input), not a full terminal emulator — an xterm.js-based view is a follow-up once `erun-kit` carries a shared terminal widget, matching `erun-ui/frontend`'s own usage. The session id (which dtach socket to attach to) is operator-supplied, the same disclosed-gap shape as the MCP hostname above: nothing resolves it automatically yet. Verified against a mocked `WebSocket` (`attachClient.test.ts`, `MCPAccessPanel.test.tsx`); not yet run against a real browser + real deployed edge together, the same caveat the live-edge paragraph above already carries for cross-origin `fetch`.

The disclosed gap: the environment's MCP hostname (`mcp.<tenant>-<env>.<services-zone>`) is **operator-supplied**, not auto-discovered — exposing the `mcp` service is a manual `erun expose <tenant> <env> mcp` step for most environment types today (nothing in `erun-backend-api` persists or returns an exposed hostname), so the console has no reliable way to resolve it on its own yet. And no real browser, real public TLS hostname, and real cross-origin round trip has been exercised together in one live test — the mocked-`fetch` tests and the real-server wire-protocol check above are the two closest approximations available without a services zone / ingress standing in front of a real deployed environment. When a services zone becomes available for a verification pass (or the hostname becomes discoverable), extend the verification to a real cross-origin browser call and consider resolving the hostname automatically instead of asking the operator to paste it.

## Layout

- `src/shell/` — the app shell (issue #1207): `AppShell.tsx` composes `ConsoleSidebar.tsx` (navigation; `sections.ts` derives the section list from `tenant.type`, gating the identity sections the same way `App.tsx` used to) and `ConsoleHeader.tsx` (section title, identity, `ThemeToggle.tsx`/`useTheme.ts`/`theme.ts` for the class-based dark mode, sign-out) around a main pane that renders exactly one panel for the single derived `active` section id. `PreShellScreens.tsx` + `CenteredCard.tsx` + `BrandMark.tsx` are the pre-sign-in screens (loading, sign-in, not-enrolled, error) — a branded card using the platform's `brand` from discovery instead of the bare paragraph the console used to show. `TenantSwitcher.tsx` sits above `ConsoleSidebar`'s nav (issue #1614): a plain label naming the active tenant when `GET /v1/tenants/reachable` reports only one (or no OIDC config is available to switch through), a real `SelectField` control once it reports more than one. Picking another tenant is never a client-side re-scope — tenant resolution is a pure function of the token — so it records the intended target (`tenantSwitch.ts`, one-shot `sessionStorage`) and relaunches OIDC sign-in with `prompt=select_account` (`auth/auth.ts`'s `beginLogin`). `App.tsx` consumes that intent once the post-redirect config resolves and, if the new token landed on a different tenant than requested, renders `TenantSwitchMismatchBanner.tsx` rather than silently proceeding — the console never claims a switch succeeded that the API disagrees with.
- `src/app/` — the Redux Toolkit + RTK Query data layer (erun#1283), mirroring `erun-ui/frontend/src/app/`'s idiom: `store.ts` (`createAppStore` factory + the `store` singleton — a factory rather than a bare export so tests can build an isolated store per render), `hooks.ts` (`useAppSelector`/`useAppDispatch`), `authThunks.ts` (the OIDC + token resolution lifecycle), `queryError.ts` (reads a message/status out of whatever shape a query/mutation rejected with), `slices/authSlice.ts`, and `api/` — one `platformApi` (`api/platformApi.ts`, real `httpBaseQuery` in `api/httpBaseQuery.ts`) with per-domain endpoint files injected into it: `configApi.ts` (injects erun-kit's shared `buildPlatformConfigEndpoints` — see `erun-kit/AGENTS.md`), `environmentsApi.ts`, `contextsApi.ts`, `mcpApi.ts`, `identityApi.ts`. A write mutation that changes what `getConfig` reads (register/deploy an environment, provision a context) invalidates the shared `'Config'` tag so the read view refetches without an explicit `onChanged` plumbed by hand.
- `src/config/` — `ConfigView.tsx` renders the tenant header, environments table, and the contexts list with empty states and a per-context and per-environment provisioning status badge, reading `Tenant`/`Environment`/`CloudContext`/`TenantConfigView` from `erun-kit` (moved there in erun#1283 — it's erun-backend-api's own wire contract, not a console-only concept). `platform.ts` remains the one hand-rolled `fetch` in this module: `GET /v1/platform` resolves before any token exists, so it predates the store and stays a plain async function rather than an RTK Query endpoint.
- `src/provision/` — the cloud-context provisioning surface (issue #605/#676): `controller.ts` is a thin adapter over `contextsApi`'s mutations/query (register a BYO-cloud alias, `POST /v1/contexts`, then poll `GET /v1/contexts/{id}` via `dispatch(contextsApi.endpoints.getContext.initiate(...))` to `running`/`failed`) that keeps the pre-Redux `useProvisionController` return shape so `ProvisionPanel.tsx` did not need to change. **Verifiable**, not a placeholder: `ProvisionPanel.test.tsx` exercises the alias PUT and the create→poll flow against a mocked `fetch` (RTK Query's `httpBaseQuery` calls the same global `fetch`, so the existing mock-at-the-boundary tests needed no rewrite beyond wrapping `render` in a store `Provider` — see `test/renderWithStore.tsx`). The live OIDC token still comes from the dev stub — only the auth flow is flagged.
- `src/mcp/` — the per-env MCP access surface (issue #686, extended by #1692): `controller.ts`'s `useMcpTokenController` adapts `mcpApi`'s `useRequestMcpTokenMutation` to mint a token at a given scope (defaults to `erun:admin`); `useMcpToolCallController` adapts `liveClient.ts`'s `callMcpTool` to actually drive one against the operator-supplied MCP hostname; `useAttachSessionController` owns the mint-at-`erun:attach`-then-connect lifecycle for `attachClient.ts`'s live WebSocket session. `liveClient.ts` is the browser-side JSON-RPC client for the live edge, `attachClient.ts` the browser-side WebSocket client for the attach edge — see "What is verifiable here" above for what each does and how it's verified. **Verifiable**, not a placeholder: `MCPAccessPanel.test.tsx` exercises the mint, the 501 (unconfigured backend), the drive-a-tool flow, and the attach flow (mint → connect → scrollback → outcome) against mocked `fetch`/`WebSocket`; `liveClient.test.ts` and `attachClient.test.ts` exercise their respective wire protocols in isolation.
- `src/identity/` — the IdP-identity administration surface (issue #1209): `controller.ts` adapts `identityApi`'s query/mutations (`useListIdentityUsersQuery`, `useCreateIdentityUserMutation`, `useSetIdentityUserActiveMutation`, `useGetOrgSettingsQuery`, `useUpdateOrgSettingsMutation`) behind the pre-Redux `useUsersController`/`useOrgSettingsController` shapes; `UsersPanel.tsx` and `OrgSettingsPanel.tsx` are unchanged. Enrolling or (de)activating a user invalidates the `'IdentityUsers'` tag instead of the controller calling `refresh()` by hand. Both panels have a nav entry, and are reachable, only when `config.tenant.type === 'OPERATIONS'` (`shell/sections.ts`), mirroring the backend's own restriction — a `COMPANY`-tenant Operator never sees the nav entries, let alone the forms. **The IdP credential (Zitadel's org-owner PAT) is backend-only**: the console only ever calls erun-backend-api, never Zitadel directly. **Verifiable**, not a placeholder: `UsersPanel.test.tsx`/`OrgSettingsPanel.test.tsx` exercise list/enroll/deactivate/reactivate and get/update against a mocked `fetch`.
- `src/tenants/` — the tenant-registration surface (issue #1601): `controller.ts` adapts `tenantsApi`'s `useListTenantsQuery`/`useCreateTenantMutation` behind `useTenantsController`, classifying a `POST /v1/tenants` validation failure to the one field its message names (`classifyTenantFieldError`, since the API reports no structured field-level error shape) so `TenantsPanel.tsx` can render it against that control instead of a bare status. Reachable, and rendered, only when `config.tenant.type === 'OPERATIONS'` (`shell/sections.ts`), the same restriction `src/identity/` uses — a `COMPANY`-tenant Operator never sees the nav entry. **Verifiable**, not a placeholder: `TenantsPanel.test.tsx` exercises list/create, field-scoped validation errors, and the general-failure fallback against a mocked `fetch`; `shell/AppShell.test.tsx` asserts the nav-visibility split.
- `src/auth/` — the OIDC Authorization Code + PKCE sign-in (`oidcConfig` / `beginLogin` / `completeLogin` / `resolveToken` / `signOut`) and the dev-token fallback, plus the note on the still-deferred env-MCP driving (see above). `app/authThunks.ts` is the only caller of `resolveOidcConfig`/`resolveToken` now; components call `beginLogin`/`signOut` directly (they have no state of their own to update).
- `playwright/` — a **separate yarn package** holding the real-Zitadel browser sign-in e2e. Opt-in behind `ERUN_E2E_CONSOLE_OIDC=1`; `playwright/run.sh` is what sets it, after standing up Zitadel + a migrated API + the console. See `playwright/AGENTS.md`.
- `src/App.tsx` — dispatches `resolveAuth()` once on mount, reads the auth slice + `useGetConfigQuery`, and combines them into the same `LoadState` union (loading / signed-out (401) / not-enrolled / error / ready) the pre-Redux version rendered, rendering one of `shell/PreShellScreens.tsx`'s pre-sign-in screens or `shell/AppShell.tsx` once a token has produced a rendered config.
- `src/test/setup.ts` — Testing Library jest-dom matchers for vitest. `src/test/renderWithStore.tsx` wraps Testing Library's `render` in a fresh `Provider store={createAppStore()}` per call — every panel now reads through the store, and reusing one store across tests would let RTK Query's cache carry a prior test's mocked-`fetch` response into the next.

## Permission degradation

- **Degrade by permission, and never by role name.** `GET /v1/whoami` reports the caller's effective permission set (`capabilities`: canonical `{method, path}` pairs, specced in `erun-docs/docs/agent-reference/api-protocol.md#capability-set`). That set is the only input a surface may gate on: a role's name says nothing about what a tenant granted it, so a control shown because a role is literally called `WriteAll` is wrong for every custom role a tenant defines.
- The rules are the same ones `erun-ui/AGENTS.md` states for the desktop, because a permission-shaped empty state should read identically in both clients: a list the caller may not read is not an empty list, a read they may not make is not attempted, a control they may not use does not render (with the missing access still named somewhere visible), partial access degrades partially rather than blanking the whole view, and "nothing exists yet" / "nothing matches the filter" / "you may not see this" stay three distinguishable states.
- Express "may I?" through the shared capability shape rather than a console-local predicate. The console now has a Redux store and `httpBaseQuery` (erun#1283), but no capability-gated surface yet — the nav and panels still gate the identity sections on `tenant.type === 'OPERATIONS'` (`shell/sections.ts`), matching the backend's own restriction; the first surface to need finer-grained gating adds the capability shape to the shared kit, not to a component.

## Toolchain

- Vite + React 19 + strict TypeScript, **Yarn** (`yarn@1.22.22`), matching `erun-ui/frontend`'s style. Do not introduce `npm`/`pnpm` lockfiles.
- Redux Toolkit + RTK Query + `react-redux` for the data layer (`src/app/`, erun#1283) — same versions and idiom as `erun-ui/frontend`'s store, with `httpBaseQuery` as the console's counterpart to the desktop's `wailsBaseQuery`. See `erun-kit/AGENTS.md`'s Tier 4 for what's shared between the two stores (the `GET /v1/config` model + endpoint definition) versus what stayed console-local (everything with no desktop equivalent today).
- ESLint flat config (`eslint.config.mjs`) mirrors `erun-ui/frontend`: type-aware `strictTypeChecked` + `stylisticTypeChecked`, `complexity:10`, `max-lines-per-function:100`, `max-lines:500`, React hooks/refresh, `jsx-a11y`. Every rule is `error`; fix findings by correcting the code — never disable, suppress, or downgrade a rule.
- Prettier (`.prettierrc.json`) is the formatter, same config as `erun-ui/frontend`.
- Styling is Tailwind 4 + `erun-kit`'s design tokens (`src/styles.css` imports `erun-kit/theme.css` and declares a Tailwind `@source` pointing at `erun-kit/src`, since the kit's utility classes live under `node_modules` via the workspace symlink and are otherwise excluded from Tailwind's default content scan — see `erun-kit/AGENTS.md`). Every panel is built from `erun-kit`'s generic widgets (`StatusBadge`, `EmptyState`, `FieldLabel`, `SelectField`) and shadcn primitives (`Button`, `Card`, `Input`, `Textarea`, `Select`, `Checkbox`, `Table`) styled with Tailwind utilities in the component — `src/styles.css` carries only true globals (box-sizing, body margin) plus the `erun-kit` theme import, the same shape as `erun-ui/frontend`'s global CSS. A bespoke per-panel class vocabulary (the pre-#1207 `.provision-form`, `.mcp-access-form`, `.identity-*`, `.deploy-*` selectors) is a regression; if a surface needs a control the kit doesn't have yet, add the shadcn primitive there (`yarn shadcn add <primitive>` from `erun-kit/`, see its AGENTS.md) rather than hand-rolling CSS here.
- Dark mode is the class-based `.dark` toggle `erun-kit/theme.css` already defines the token scale for (`shell/theme.ts`/`shell/useTheme.ts`), persisted to `localStorage` and defaulted from `prefers-color-scheme`. `erun-ui/frontend` now ships the same mechanism (`app/theme.ts`/`app/useTheme.ts`, #1407), mirroring this implementation under the same `.dark` class contract.

## Validation

Run all of these from `erun-console/` for any change to this module:

```bash
yarn install
yarn typecheck      # tsc --noEmit
yarn lint           # eslint .
yarn format:check   # prettier --check .
yarn build          # vite build
yarn test           # vitest run — the component tests
```

- `yarn test` (vitest + `@testing-library/react`, jsdom) mocks `fetch` and asserts the render/controller behaviour: `ConfigView`'s read model and empty states, the app shell's navigation and theme toggle (`shell/AppShell.test.tsx`), the provisioning/MCP/identity panels, and the PKCE mechanics. `vite.config.ts` scopes it to `src/`, so it never collects `playwright/`'s spec. `src/test/setup.ts` also polyfills `ResizeObserver` and `matchMedia`, which jsdom does not implement and which Radix primitives (`Select`, `Checkbox`) and the theme hook probe on mount.
- The **real-IdP** verification lives in `playwright/` (its own package, own validation commands): a browser sign-in against a live Zitadel v4 through to the rendered tenant. Run it from `erun-console/playwright/` with `yarn test`; see `playwright/AGENTS.md`. Anything that changes `src/auth/` or `App.tsx`'s auth lifecycle should be re-verified there, not only under vitest.

## Running against a real erun-backend-api (dev)

The console can be driven against a **live** `erun-backend-api` with no live IdP, the same way the MCP edge is tested (issue #674): the API trusts a `file://` desktop key, so a desktop-signed token authenticates the read view end to end. For a run with a live issuer instead, use `playwright/run.sh`, which wires the same API to a real Zitadel.

- `vite.config.ts` proxies `/v1/...` to `VITE_API_PROXY_TARGET` (default `http://127.0.0.1:17033`) so `yarn dev` fetches **same-origin** — the API sets no CORS headers by design, and the dev proxy forwards server-side, so there is no browser preflight. In production the console is served same-origin behind the API edge, so no proxy is needed.
- `VITE_DEV_BEARER_TOKEN` is the bearer token `App.tsx` presents. For a real-API run it must be a token the API trusts: either an OIDC JWT, or a desktop-signed `file://` token (EdDSA, audience `erun-api`) when the API is started with `ERUN_API_DESKTOP_PUBLIC_KEY_PATH` pointing at the matching public key. See [`api-protocol.md` § Sign-in](../erun-docs/docs/agent-reference/api-protocol.md) for the token model.

```bash
# point yarn dev at a running API on :17055 with a desktop-signed token
VITE_API_PROXY_TARGET=http://127.0.0.1:17055 VITE_DEV_BEARER_TOKEN=<token> yarn dev
```

Unlike `yarn test` (mocked `fetch`), this renders the **real** `{ tenant, environments[], contexts[] }` the API serves from Postgres — the verification that closed the option-2 console↔API check for #606/#658.
