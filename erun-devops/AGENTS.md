# AGENTS.md

Additional guidance for `erun-devops` and its subtree.

- Follow the repository root `AGENTS.md` first.
- This file adds DevOps-module-specific guidance for runtime images, charts, Linux packaging, and release behavior.

## Scope

- This module owns the shared DevOps runtime image, its base images, its Kubernetes runtime chart, and Linux packaging assets used during build and release flows.
- Treat the module as the operational runtime contract for build, open, deploy, and release behavior.

## Runtime Image Rules

- Treat `erun-ubuntu`, `erun-devops`, and `erun-dind` as one dependency graph. When a release image depends on another local image, preserve the dependency ordering so base images publish before dependents.
- Keep the runtime image thin over `erun-ubuntu`. Put shared OS package setup in `erun-ubuntu` when it is truly common, and keep `erun-devops` focused on DevOps tooling and runtime-specific wiring.
- Keep release-critical tool versions pinned in Dockerfiles. Do not switch to floating tags or unpinned downloads for kubectl, Helm, Terraform, Docker, gh, golangci-lint, or similar tooling. `golangci-lint` is the one pin that also has to agree with a contributor's local install and the pre-commit hook, so it lives in the checked-in repo-root `GOLANGCI_LINT_VERSION` file rather than a Dockerfile `ARG` default: both Dockerfile stages `COPY` it in and fall back to it when no `--build-arg` overrides it, and the root `Makefile`'s `lint` target and `.githooks/pre-commit` both assert the installed `golangci-lint --version` against the same file before running, so a contributor on a different version gets a clear refusal instead of a gate that quietly disagrees with the image build.
- Prefer simple, reviewable Docker layer ordering. Put stable, expensive tooling installation layers before builder artifact copies so source changes do not invalidate them unnecessarily.
- Treat `ARG TARGETARCH` and multi-arch tooling downloads as cache boundaries. Per-arch caches are expected; do not assume `amd64` and `arm64` can reuse the same layer.
- Pin published base images by content via `docker.fingerprints` in `.erun/config.yaml`. The map is keyed by image name (e.g. `erun-ubuntu`) and stores the 16-character lowercase hex fingerprint that release CI computed when it last published `<image>:<VERSION>`. Before resolving incremental promotion, the build flow pulls `<image>:<VERSION>` from the registry and tags it locally as `<image>:fp-<fingerprint>-<arch>`; the standard fingerprint check then promotes the build instead of rebuilding it. Local Dockerfile edits diverge the locally-computed fingerprint from the configured one, the inspect misses, and the build rebuilds — exactly the desired safety net. Bump the configured fingerprint in the same commit that publishes a new base.
- Bump the published tag whenever a base-image Dockerfile changes content. Cluster pods pull by tag with `imagePullPolicy: IfNotPresent`, so reusing the same tag with new content does not roll out — kubelets keep the old cached digest. The `erun-dind` image uses `<docker-version>-<rev>` (for example `28.1.1-1`); when the Dockerfile changes, increment the trailing `-rev`, update the chart reference that defaults to `erun-dind:<tag>` (`erun-devops/k8s/erun-devops/templates/service.yaml`), and clear the corresponding `docker.fingerprints` entry so the next release publishes a fresh fingerprint for the new tag.
- The runtime image defines a canonical **agent outputs directory** at `$ERUN_OUTPUTS_DIR`, default `/home/erun/.erun/outputs` — where agents and skills write deliverables (reports, generated artifacts, logs, doc builds) that an operator pulls out with `erun outputs list`/`erun outputs download`. It lives on the `/home/erun` PVC so it persists across pod restarts, and is distinct from the repo worktree (`$ERUN_REPO_PATH`, files that belong in git) and the paste-attachments dir (`/home/erun/.codex/attachments`). It is wired in three places that must stay aligned: the Dockerfile creates it (`mkdir -p /home/erun/.erun/outputs`), the runtime chart exports `ERUN_OUTPUTS_DIR` on the runtime container (`erun-devops/k8s/erun-devops/templates/service.yaml`, next to `ERUN_REPO_PATH`), and the entrypoint `mkdir -p`s it at boot (`ensure_outputs_dir`) as a fallback for older images. `outputs list`/`download` default to this dir but accept a `--path` elsewhere under the home/workspace.
- The runtime image bakes agent skills under `/etc/erun/skills/<skill-name>/` from the canonical source at `erun-skills/skills/<skill-name>/` (whole tree vendored via `COPY erun-skills/skills /etc/erun/skills`). On every entrypoint run, `initialize_claude_config` and `initialize_codex_config` invoke the baked `erun-install-skills` helper (`skills-install.sh`, baked to `/usr/local/bin/erun-install-skills`) for `~/.claude/skills/` and `~/.codex/skills/`. It **installs** each baked skill when the destination is absent and **refreshes** it when the image's copy changed — unless the operator edited it in-pod, which is preserved. Provenance is tracked per skill by recording the baked `SKILL.md` hash in a `.erun-skill-baked-sha256` marker: an installed copy whose `SKILL.md` still matches its marker is unmodified since erun installed it and is refreshed to the baked version, while one that differs was edited in-pod and is left untouched (a legacy copy with no marker is treated as unmodified and refreshed). Because `~/.claude`/`~/.codex` live on the home PVC, the old install-only-when-absent guard froze the first-installed copy forever; the refresh is what now lets a rebuilt image's updated skill reach an existing env. Supporting files (templates, helper scripts) inside a skill directory ship with the skill automatically. Editing a baked skill is a content change in `erun-skills/`, not in this module; see `erun-skills/AGENTS.md` for the source and the marketplace contract that vendors the same tree for laptop Claude Code installs. Both config scripts call the one helper — keep the install/refresh policy there, not duplicated inline; `skills-install_test.sh` locks the install/refresh/preserve/legacy behavior.
- The runtime image bakes `erun-prune-sessions` (`session-prune.sh`, baked to `/usr/local/bin/erun-prune-sessions`), and the entrypoint calls it from the **container-boot path only** (`devops` / no-args), never from the `shell` path. It removes `*.dtach` sockets in the desktop session dir (`/tmp/erun-sessions`, overridable for tests via `ERUN_APP_SESSION_DIR`) that no live `dtach` process references, plus their `.owner` files. The session dir is container-lifetime **by design** — a `dtach` server is a process in the container, so a socket that outlived its pod could never be attached to, and clearing it is what lets `claude --continue` resume in a fresh session. Do not move the session dir onto the `/home/erun` PVC: that would persist exactly the leftovers this prunes. Pruning from the `shell` path would delete live sessions' sockets — keep the call in the boot branch. `session-prune_test.sh` locks the prune/keep-live/absent-dir/usage behaviour; `entrypoint_test.sh` locks that boot prunes and `shell` does not. The directory name must keep sharing nothing with the desktop binary's process name (`erun-app`): the natural way to free that binary before a rebuild is `pkill -f erun-app`, and while the sockets lived under `/tmp/erun-app` that pattern matched every session's `dtach` command line and killed the operator's live terminals. `eruncommon.DesktopAppName` is the name to keep out; `TestSessionSocketPathCannotCollideWithTheDesktopBinary` pins the property.
- The runtime image bakes `erun-adopt-worktree` (`worktree-adopt.sh`, baked to `/usr/local/bin/erun-adopt-worktree`), and the **chart's `adopt-worktree` init container** is its only caller — never the entrypoint. By the time the entrypoint runs, the worktree claim is already mounted over the repo path, so the tree it would have to rescue is unreachable; the init container is the one place both volumes can be staged side by side outside `/home/erun`. It adopts only when the claim is empty *and* the staged legacy path is a real repository, and it copies-then-sets-aside (to `<repo>.pre-worktree-volume`) rather than moving: losing the tree a second time is the failure it exists to prevent, so the original is only touched after the copy is proven. A partial copy lands in `<claim>/.erun-worktree-adopt-partial`, which the empty-claim check ignores, so an interrupted run retries instead of presenting itself as a populated claim. `worktree-adopt_test.sh` locks the adopt/no-op/idempotence/retry/usage behaviour and `k8s/erun-devops-chart_test.sh` locks that the init container renders for `pvc` only and stages both volumes off the live worktree path.
- **`start_environment_monitor` is one loop per pod, and it runs in every pod.** Each 30s tick first calls `erun activity sample`, which records activity for the container's resident build/agent processes that are actually burning CPU — the backstop for work nobody wrapped in an activity lease, and the signal the desktop reads to render an environment as busy. Only the auto-stop half is gated on `runtime_cloud_environment`; do not re-gate the whole loop on it, or a non-cloud environment goes back to reporting as untouched under load. The sample runs *before* the sleep so the first tick establishes the CPU baseline the next one compares against. `entrypoint_test.sh` locks that boot samples.
- The **erun Terraform modules** (`erun-devops/terraform-erun/modules/`) are **not** baked into the image — like the Helm charts (published to OCI, referenced by `deploy`), they are referenced from their published source. A platform skill (e.g. `erun-enable-hosting-edge`) sources a module with Terraform's native module addressing, pinned to the erun version it runs — `source = "git::https://github.com/sophium/erun.git//erun-devops/terraform-erun/modules/<module>?ref=v<version>"` — so `terraform init` fetches it; `terraform` itself is installed in the image. Keep these as **pure modules** (no `provider` blocks): the skill's generated root config declares the providers, so the module is usable via `module { source = … }`. Publishing modules to an OCI registry alongside the chart (so skills can `source = "oci://…"`) is a follow-up.
- **Never bake tenant artifacts under `/home/erun`; use `/opt/erun/release` instead.** The runtime chart mounts the persistent `<release>-home` PVC over `/home/erun` (see Runtime Chart Rules) with no seed step, so anything a `<tenant>-devops` image `COPY`s under the home tree (e.g. `/home/erun/git/<repo>/…`) is shadowed by the PVC and never appears in the running pod. The supported way to surface baked artifacts (a platform Terraform tree, seed data, fixtures) in a **sourceless runtime env** is to `COPY` them into **`/opt/erun/release/`** — outside `/home/erun`, so the image layer shows through — laid out relative to the repo root (`~/git/<repo>`). On boot the entrypoint's `link_runtime_release` (via `erun-link-release`, `release-link.sh`, baked to `/usr/local/bin/erun-link-release`) symlinks the git folder at `/opt/erun/release`, so `~/git/<repo>` reflects the baked tree and always matches the deployed image — no copy, no staleness. Guarded to runtime envs with no worktree (`ERUN_ENV_TYPE=runtime` and not a mount-source clone): agent envs and mount-source runtime envs keep their real worktree, and a populated directory is never clobbered. The runtime chart pairs with this by setting `ERUN_REPO_PATH=/home/erun/git/<worktreeRepoName>` even for a sourceless runtime env (storage `none`, no worktree volume), so `erun terraform` and the MCP repo-path resolve the symlinked tree; `worktreeRepoName` is threaded to the chart for every env (`resolveWorktreeRepoName` in `erun-common/deploy.go`). `release-link_test.sh` locks the install/replace-empty-stub/preserve-worktree/relink/skip-when-absent behavior. `erun terraform` resolves the per-env root under `<tenant>-devops/terraform-<tenant>/` too (the same `-devops` convention `build`/`deploy` use), so a tree baked under `<tenant>-devops/` is found without a `paths.terraform` override; it keeps Terraform's mutable state — the local-backend `terraform.tfstate`, the plan file, and `TF_DATA_DIR` — under `~/.erun/terraform/<tenant>/<env>/` on the `/home/erun` PVC, so the baked playbook tree stays read-only while state and the provider cache survive a pod restart.

## Runtime Chart Rules

- Keep the shared runtime chart and any generated tenant chart contract in sync. The shared runtime is the template for tenant-specific DevOps modules, so deployment behavior must remain aligned across both.
- The runtime stack is split into per-pod Helm releases under `erun-devops/k8s/`:
  - `erun-devops` — the runtime pod (the devops container, which also serves the env's MCP edge, plus the dind sidecar for env types that build). Always deployed; produces the shared `/home/erun` PVC and the runtime ServiceAccount/RBAC. The dind sidecar, its docker daemon PVC, the docker-socket volume, the binfmt installer, and the pod's dind-group membership are all gated on `$envType != "runtime"` (see Runtime Chart Rules) — a `type: runtime` env installs published versions by reference and never builds, so none of it has anything to do there.
  - `erun-backend-postgres` — opt-in. Owns the postgres Deployment + Service + PVC and the postgres password Secret (default `<tenant>-backend-postgres`, e.g. `erun-backend-postgres` for the `erun` tenant). Created on first deploy and reused via `lookup` on subsequent deploys. **The disposable-data reset (`api.postgres.reset`, armed only for a snapshot version — see `deployResetsDatabase` in `erun-common/deploy.go`) is a `post-install,post-upgrade` Helm hook Job (`reset-job.yaml`), never a step inside the Deployment's own pod spec.** The pod spec is what a crash, eviction, node reboot, or `rollout restart` re-applies, so anything destructive there would re-run on every one of those, not just on a deploy — this is exactly the failure that let a postgres pod restart wipe `erun-local`'s tenant/user/issuer data for five days (2026-08-22) before anyone deployed again. The hook Job wipes over the network (`DROP DATABASE ... WITH (FORCE)` then `CREATE DATABASE`) against the already-running server instead of touching PGDATA on disk, so it needs no filesystem access and never contends with the running pod for the data PVC. `erun-backend-postgres-chart_test.sh` locks that the Deployment's pod template is byte-for-byte identical whether or not `api.postgres.reset` is set; it runs via `make check`'s `helm-chart-tests` target, alongside the other `k8s/*chart_test.sh` scripts (see Build Workflow).
  - `erun-backend-db` — opt-in. Owns the migration Job. The Job is wired as a Helm `post-install,post-upgrade` hook with `helm.sh/hook-delete-policy: before-hook-creation` so each release run replaces the prior Job and migrations only run when this release is applied. It also owns a `migrate-repair-cronjob.yaml` CronJob that re-runs the identical `migrate.sh` every 5 minutes, independent of any Helm operation — `atlas migrate apply` is a fast no-op once the schema is already at head, so this is safe to run continuously, and it is what stops a database that loses its schema by any means (a bug, a manual reset, a restore onto an empty volume) from staying schema-less until someone happens to deploy. `erun-backend-db-chart_test.sh` locks both the hook Job and the CronJob, via the same `helm-chart-tests` target; `erun-devops/docker/erun-backend-db/migrate_test.sh` proves the whole property end-to-end against a real postgres: a restart preserves committed data, the reset genuinely wipes when it runs, and a schema-less database is fully repaired by the same command the CronJob invokes. It needs a real docker daemon and the atlas CLI, neither of which the image test stage carries, so it stays out of `make check` and runs instead via the root Makefile's `test-postgres-restart` target — by hand, or via `erun exec job` in an agent env, before merging a change to postgres reset/migrate/restart behavior.
  - `erun-backend-api` — opt-in. Owns the API Deployment + Service. Consumes the postgres Secret via `secretKeyRef`; expects `erun-backend-db` to have run before the API rolls.
  - `erun-oci-registry` — opt-in. The platform's hosted container registry singleton (zot, see "Wrapping And Pinning Third-Party Service Images"): a Deployment + Service + PVC, with a ConfigMap rendering zot's bearer-auth and retention config. Auth is fully delegated to `erun-backend-api`'s `GET /v2/token` route (`internal/registrytoken`) — the chart carries no credential of its own, only two operator-supplied, required values: `registry.tokenRealm` (that route's URL) and `registry.signingKeySecretName` (an existing Secret holding the token service's public signing key, `public.pem`, so zot can verify what it mints); the render fails when either is unset. `registry.retentionDays` (default 30) is a named, chart-level setting because deleting a tenant's images is destructive and the window must be visible and changeable. `k8s/erun-oci-registry-chart_test.sh` locks the tenant-scoped naming, the rendered bearer/retention config, the required-value refusals, and the image override; like the other chart tests it runs via `make check`'s `helm-chart-tests` target.
  - `erun-zitadel` — opt-in. The platform's hosted IdP singleton: one Deployment with **two** containers (Zitadel core + the separate Login V2 container) sharing an `emptyDir` at `/zitadel/bootstrap`, plus a Service and one Ingress with two paths. Zitadel v4 core serves no interactive login, so a core-only chart is broken by construction — see the template header for the full topology and the PAT handoff the shared volume exists for. Runs against the shared `erun-backend-postgres` in its own `zitadel` database, so sequence it after postgres. The masterkey is operator-supplied via an existing Secret (`zitadel.masterkeySecretName`); the render fails when it is unset, and the chart must never grow a generated default. `k8s/erun-zitadel-chart_test.sh` locks the topology (both containers, the shared-volume PAT handoff, the Login V2 env, both Ingress paths, the external-origin invariant, and the two required-value refusals); like `erun-devops-chart_test.sh` it runs via `make check`'s `helm-chart-tests` target.
  - `erun-docs` — opt-in. Owns a single Job that runs `wrangler pages deploy /site/` to publish the prebuilt Docusaurus static site to Cloudflare Pages. No Service, no Ingress, no in-cluster traffic. Gated by `docs.enabled` so accidental local deploys don't push to the live project. Consumes a `cf-creds` Secret (configurable) for `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. See `erun-docs/AGENTS.md` for the full hosting contract and the one-time external setup (Cloudflare Pages project, custom domain, DNS).
  - `erun-console` — opt-in. The hosted web console SPA, served same-origin with `erun-backend-api` behind its own nginx (see `erun-console/AGENTS.md`). Its Ingress serves the canonical `console.<baseDomain>` host and, whenever a base domain is known, also renders a second Ingress + Traefik `Middleware` that 301-redirects the bare apex and `www.<baseDomain>` hosts to that canonical origin (erun#1208) — a visitor who types the product's own domain lands on the console instead of a dead end, while OIDC sign-in (Authorization Code + PKCE) keeps exactly one origin, since the redirect rule never reaches the canonical Ingress. On by default once `platform.baseDomain` **or** `console.apexHost` resolves a host — a tenant with no platform-wide domain but a specific apex to redirect enables it by setting `console.apexHost` alone, since gating on `baseDomain` alone left that half-configured pair silently off and made the status ConfigMap's "not configured" reason lie about a host that was, in fact, configured (erun#1471); `console.apexRedirectEnabled=false` turns it off for a platform whose apex serves something else (e.g. a marketing site), and `console.apexHost`/`console.wwwHost` override the derived hosts. The redirect target is `platform.consoleUrl` when configured (the value `GET /v1/platform` hands clients), falling back to the chart's own `externalDomain` — never a literal, so a second instance on its own domain behaves correctly with no source change. The shared TLS Secret's Certificate request (driven by the canonical Ingress's `cert-manager.io/issuer` annotation) is extended to cover the apex/www hosts as SANs too; the redirect Ingress references the same Secret without its own cert-manager annotation, so it never races a second Certificate for it. DNS for the apex/www hosts is a separate concern, applied through the new `terraform-erun-cloudflare-apex` module (writes A records directly into the already-Cloudflare-authoritative apex zone — it does not create a zone, unlike `terraform-erun-cloudflare-services`). **An unset `platform.baseDomain` disables the redirect the same as `apexRedirectEnabled=false` would, but that off-by-default state must never be silent** — most deploys legitimately have no apex and must keep rendering exactly as before, so the chart cannot fail loudly on an unset `baseDomain` the way it does on the `required` host checks below it. Instead a `<tenant>-console-apex-status` ConfigMap always renders (on, off-by-default, and off-by-`apexRedirectEnabled=false` each get their own recorded reason), so `kubectl get configmap`, `helm get manifest`, or a `--dry-run` install always shows whether the redirect is live and why it isn't when it's not. `k8s/erun-console-chart_test.sh` locks the default-on/explicit-off/override/shared-certificate/canonical-Ingress-untouched/status-ConfigMap behavior; like the other chart tests it runs via `make check`'s `helm-chart-tests` target.
- The `erun-devops` chart names its Kubernetes resources (Deployment, PVCs, ServiceAccount, RoleBinding, and the local-only namespace-manager ClusterRole/bindings) after the **helm release** via `{{ .Release.Name }}`, not a hardcoded `erun-devops`. A deploy of release `<tenant>-devops` (`RuntimeReleaseName(tenant)`) therefore produces a `<tenant>-devops` Deployment, `<tenant>-devops-home`/`-docker`/`-worktree` PVCs, and matching RBAC — so `erun open`, which execs `deployment/<tenant>-devops`, finds the pod. Only the runtime **image** (`erun-devops`) and the main container's name stay fixed across tenants. The resource names below use the `erun` tenant's release for illustration; substitute the env's release name for other tenants.
- **Runtime SA RBAC is namespaced by default; cluster-scoped grants are opt-in.** For every env the runtime SA gets only a `RoleBinding` to the built-in `admin` ClusterRole (namespaced admin in its own namespace). The `local`-only block additionally grants the contribute-mode self-deploy set (a cluster-wide `admin` binding, the `namespace-manager` ClusterRole, and the by-name `self-deploy` grants). A hosted env that must manage cluster-scoped platform resources — in-pod `erun terraform apply` of the cluster edge, or platform installs that create CRDs/cluster RBAC — opts in via `platformAccount` (`EnvConfig.platformaccount`, `erun init --platform-account`), which renders a `<release>-platform` ClusterRoleBinding to the built-in `cluster-admin`. It is emitted only when the value is set, so non-platform deploys are byte-for-byte unchanged, and it reconciles both ways (an absent value prunes the binding on upgrade). Bootstrapping constraint: the API server's privilege-escalation check means the binding can only be *created* by an admin-capable context, so the first deploy that adds it runs from the control plane / an operator's cluster-admin kubeconfig — an in-pod self-deploy cannot grant itself cluster-admin. Every optional RBAC block in `service.yaml` (the `local` set, `platformAccount`, `extraRules`) must render a trailing `---` so its last document is separated from the Deployment; a block without one glues its final `ClusterRoleBinding` into the Deployment document.
- The **component charts** (`erun-backend-postgres`, `erun-backend-db`, `erun-backend-api`, `erun-oci-registry`, `erun-powerdns`, `erun-zitadel`, `erun-docs`) scope every resource `metadata.name`, label/selector, and cross-chart reference to the tenant via `{{ .Values.tenant | default "erun" }}`. A deploy with `--set tenant=frs` renders `frs-postgres`/`frs-api`/`frs-powerdns` and `frs-backend-postgres` (the password Secret), and wires the API/db/powerdns DB host to `frs-postgres` — so a tenant's stack never collides with another tenant's `erun-*` resources in a shared platform namespace. The `erun` default keeps the erun tenant's own resources named `erun-*` (no migration). Unlike the runtime chart (which scopes by `{{ .Release.Name }}`), component charts scope by `.Values.tenant` because `erun deploy` threads `--set-string tenant=<tenant>` to every component. When authoring a new component chart, derive names from `.Values.tenant | default "erun"` the same way — never hardcode an `erun-` prefix on a resource name, label, or cross-reference. Container names and image keys stay literal across tenants (some are referenced by name from Go code, e.g. `erun-backend-api`).
- **The environment's MCP edge runs inside the `erun-devops` runtime container, not a container of its own.** The entrypoint's `devops` path starts `emcp` under a supervision loop (`start_runtime_mcp`) before its idle foreground, sharing one argv builder (`exec_runtime_mcp`) with the standalone `mcp` path so both serve the same server. That is what makes an MCP tool call execute with the environment's own toolchain: a `<tenant>-devops` image that adds a JDK or a compose plugin is visible to `raw`/`build` over MCP exactly as it is to `erun open`. The gate is `ERUN_MCP_ENABLED` (chart value `mcpEnabled`, default true); with the value unset — an older chart — a configured `ERUN_MCP_PORT` still brings the edge up. Nothing else restarts a crashed server, so keep the supervision loop and its start/restart logging; `entrypoint_test.sh` locks the enabled/disabled/restart behavior (run directly, not through `make check`) and `k8s/erun-devops-chart_test.sh` locks the rendered pod shape (via `make check`'s `helm-chart-tests` target). Do not reintroduce a separate MCP container or image: `erun-devops/docker/erun-mcp/` was retired, and a sidecar built from the stock image is exactly the divergence this arrangement removes.
- **The dind sidecar, its docker state PVC, the docker-socket volume, the binfmt installer, and the pod's dind-group membership are deployed only for env types that build (`local-agent`, `remote-agent`) — a `type: runtime` env renders none of them.** `deploy` installs a published version by reference and never builds, so a runtime pod's docker daemon has nothing to do — it sat there unconditionally, unschedulable on any namespace whose `LimitRange` handed the sizeless-by-then sidecar a default big enough to double the pod's effective ask. The chart already computes `$envType` (`runtime` / `local-agent` / `remote-agent`, see below) and derives `$dindEnabled := ne $envType "runtime"` from it once, at the top of `service.yaml`; every dind-related block (the container, its PVC, the docker-socket emptyDir and mount, `DOCKER_HOST`/`DOCKER_BUILDKIT` on the main container, the binfmt installer, `securityContext.supplementalGroups`) is gated on that one boolean. `k8s/erun-devops-chart_test.sh` locks both directions: build-capable env types render the sidecar with explicit resource limits, `runtime` renders none of it.
- The runtime pod contract is intentional, for the env types that get a dind sidecar:
  - the main `erun-devops` container uses `DOCKER_HOST=unix:///var/run/docker.sock` and serves the MCP edge
  - the `erun-dind` sidecar provides the daemon, with its own explicit `resources.limits`/`requests` (`runtime.dind.resources` values, defaulting alongside the main container's own `runtime.resources` defaults, see #1061) — declared rather than left to an unrelated `LimitRange` policy object to assign
  - **the sidecar's declared memory limit is capacity planning, not enforcement, and no reachable mechanism closes that gap (#1805).** Under cgroup v2, `dockerd`'s embedded BuildKit worker (the one plain `docker build` uses; see Build Workflow's ban on switching to a dedicated buildx builder) runs every build step's containers as **siblings** of the sidecar's own limited cgroup, with `memory.max: max` — the sidecar's `resources.limits.memory` therefore caps a cgroup no build step runs in, and raising it (#1872 moved the default 8916Mi → 20Gi) is honest headroom, not a ceiling anything actually enforces. Three mechanisms were tried and rejected, cheapest first: (1) `buildkitd.toml`'s `[worker.oci] max-parallelism` is not read at all by dockerd's embedded builder — confirmed by mounting the config into a nested `docker:dind` daemon and observing two independent Dockerfile stages still run concurrently regardless of the setting, and by dockerd's own startup log never mentioning the file; that config path is consulted only by a standalone `buildkitd` (the `buildx create --driver=docker-container` path this repo already refuses to adopt). (2) Writing `memory.max` directly on the sibling cgroup is technically reachable from inside the privileged sidecar (it runs with the **host's** cgroup namespace, not a private one, so `/sys/fs/cgroup/docker/buildkit` is a real, writable path) — but that same host-namespace fact means the path is **shared by every privileged, build-capable pod scheduled onto the same node**, not scoped to one environment: a cap written there throttles or kills a co-located tenant's unrelated build, not just this one's. A per-build-step leaf cgroup (each gets a unique, unpredictable name, and this pod's own private PID namespace can prove which leaf PIDs are genuinely its own) could be capped safely, but only bounds one step at a time, not the aggregate the sidecar's limit is meant to represent, and migrating a leaf cgroup to a private parent for aggregate scoping risks breaking BuildKit's own cleanup of a cgroup it no longer finds where it left it. (3) `--cgroup-parent` (daemon or container) is foreclosed regardless of flavor — already live-tested and found to break `kubectl exec`, `erun open`, the postStart hook, and the readiness probe. What #1805 did land, safely: `erun init --dind-memory`/`erun resize --dind-memory` size the limit explicitly, `erun release`/`erun build` report a `signal: killed`/`ResourceExhausted` build failure as a resource-exhaustion naming the container and its limit instead of letting a linter's rendering of a killed compiler stand as the verdict, and the per-platform build loop already runs one architecture at a time (see Build Workflow) so peak memory is one `make check`, not two concurrent ones. `scripts/parallel-gate.sh`'s own memory-aware job-count sizing (`width` mode) turned out to have the identical blind spot for the identical reason — its own process's cgroup reads `memory.max: max` inside this exact `RUN make check` step — fixed via the `PARALLEL_GATE_MEMORY_LIMIT_MIB` override the erun-devops Dockerfile's test stage now sets from a `DIND_MEMORY_LIMIT_MIB` build arg (default 20480, matching the chart default above); real today only in configurations where memory, not CPU or job count, would otherwise bind the fan-out width.
  - `/var/lib/docker` is persisted on the `<release>-docker` PVC
  - `/home/erun` is persisted on the `<release>-home` PVC
  - the pod carries **no `fsGroup`**, and must not regain one. `fsGroup` applies to every volume in the pod, so it also reached the `<release>-docker` claim and had the kubelet recursively chgrp + `g+w` (and setgid) the whole docker state store on each pod start — rewriting the permissions of every image layer, which is silently fatal to anything permission-sensitive inside those images (sshd host keys, `PGDATA`, any baked `0600` file). `fsGroupChangePolicy: OnRootMismatch` does **not** fix it: dockerd resets its own root to `0710 root:root` at every start, so the volume root permanently mismatches the fsGroup and the full sweep re-runs regardless. Kubernetes has no per-volume opt-out, so what fsGroup was buying — a freshly provisioned, empty, root-owned claim that uid 1000 must write — is bought instead by the `prepare-volumes` init container, which runs as root and chowns the *mount points* of the home claim and (for `worktreeStorage=pvc`) the worktree claim. Mount points only: an existing claim's contents already belong to uid 1000, and recursing a populated home volume on every start would trade this bug for a slow one. It runs first, before `adopt-worktree`, which writes the claim as uid 1000; it never mounts the docker state claim or the docker socket emptyDir, and a `host` worktree is the operator's own node directory and is never chowned. `k8s/erun-devops-chart_test.sh` locks all of this.
  - the runtime container reaches the daemon by **group membership**, not by a relaxed socket mode: the pod's `securityContext.supplementalGroups` carries the `docker` gid baked into the dind base (`dindDockerGid`, default `2375`), so the daemon's own `0660 root:docker` socket is usable however many times dockerd recreates it. The sidecar's `postStart` `chmod 0666` is a fallback for anything outside that group and must stay non-fatal; it waits on a daemon that answers rather than on a socket file, because a `SIGKILL`ed dockerd cannot unlink its socket and the leftover file makes an existence check pass against an inode that is about to be replaced. Bump `dindDockerGid` if the base image's group moves, and keep the wait bounded — kubernetes never times a `postStart` hook out.
- **Any chart-rendered ServiceAccount must carry the env's image-pull credentials, because giving a pod its own ServiceAccount silently drops the credential it inherited from the namespace's `default` ServiceAccount.** A pod with no `serviceAccountName` of its own pulls under `default`, and an operator-provisioned registry secret attached there (e.g. via a platform terraform apply) makes every such pod work without anyone wiring pull secrets per chart. The moment a chart gives a pod its own ServiceAccount — for RBAC scoping, least privilege, whatever the reason — that inheritance stops, and the new ServiceAccount starts from zero. This has bitten twice live: the `erun-backend-api` chart's `<tenant>-env-deployer` ServiceAccount (the deploy Job `erun deploy` runs as) and the `erun-zitadel` chart's `<tenant>-zitadel` ServiceAccount (needed once the OIDC bootstrap sidecar required its own RBAC) both went `ImagePullBackOff` on a private tenant image until patched by hand. Every deploy already threads the env's configured `EnvConfig.ImagePullSecrets` to helm as top-level `imagePullSecrets[i].name=<name>` (`helmImagePullSecretSetArgs` in `erun-common/deploy.go`, appended to every `HelmDeploySpec.command()` regardless of which chart — runtime or component — is being installed); the fix is chart-side, not a new plumbing mechanism: every `kind: ServiceAccount` a chart renders should consume `.Values.imagePullSecrets` with `{{- with .Values.imagePullSecrets }}imagePullSecrets:{{ toYaml . | nindent 2 }}{{- end }}` right after its `metadata:` block (see `erun-devops`, `erun-zitadel`, `erun-backend-api`, and `erun-docs` templates). Putting it on the ServiceAccount rather than only on a pod spec matters for a ServiceAccount a chart names but does not itself run a pod under — `erun-backend-api` builds its `env-deployer`/deploy-Job pod spec in Go (`internal/deployexec`), not in this chart's templates, and Kubernetes applies a ServiceAccount's own `imagePullSecrets` to any pod that runs as it without the pod needing to repeat them. Adding a new dedicated ServiceAccount to any chart under `erun-devops/k8s/` means adding this block to it in the same change, and a `*chart_test.sh` assertion that the rendered ServiceAccount carries a configured pull secret.
- **A ServiceAccount's Role must grant exactly the Kubernetes API calls the identity behind it makes — when a change makes a component call the API for a resource it did not call before, the chart's Role moves in the same commit.** This is the RBAC-side twin of the pull-credential rule above, and it has bitten by the same pattern three times: `<tenant>-env-deployer`'s pull secret (no `imagePullSecrets`), `erun-zitadel`'s pull secret (same), and the `erun-backend-api` Role scoped to Jobs and Pods before the registry probe needed `get` on the image-pull Secret too. None of the three was reachable from `make check` — nothing in the test suite can observe live cluster RBAC — so each was found only by deploying and watching the identity fail. Prefer `resourceNames` to scope a grant to the specific object(s) a component actually reads or writes (e.g. the named pull secret) over a blanket grant on the resource type; fall back to an unscoped grant only when the object doesn't exist yet at grant time (`create` cannot be scoped by `resourceNames`) or the caller genuinely needs the whole collection, and say why in a comment next to the rule. Pin the pairing with a test at the same layer the pull-secret assertion above uses (a `*chart_test.sh` that checks the rendered Role grants the resource a known client-go call needs); `erun-devops/k8s/erun-backend-api-chart_test.sh` locks this for the env-deployer and release-queue Roles against `internal/jobexec` and `internal/provision`'s own Kubernetes calls.
- **`registryCredentialSecretName` delivers a registry credential into the pod without any RBAC grant, because a volume-mounted Secret is populated by the kubelet, not fetched by the pod's own ServiceAccount token.** `erun init` resolves a ghcr.io credential from the *host* running init (docker config / gh session / `GH_TOKEN`, `resolveGHCRBasicAuth` in `erun-common/registry_auth.go`) — the same three routes `ensureRemoteRegistryCredentials`' in-pod check already looks for — and, when one resolves, mints a `kubernetes.io/dockerconfigjson` Secret named `<release>-registry-credential` via `kubectl apply -f -` on stdin (`provisionRegistryCredentialSecret` in `erun-common/registry_credential_secret.go`; never as an argv element, matching `applyCloudflareCredentialsSecret`/`applyMCPAuthSecret`). The chart mounts it read-only at `/etc/erun/registry-credential` (`optional: true`, so a deploy that races ahead of the secret's own apply still starts) only when `.Values.registryCredentialSecretName` is set — absent, the pod is byte-for-byte unchanged. The entrypoint's `sync_registry_credential` merges the mounted `.dockerconfigjson` into `~/.docker/config.json` at every boot, seeding only host entries the pod doesn't already carry — the pod's own `docker login` or gh-driven push-recovery is more current than what erun resolved on the host at init time, so an existing entry is never overwritten (#1201). Only `erun init` mints or rotates the secret name; a plain `erun deploy` carries the persisted `EnvConfig.RegistryCredentialSecretName` forward unchanged, same as `ImagePullSecrets`. `erun-devops-chart_test.sh` locks the mount/volume shape and the byte-for-byte-unchanged-when-absent case; `entrypoint_test.sh` locks the merge-missing/preserve-existing boot behavior.
- Backend deployment is opt-in via `erun deploy --components=...`. Default `erun deploy` brings up only the runtime pod. The opt-in component names match the chart directory names (`erun-backend-postgres`, `erun-backend-db`, `erun-backend-api`).
- Charts deploy in dependency order regardless of `--components` input order. The order is configured per environment in `.erun/config.yaml` under `environments.<env>.k8s.deployments`. Each item is either a component name (deployed alone) or a list of names (deployed in parallel within that step). Different environments may declare different plans (e.g. dev runs a slim plan, prod runs the full backend). When an environment has no `k8s` section, deploy falls back to the default rank `erun-backend-postgres → erun-backend-db → erun-backend-api → other`. The `erun` repo's own `local` environment declares `[erun-devops, erun-backend-postgres]` as a parallel first step (they share no state), then `erun-backend-db`, then `erun-backend-api`.
- When all locally-built images for a chart were promoted from a cached fingerprint (no rebuild), `erun deploy` skips the helm command and the redundant push for that chart. `erun-backend-postgres` is a passthrough wrapper over a pinned `postgres:<VERSION>` (see `erun-devops/docker/erun-backend-postgres/VERSION`) so it participates in the same fingerprint-promote-and-skip path as the other backend components. Charts with no locally-built images at all would always deploy when included so chart-only changes still ship.
- **A `pvc` worktree mounts over a path the home volume may already own, so the chart adopts before it mounts.** The `<release>-worktree` claim is mounted at `/home/erun/git/<repo>`, and an env that predates the claim kept its checkout there on the `<release>-home` volume — a plain mount masks it, and the one-way pod→host workspace sync then propagates the empty tree over the operator's mirror. The `adopt-worktree` init container (rendered only for `worktreeStorage=pvc`, running the runtime image) stages both volumes at `/mnt/erun-home` and `/mnt/erun-worktree` — deliberately outside `/home/erun`, because that is the only place the claim cannot shadow the tree being read — and delegates the decision to the baked `erun-adopt-worktree` helper (see Runtime Image Rules). Do not move the staging paths under `/home/erun`, do not let the adoption run from the entrypoint, and do not soften the "no helper in this image + a real repository at the legacy path" arm from a refusal into a warning: starting the pod is what loses the tree. `erun deploy` pairs with this by reading the claim before the rollout and naming the relocation in its output; keep those two aligned, and see `erun-docs/docs/agent-reference/conventions-spec.md` § "Worktree volume adoption" for the published contract.
- Do not move build cache, Docker state, or home-directory state onto `emptyDir` unless the change is deliberate and the persistence tradeoff is documented in the code review and tests.
- Keep binfmt installation explicit for release builds. Multi-arch release support depends on the chart installing `amd64` and `arm64` emulation before the dind daemon is used.
- **The dind sidecar starts through `files/dind-entrypoint.sh`, which derives dockerd's bridge MTU from the pod network rather than letting docker default it to 1500.** A CNI that encapsulates gives the pod less than 1500 (a VXLAN overlay costs 50 bytes, leaving 1450); dockerd left at its default then bridges every container — including every BuildKit step — wider than the path can carry, the oversized replies are dropped with DF set, and the ICMP `fragmentation needed` that would let path-MTU discovery recover does not survive the overlay. The result is a black hole with a deeply misleading signature: TCP connects, small packets flow, and a TLS handshake gets through ClientHello and ServerHello before stalling forever on the server's certificate flight — surfacing many minutes into a build as a `curl` error against whichever third-party host that build reached first, on whichever platform iteration happened to be in flight. That is how erun#1886 read as an amd64-emulation fault for three runs: the "native" control was run in the pod's netns (correct MTU) while the "emulated" one ran in a container on the daemon's bridge (1500), so the confound was in-pod vs in-container, not the architecture. Emulation was never involved — the identical qemu-emulated container succeeds at 1450 and fails at 1500, and the break point bisects to exactly the pod's own `eth0` MTU with no slack. **Derive this number; never hardcode it and never make it a chart value** — it is a property of the cluster's CNI, which an operator should not have to know or keep in sync. The sidecar shares the pod's network namespace, which is what makes it readable in the first place. `erun-devops-dind-entrypoint_test.sh` locks the resolver (default-route selection, arg ordering, jumbo frames, and the degrade-to-default arms) by driving the real script against a stubbed procfs/sysfs and a stubbed `dockerd-entrypoint.sh`; `erun-devops-chart_test.sh` locks that the chart still embeds and invokes it. Both run via `make check`'s `helm-chart-tests` target. Keep the wrapper's failure to resolve an MTU non-fatal: a daemon that refuses to start is strictly worse than one bridging at the default.

## Wrapping And Pinning Third-Party Service Images

Components that run an upstream image unmodified (PostgreSQL, PowerDNS, Zitadel, and zot's hosted-registry wrapper (`erun-oci-registry`) today; other platform singletons next) follow one shape, generalized from `erun-backend-postgres`. Treat that component as the template. Do not bake a third-party image reference straight into a chart, and do not pull a floating upstream tag.

- **Pin the upstream version in a `VERSION` file.** `erun-devops/docker/<name>/VERSION` holds the exact upstream tag (e.g. `18.3` for `erun-backend-postgres`). It is the single source of truth for what version this component wraps; bump it deliberately in its own reviewable change.
- **Wrap it in a passthrough `Dockerfile`.** `erun-devops/docker/<name>/Dockerfile` is `ARG <UPSTREAM>_VERSION=<version>` + `FROM <upstream>:${<UPSTREAM>_VERSION}` and nothing more, unless the component genuinely needs added content. Wrapping (rather than referencing `docker.io/<upstream>` from the chart) gives the image an erun-owned name, publishes it to the env's registry alongside the runtime image, and lets it ride the same fingerprint promote-and-skip path as every other built component.
- **Reference it through `imageOverrides` in the chart.** The template defaults the image to `<registry>/<name>:<version>` and lets `imageOverrides.<name>` win when set — e.g. `{{ default (printf "%s/<name>:<version>" $containerRegistry) (index (default dict .Values.imageOverrides) "<name>") }}` (see `erun-devops/k8s/erun-backend-postgres/templates/postgres.yaml`). Keep the template's default tag aligned with the `VERSION` file: they pin the same upstream version in two places and must move together. `erun deploy` threads an override in as `--set-string imageOverrides.<name>=<image>` (`erun-common/deploy.go`), so a caller can point one env at a specific build without editing the chart — the same mechanism the runtime image uses via `imageOverrides.erun-devops`.
- **Register it as an opt-in component and sequence it per env.** The chart directory name is the component name; its tenant-agnostic base joins `deployComponentBaseOrder` (`erun-common/deploy_components.go`), which sets the default rank and makes the component offerable, and it is ordered per environment under `environments.<env>.k8s.deployments` (see Runtime Chart Rules). A passthrough wrapper carries no locally-built source beyond the `FROM`, so it participates in fingerprint promote-and-skip: an unchanged wrapper is promoted rather than rebuilt, and its chart deploy is skipped when nothing changed.
- **Record the published fingerprint on first release.** The first release that publishes `<name>:<VERSION>` computes a content fingerprint; add the matching `docker.fingerprints.<name>` entry to `.erun/config.yaml` in that same commit. The value is not a secret of the release: a wrapper's fingerprint is a pure function of its build-context files (the chart is excluded, and a passthrough consumes no `ERUN_VERSION`), so `erun build --dry-run` from the component's `docker/<name>/` directory prints the exact `fp-<hash>` tag the publishing release will compute — read it from there rather than guessing, and confirm the algorithm by re-deriving an already-recorded wrapper's hash the same way so later builds pull-and-promote instead of rebuilding (see the `docker.fingerprints` rule under Runtime Image Rules). Clear or bump the entry whenever the wrapper's content or pinned version changes. A version-pinned base's co-located Helm chart is deliberately **excluded** from its image fingerprint (`hashComponentChartInto` in `erun-common/build_incremental.go` skips builds whose version comes from their own build-dir `VERSION` file): the chart tracks the release version and is bumped every cycle, but the wrapped image content is the pinned upstream version, and the chart is not published in lockstep (only the runtime devops chart is). Folding it in would churn the fingerprint every release and defeat the pin, so the recorded fingerprint stays valid across releases until the wrapper's Dockerfile/COPY content or pinned `VERSION` changes — do not re-introduce chart hashing for these bases.
- **Reclaim the image's provenance label.** A passthrough `FROM` inherits every OCI label the upstream set, including `org.opencontainers.image.source`. Left alone, the published package attributes itself to the vendor's repository and the registry links it there rather than to this one, which puts it outside anything repo-scoped. Every wrapper therefore sets `LABEL org.opencontainers.image.source` to this repository. Registry **visibility** is a separate axis and is *not* label-driven: a newly created package starts private whatever its labels say, linking it to a public repository does not change that, and there is no API for it — switching it to public is a registry-UI action, and a private package cannot be pulled by a cluster. Do not conflate the two; they fail identically from the outside.
- **Singletons extend this shape, they do not abandon it.** A component that needs more than a plain passthrough — extra config baked in, host-level networking (e.g. PowerDNS binding `:53` via `hostNetwork`/`NodePort`/LoadBalancer), its own Secret/PVC — still pins via `VERSION`, wraps via a `Dockerfile`, references via `imageOverrides`, and registers as a component. Add the component-specific chart resources on top of that base rather than special-casing the image reference.

## Build Workflow

- `erun build` should behave as one coherent workflow across transports and modules. This module provides the runtime assets consumed by that workflow rather than defining a separate local policy.
- Tests run inside the build, per the delivery-pipeline convention (docs `/pipeline`, "How you set it up — and where tests run"): the `erun-devops` Dockerfile has a `test` stage that runs `make check`, and the builder stage depends on its marker, so a failing gate fails the build and no image is tagged. Pin test stages to `--platform=$BUILDPLATFORM` so the suite runs natively once per build instead of once per target arch under emulation. Any erun-driven build — developer machine, runtime pod, or a future erun-owned build system (#521) — runs the same in-build gate, so every built or released image is a tested build.
- **The `builder` stage's `COPY --from=test /test-ok` marker sits before its own two heavy `RUN` steps (erun/emcp compile, from-source golangci-lint install), not after them.** `test` and `builder` are otherwise independent stages (same base image, no data dependency), so BuildKit is free to run them at once — and without the early gate, it does: `make check`'s own golangci-lint pass then races a *second* full from-source golangci-lint build plus two Go compiles, all sharing the `erun-dind` sidecar's fixed memory limit, on every genuine (non-cache-hit) rebuild. `erun`'s own build orchestration is not the source of that overlap — `runMultiPlatformBuild` (`erun-common/build_docker_commands.go`) already builds each image's two platforms strictly one after another, and `push`/`release`/`build --deploy` already force image-level concurrency to one (`runDockerBuildsSequentially` in `erun-common/build_run.go`) — so this Dockerfile-internal stage race was the one remaining concurrent-compile path. Moving the gate earlier costs nothing on a cache hit (the whole image build is skipped by fingerprint promotion) and only adds wall-clock on a genuine rebuild, trading a small amount of time for not exhausting the sidecar. Do not move it back after the two `RUN` steps without re-checking this.
- **The test stage carries a pinned Node/Yarn toolchain** (a `node` stage — same COPY-out-of-a-pinned-image pattern as `goroot` below — feeding the full three-member Yarn workspace (`erun-kit`, `erun-ui/frontend`, `erun-console`) into `make check` via the root Makefile's `test-frontend` target, issue #1207). `erun-ui/frontend`'s gate needs its generated Wails bindings regenerated first (`erun-ui/generate-wailsjs.sh`, run by `test-frontend` before that gate); `erun-ui/build.sh` still runs the same three gates redundantly as a fast local signal. Adding a fourth workspace member means adding its `COPY` here too, the same rule the Go `LINT_MODULES` COPYs already follow.
- **The test stage also carries a pinned `helm` binary**, fetched directly (`get.helm.sh`, version shared with the final image via the `HELM_VERSION` ARG declared once at the top of the Dockerfile) rather than copied out of another stage, feeding the `erun-devops/k8s` chart tests into `make check` via the root Makefile's `helm-chart-tests` target. Every `k8s/*_test.sh` chart test needs only `helm template` — no cluster, no docker — so this is enough to run all of them in the bare `golang` test image; a chart test that needs more than `helm` cannot join this target and must be wired the way `erun-devops/docker/erun-backend-db/migrate_test.sh` is instead (see the `erun-backend-db` component bullet above). `COPY erun-devops/k8s /src/erun-devops/k8s` brings in the charts and scripts `helm-chart-tests` iterates; a new `k8s/*_test.sh` needs no further Makefile or Dockerfile change, but a chart added outside `erun-devops/k8s/` would.
- **`erun-devops/dns01-webhook`'s own `go test ./...` runs via the root Makefile's `test-erun-dns01-webhook` target**, `COPY`d into the test stage's context the same way the `LINT_MODULES` COPYs are (this module carries no `.golangci.yml` and no `LINT_MODULES` entry, so it needs no lint COPY, only a test one). It had neither a test stage of its own nor a `LINT_MODULES` entry, so its real regression coverage — including a fix for a cleanup path that must tolerate an already-deleted token Secret — sat reachable only by a contributor running `go test` from the module by hand.
- **Pin any stage to `--platform=$BUILDPLATFORM` when it is explicitly cross-compiled or emits architecture-independent output**, not only test stages. A Go builder stage that sets `CGO_ENABLED=0` with explicit `GOOS`/`GOARCH` (the `builder` stages in `erun-devops`, `erun-backend-api`, and `erun-dns01-webhook`) already selects its output arch through those flags — the compiler itself has no reason to run as the target arch, so pinning it to the build host lets the compiler run natively instead of under qemu, for free. The same applies to a static-site or other build whose output is copied out with no architecture of its own (the `erun-docs` builder stage already does this). The counter-case matters just as much: never pin a stage that ships as the final image layer for a target arch, or that runs target-arch binaries — doing so bakes host-arch content into an image tagged for the other architecture, which then fails at runtime there (an `npm install -g` or `apk add` in a final stage, or a passthrough final stage over a third-party image, must stay unpinned). When a pinned builder stage's output includes something that must ship into the final image as target-arch content — `erun-devops` copies the Go toolchain itself into the runtime image so in-pod `go build` works — source that piece from a separate, unpinned stage with no `RUN` instructions of its own (see the `goroot` stage in `erun-devops/docker/erun-devops/Dockerfile`): a stage that only pulls an image and copies files out of it needs no emulation, because nothing executes for the foreign arch, but it still resolves to the correct per-arch content because it isn't pinned to the build platform.
- All Docker builds shell out to plain `docker build` against the local daemon's BuildKit (the runtime image sets `DOCKER_BUILDKIT=1`). Docker 23+ routes `docker build` through the `docker-buildx` CLI plugin whenever BuildKit is enabled, so the runtime image installs the plugin into `/usr/local/lib/docker/cli-plugins/docker-buildx` as the BuildKit frontend driver. Cross-architecture builds rely on that plugin running against the local daemon plus binfmt — not on creating a separate buildx builder instance. BuildKit cannot be turned off because the Dockerfiles depend on `RUN --mount=type=cache,...`.
- Every `erun build`, `erun build --release`, and `erun deploy` invocation builds for both `linux/amd64` and `linux/arm64`. There is no single-platform code path. The reason: a single-arch artifact built locally cannot be deployed to a cluster of a different architecture, and arch-specific Dockerfile bugs should fail at developer-machine build time, not at remote deploy time.
- The default platforms are set on every `DockerBuildSpec` at construction (`resolveDockerBuildSpec`/`ResolveDockerBuildForImageReference`). Per-command configurators only flip `Push` (false for plain `erun build`, true for `--release` and `deploy`) — they do not touch `Platforms`.
- Build execution iterates per platform: `docker build --platform <p> --provenance=false -t <image>:<version>-<arch>`, then `docker tag` to attach the fingerprint cache tag (`fp-<hash>-<arch>`). When `Push` is true, after both arches have built and fp-tagged, the per-arch tags are pushed individually and assembled into a manifest list with `docker manifest create --amend` + `docker manifest push`. `--provenance=false` is required so each per-arch tag is a plain image manifest the assembly step can consume.
- Cross-architecture builds rely on the daemon having binfmt/qemu installed for the foreign arch — the runtime chart installs that before dind starts. Per-platform results land in the daemon's local image store, which is what lets fingerprint promotion (`docker tag <fp-tag> <release-tag>-<arch>` then push + manifest assembly) skip the `docker build` on the next run.
- Multi-arch builds must verify the daemon can produce every required platform. Failure mode: a missing binfmt entry, surfaced as a direct error rather than a confusing per-arch build failure.
- BuildKit cache mounts (`RUN --mount=type=cache,…` in the Dockerfiles) persist in `/var/lib/docker/buildkit` on the `<release>-docker` PVC, so repeated builds in the same namespace reuse Go module / apt / npm caches without publishing cache artifacts to the registry.
- Fingerprint cache tags (`<image>:fp-<hash>-<arch>`) are content-derived (Dockerfile + COPY sources, `.dockerignore`/`.gitignore` applied) and per-platform. For a charted component the contents of its deployed Helm chart are folded in too, so a chart-only edit moves the fingerprint and the image rebuilds and republishes its chart in lockstep — except for version-pinned base wrappers, whose chart is excluded (see "Wrapping And Pinning Third-Party Service Images"). The hash itself is platform-independent so a single content edit invalidates both per-arch fp tags simultaneously. Both arches must be present locally for a build to promote without rebuild; if either arch is missing, both arches rebuild and both fp tags are re-applied.
- **The `ERUN_VERSION` build arg is a fingerprint input for any Dockerfile that references it** (`hashBuildVersionInto` in `erun-common/build_incremental.go`, gated on `dockerfileConsumesVersion`). The fingerprint is an *artifact* identity, not a source identity, and for an image that resolves its own content from the version — `erun-devops` bakes it into the `erun`/`emcp` binaries via `-ldflags`, a wrapper selects its base with `FROM …:${ERUN_VERSION}` — two versions are two artifacts even when every file in the context is byte-identical. Without this a release whose only diff was `VERSION` promoted the previous release's image and the binary inside kept reporting the older version, so the published tag, the chart version, and `erun version` in the deployed pod disagreed. The folded value is the unsuffixed build-arg version, so both per-arch fingerprints move together; a snapshot build folds in the stable `<base>-snapshot` string, so dev builds still promote across timestamps. Images that never reference `ERUN_VERSION` keep a version-independent identity and still promote across releases — that is why the `docker.fingerprints` pins for `erun-ubuntu`, `erun-dind`, `erun-powerdns`, and `erun-backend-postgres` stay valid across version bumps. Do not "fix" a release that rebuilds `erun-devops` with no code change by relaxing this: the rebuild is the contract.
- Dry-run output for build, release, and deploy should show the real `docker build`, `docker tag`, `docker push`, and `docker manifest` commands, not just a summary.
- Do not switch the build flow to `docker buildx build`, multi-arch single-shot builds, or a dedicated container-driver builder instance. The current per-platform `docker build` path is what makes incremental promotion work: results land in the daemon's image store where `docker tag <real-arch> <fp-tag>` can attach the fingerprint cache tag. A naive `buildx build --push` skips the local store and breaks promotion, and `--load` is single-platform only, so a multi-arch buildx flow ends up iterating per platform anyway — the same shape as today, with extra moving parts. The buildx plugin shipped in the runtime image is allowed only in its role as the BuildKit frontend for plain `docker build`.

## Release Workflow

- Stable release behavior for this module currently means, in this order:
  - release chart metadata is rewritten so chart version and application version match the release
  - package-manager metadata for supported installers is updated together with the release when present
  - the release commit and a **local** tag are created — recoverable state, nothing public yet
  - the release-tagged Docker images and their charts are built and published, then read back from the registry to prove they resolve
  - only then does the tag reach origin, packaging checksums sync against the now-public archive, the next patch version is prepared, and the branches push
  - a release that cannot publish fails at the publish, leaving no public tag and `VERSION` still on the version it was releasing, so re-running retries the same version
- Candidate releases use candidate version tags and still rely on the same shared release/build orchestration.
- When changing release behavior, validate the repository-wide flow, not only this subtree. At minimum run the release-sensitive suites in `erun-common`, `erun-cli`, and `erun-mcp`.
- A non-erun tenant consumes erun's **published** charts by reference — it never forks or copies them:
  - **Runtime.** The default is image-only: `erun-build-env` produces a `<tenant>-devops` **image** (extending `erun-devops`) that rides into the published `erun-devops` chart as `imageOverrides.erun-devops`; no chart is added. Only when the pod shape needs more than a Dockerfile can express (sidecar, extra volume/env, RBAC) does `erun-build-env` add a thin `<tenant>-devops` **umbrella** that *depends on* `erun-devops` (never forks it); `erun push` publishes it as `charts/<tenant>-devops`. `deploy` then prefers that published `charts/<tenant>-devops:<version>` over `charts/erun-devops` on a sourceless env — the published analogue of the repo-local `<tenant>-devops`-first lookup (`resolvePublishedRuntimeChartReference` in `erun-common`, probed against the chart registry, controllable in tests via the `ERUN_PUBLISHED_CHART_PROBE_OVERRIDE` seam). It falls back to `charts/erun-devops` when the tenant publishes no umbrella. When deploy resolves the tenant's own `<tenant>-devops` umbrella, it **defaults `imageOverrides.erun-devops` to that umbrella's own image** (`<registry>/<tenant>-devops:<version>`, via `resolveDeployRuntimeImage`) unless the env sets an explicit `runtimeimage`: `push` publishes the image and umbrella together on the tenant's version line, so the umbrella's identity names the image and building it is sufficient — a mis/unset `runtimeimage` no longer silently falls back to the stock `erun-devops:<tenant-version>` (which that line never publishes → ImagePullBackOff). The **image-only** case (shared `charts/erun-devops`) carries no such signal, so it still needs `runtimeimage`, and the `erun` product tenant keeps the stock image.
  - **Components.** `erun deploy <tenant> <env> --components erun-backend-…` installs the published `charts/erun-backend-*` / `charts/erun-powerdns` / `charts/erun-docs` directly with `--set-string tenant=<tenant>`, which the tenant-scoping above renders as `<tenant>-*`. Optional per-env `<tenant>-<component>` umbrellas (`erun-blueprint-platform`) *depend on* the published `erun-<component>` charts for real-time patching or value overrides — again never copies.
  - To land a runtime change, publish it from the `erun` tenant first (build/release + push), then deploy the tenant, which pulls the new published image/chart by reference.

## Version and Metadata Rules

- Keep one canonical module version input and treat it as the source of truth for release-tagged runtime artifacts.
- Keep chart version and application version aligned during releases.
- If the release flow changes package-manager metadata, update both version references and checksums where required. Do not leave Homebrew or Scoop definitions partially updated.

## Testing Expectations

- When changing Dockerfiles, add or update tests that lock in the intended dependency ordering, cache behavior, or pinned tooling versions.
- When changing the chart, test both the shared runtime chart behavior and the tenant-generation contract when practical.
- When changing release/build behavior that affects this module, add regression tests at the layer that owns the behavior and keep transport-specific preview and trace expectations aligned.
